# Pheromone-mini V0.6 分功能需求列表

**版本：** V0.6  
**状态：** 冻结设计基线  
**实现语言：** C11

## 1. 文档目的

本文是 V0.6 的可执行功能需求清单。每项需求均明确输入、行为、输出、责任方和验收条件，并与 01～05 设计文档对应。它是独立需求基线，不替代完整软件设计方案。

## 2. 范围、角色与优先级

### 2.1 角色

- 上游 Data Bucket SDK：Object Commit、DataReadyEvent、Inline / DataRef 和 DataRef 生命周期。
- 本模块：App Registry、DIRECT Dependency、Event Trigger、Task Builder、Task Router、Delay Queue。
- 下游 Task Coroutine Pool：静态 Function 配置注册、原子任务入队、队列消费、协程调度、SO 加载和 handler 执行。

### 2.2 本期基础规则

- 仅一份 app.json。
- app_name 全局唯一。
- Bucket 在当前 Registry 全部 App 范围内全局唯一。
- so_name 是 /dev/shm 下的物理 SO 文件名；重复使用同一 so_name 时函数静态配置必须一致。
- 所有 SO 只导出无状态 handler。
- DIRECT 是独立依赖路径；Immediate / ByName 是两种 Trigger Primitive。
- 一个 Bucket 可以关联多个 Trigger。
- DataReadyEvent 不传 app_name。
- Pool 原子 try_enqueue；本模块不调用 wake_one。
- 全局 Delay Queue；不实现 Rerun 和 resource.timeout_ms。

## 3. App Registry 需求

### APP-01：单一 app.json 注册入口

- **优先级 / 责任方：** P0 / 本模块。
- **输入：** config_json、config_size。
- **行为：** 一次解析 App、Function、Bucket、DIRECT Dependency、Trigger 和 scheduler.delay_queue。
- **输出：** 注册成功或结构化配置错误。
- **验收：** 不依赖 function.json；不存在独立 Function / Trigger 注册 API。

### APP-02：app_name 全局唯一

- **行为：** Registry 中已有同名 App 时拒绝注册。
- **验收：** 重复注册返回 PM_ERR_DUPLICATE_APP，现有配置不受影响。

### APP-03：Bucket 全局唯一

- **行为：** 检查候选 App 内部及已注册全部 App 的 Bucket 名称。
- **验收：** 跨 App 重名返回 PM_ERR_DUPLICATE_BUCKET；不发布部分索引。

### APP-04：Function / SO 配置校验

- **行为：** 校验 so_name 安全文件名、资源和执行配置；入口固定 handler。
- **验收：** 路径穿越、非法资源值和未知字段被拒绝；不定义执行超时字段。

### APP-05：Pool 静态 Function 注册

- **行为：** 每个唯一 so_name 将 resource / execution 配置一次性注册给 Pool。
- **验收：** 重复相同 so_name 且配置一致时幂等；配置冲突时拒绝注册；失败时不发布 App。

### APP-06：全局 Bucket 索引

- **行为：** 建立 bucket → owning App + Trigger[] 索引。
- **验收：** DataReadyEvent 仅凭 bucket 即可定位 App 和 Trigger 列表。

### APP-07：DIRECT Dependency 索引

- **行为：** 建立 source_so_name → ordered target_so_name[]。
- **验收：** 所有来源和目标函数均已注册；无效引用导致整个 App 注册失败。

### APP-08：Trigger Index

- **行为：** 建立 bucket → 有序 TriggerConfig 列表。
- **验收：** 保留配置顺序，不按目标函数去重。

## 4. DIRECT Dependency 需求

### DIR-01：DIRECT 独立路径

- **责任方：** 本模块。
- **行为：** DIRECT 不属于 Trigger Primitive，不进入 Immediate / ByName 匹配器。
- **验收：** 内部路径、配置字段和测试均单独标识 DIRECT。

### DIR-02：来源 Function 识别

- **责任方：** 上游 Data SDK + 本模块。
- **输入：** DataReadyEvent.source_function。
- **行为：** Handler 通过 Object API 写对象时，SDK 从当前 TaskContext 注入来源 so_name；外部 Actor 可为空。
- **验收：** 来源函数存在 DIRECT 依赖时能正确定位；未知来源函数拒绝或按配置校验错误处理。

### DIR-03：目标函数展开

- **行为：** 一个来源 Function 可以对应一个或多个目标 Function。
- **验收：** 每个目标生成独立 TaskAction，不按目标去重。

### DIR-04：DIRECT 优先级

- **行为：** source_function 有 DIRECT 目标时走 DIRECT，跳过本次 Bucket Trigger；否则进入 Bucket Trigger。
- **验收：** 同时配置 DIRECT 和 Bucket Trigger 时不会双重触发。

### DIR-05：DIRECT 输入模式

- **行为：** DIRECT 默认以本次提交对象作为 INPUT_VALUE；载体仍由 SDK 选择。
- **验收：** Inline 复制；Shared-Memory 每个目标独立 retain。

## 5. Event Trigger 需求

### EVT-01：Commit 成功后通知

- **责任方：** Data SDK。
- **行为：** 仅成功 Commit 后调用 event_trigger_notify。
- **验收：** 写入失败或未提交对象不产生通知。

### EVT-02：最小 DataReadyEvent

- **字段：** bucket、key、session_id、payload_type、data_size、inline_data 或 data_ref；source_function 在函数输出场景提供。
- **行为：** 不传 app_name、event_id、trigger_name、trigger_option、target_function、IP 或 RPC 控制字段。
- **验收：** ABI 不含上述冗余字段。

### EVT-03：Immediate

- **行为：** 有效 DataReadyEvent 到达对应 Bucket 时命中。
- **验收：** 每次显式通知均产生独立命中。

### EVT-04：ByName

- **行为：** event.key 与配置 key_name 完全相等才命中，区分大小写。
- **验收：** 精确匹配通过；前缀、大小写不同均不命中。

### EVT-05：同 Bucket 多 Trigger

- **行为：** 遍历全部 Trigger；每条命中规则独立生成 Task。
- **验收：** Immediate 和 ByName 同时命中时产生两个 Task；相同目标 SO 不去重。

### EVT-06：DIRECT 与 Trigger 路径隔离

- **行为：** DIRECT 优先，未命中 DIRECT 才进入 Bucket Trigger。
- **验收：** 与 DIR-04 一致。

### EVT-07：显式通知边界

- **行为：** 不扫描 Bucket，不监听未通知覆盖写。
- **验收：** 同 Bucket/Key 覆盖但无新通知不触发。

### EVT-08：事件错误与部分成功

- **行为：** 非法事件整体拒绝；合法事件内单条规则构建失败不回滚其他成功项。
- **验收：** 结果计数准确，资源无泄漏。

## 6. Task Builder 需求

### TSK-01：输入模式映射

- **映射：** trigger_option 0=INPUT_VALUE，1=INPUT_KEY_VALUE，2=INPUT_KEY_ONLY；DIRECT 固定 INPUT_VALUE。
- **验收：** 每种输入模式传递内容正确。

### TSK-02：Inline 复制

- **行为：** 对每个需要 Value 的 Task 复制 Inline 字节。
- **验收：** notify 返回后释放原缓冲区，Task 内容仍正确。

### TSK-03：Shared-Memory retain

- **行为：** validate 后为每个需要 Value 的 Task 独立 retain DataRef。
- **验收：** N 个 Task 对应 N 次 retain；成功转 Pool，失败由 Router release。

### TSK-04：KEY_ONLY 不持有 Payload

- **行为：** 只复制 Key；payload_type=NONE，data_size=0。
- **验收：** 不复制 Inline，不 retain DataRef。

### TSK-05：最小 TaskInvocation

- **字段：** so_name、session_id、input_mode、可选 key、payload_type、data_size、Inline 或 DataRef。
- **不包含：** app_name、bucket、event_id、task_id、source_function、trigger_name、source_type、resource、execution、handler 名称。
- **验收：** C ABI 和 Mock Pool 收到的字段符合最小协议。

### TSK-06：每个命中规则独立所有权

- **行为：** 多 Trigger / 多 DIRECT 目标分别拥有自己的 Inline 副本或 DataRef 引用。
- **验收：** 一项失败不影响其他项，引用数最终平衡。

## 7. Task Router 需求

### RTE-01：原子 try_enqueue

- **责任方：** Router 负责策略；Pool 提供原子接收原语。
- **行为：** 单次 try_enqueue 完成容量判断和入队。
- **验收：** 不存在先查空位再单独入队的竞态窗口。

### RTE-02：Pool 返回码

- **返回：** ACCEPTED、NO_CAPACITY、NOT_READY、INVALID_TASK、ERROR。
- **验收：** 只有 NO_CAPACITY 进入 Delay Queue。

### RTE-03：成功入队所有权转移

- **行为：** ACCEPTED 后 Pool 复制 Inline 并接管 DataRef。
- **验收：** Router 不再释放 Pool 已接管资源。

### RTE-04：全局 Delay Queue 配置

- **配置：** scheduler.delay_queue.enabled、retry_interval_ms、max_wait_ms。
- **行为：** 对全部 App / Function 生效。
- **验收：** 不存在 Function 级延时配置。

### RTE-05：容量不足进入 Delay Queue

- **行为：** enabled=true 时保留任务和 DataRef，按间隔重试。
- **验收：** 重试成功后 Pool 接管，Delay 项删除。

### RTE-06：延时到期

- **行为：** 达到 max_wait_ms 后记录 TASK_DELAY_EXPIRED 并释放资源。
- **验收：** 不发生 Function 重执行。

### RTE-07：延时关闭

- **行为：** enabled=false 时 NO_CAPACITY 直接记录 PROCESS_DISPATCH_REQUIRED，dispatched=false。
- **验收：** 不进行跨进程、跨节点调用。

### RTE-08：其他 Pool 错误

- **行为：** NOT_READY、INVALID_TASK、ERROR 终止当前任务并释放资源。
- **验收：** 不被误当作 NO_CAPACITY 无限重试。

### RTE-09：不调用 wake_one

- **行为：** Router 不提供、不调用单独协程唤醒接口。
- **验收：** Mock Pool 的 wake 调用次数为 0；Pool 自己保证入队任务可被消费。

### RTE-10：Delay Queue 容量与退出清理

- **行为：** Delay Queue 有实现级上限；队列满或关闭时释放 Router 所有资源。
- **验收：** 不出现 DataRef 泄漏或悬空 Inline 指针。

## 8. 上下游协作需求

### API-01：Bucket 全局唯一

- Data SDK 不传 app_name。
- App Registry 通过 Bucket Index 定位 App。
- 重复 Bucket 注册失败。

### API-02：source_function 注入

- Function handler 输出对象时，SDK 从 TaskContext 注入 source_function。
- 外部 Actor 写入允许为空。
- source_function 只用于 DIRECT 查找，不进入普通 Trigger 配置。

### API-03：DataRef 版本稳定

- DataRef 指向本次 Commit 的不可变版本。
- 覆盖写不能污染已 retain 引用。
- validate / retain / release 语义明确。

### API-04：Pool 静态 Function 配置

- 注册阶段一次性提供 so_name、resource、execution。
- 不在每个 Task 重复传递。
- 不包含执行超时配置。

### API-05：TaskInvocation ABI

- 下游只接收执行所需最小字段。
- 固定加载 /dev/shm/<so_name> 并调用 handler。
- TaskContext 视图只在 handler 调用期间有效。

## 9. 可观测性与安全

### OBS-01：结构化日志

日志内部可包含 trace_seq、app_name、bucket、key、session_id、source_function、so_name、route_path、trigger_name、pool_result、delay_state、elapsed_ms、dispatched。内部日志字段不得因此进入外部 ABI。

### SAFE-01：SO 名称校验

拒绝路径分隔符、绝对路径、路径穿越和不安全字符。

### SAFE-02：Object API 约束

APP 不得通过文件 I/O、网络 Socket 交换业务数据，只使用 Object/Data SDK。

### SAFE-03：数据大小与引用

Object 写入容量由 SDK 校验；Scheduler 校验事件长度与 DataRef 元数据一致，不分配底层共享内存。

## 10. 本期明确不实现

- Rerun、Function 执行超时、resource.timeout_ms。
- wake_one 和协程唤醒实现。
- Node / Process Scheduler、跨进程和跨节点调度。
- Warm / Cold Executor、动态 Trigger 更新。
- 其他 Trigger Primitive。
- Data Bucket 底层存储、共享内存池、阈值判断和数据传输。
- Task Coroutine Pool 和 handler 执行实现。

## 11. 需求完成判定

每项 P0 必须具备：设计章节、C ABI 或内部 C 接口、单元测试、Mock 集成测试、错误路径和所有权测试。上下游责任方确认接口契约后，方可进入真实联调。
