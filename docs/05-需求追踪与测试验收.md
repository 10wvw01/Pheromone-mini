## 第 20 章 测试与验收方案

### 20.1 测试目标及环境

测试分为单元、契约、集成、并发、稳定性和性能六类。初期使用 Mock Data SDK、Mock Node Scheduler 和 Mock Task Pool；后续接入真实共享内存和真实协程池。

### 20.2 配置解析测试

- 正常 app.json + func.json。
- JSON 语法错误、字段缺失、类型错误。
- 重复 ID、未定义 Function、未定义 Bucket。
- DIRECT target 不存在。
- Trigger type 非 IMMEDIATE。
- SO 路径不存在或无权限。
- 两份配置 schema_version 不一致。
- 同一 source DIRECT 与 Bucket Trigger 冲突。

### 20.3 Registry 单元测试

验证 Function 查询、DIRECT 一对一/多目标、Trigger 按 Bucket 查询、空结果、重复目标去重、配置顺序稳定、只读快照生命周期。

### 20.4 DIRECT 依赖测试

| 用例 | 输入 | 预期 |
|---|---|---|
| DEP-T01 | A → B，A 输出 | 生成 B Task |
| DEP-T02 | A → B,C，A 输出 | 生成 B、C 两个 Task |
| DEP-T03 | A → B,C，指定 B | 只生成 B |
| DEP-T04 | A → B，指定 C | DEPENDENCY_TARGET_MISMATCH |
| DEP-T05 | A 无依赖 | 普通 Bucket 事件可继续 Trigger 路径 |
| DEP-T06 | fan-out 中 C 队列满 | B 保持成功，C 返回失败且释放引用 |

### 20.5 ImmediateTrigger 测试

- Bucket 命中且 enabled：立即产生一个 Action。
- Bucket 不匹配：不产生 Action。
- 事件未 Commit：拒绝。
- 同 Bucket 两个 ImmediateTrigger：产生两个 Action。
- disabled Trigger：不触发。
- 不支持 Trigger 类型：配置加载失败。
- 重复 event_id：去重窗口内不重复提交。
- VALUE、KEY_AND_VALUE、KEY_ONLY 三种输入模式正确写入 TaskDescriptor。

### 20.6 Task Builder 测试

验证静态 Function 信息、动态事件信息、DataRef 数量、retain 次数、构建失败释放、TaskDescriptor clone/destroy 和 ABI 版本检查。

### 20.7 Task Router 测试

- 数据本地节点有容量：优先本地。
- 数据本地节点无容量、远程可读：允许远程候选。
- 数据本地节点无容量、远程不可读：返回 NO_DATA_LOCAL_CAPACITY。
- Warm Process 可用：优先 Warm。
- 只有 Cold Process 可用：选择负载最低者。
- 所有进程队列满：返回 NO_PROCESS_CAPACITY/QUEUE_FULL。
- Pool 没有等待协程但 try_submit 成功：任务仍留队列。
- Pool STOPPING：不转移所有权。

### 20.8 上下游接口契约测试

Data SDK 契约测试：Commit-before-notify、事件队列满、事件重放、DataRef generation、retain/release。Task Pool 契约测试：try_submit 原子性、接受后所有权转移、失败后所有权保留、入队后唤醒尝试、完成后释放引用。

### 20.9 异常场景测试

覆盖无效 DataRef、内存分配失败、节点失联、进程退出、队列满、重复事件、fan-out 部分成功、配置不一致、SO 缺失和 Handler ABI 不兼容。

### 20.10 并发及稳定性测试

多生产者并发发布事件；同一 event_id 并发重复投递；多个 Event Consumer 并发路由；压力下验证无重复提交、死锁、双重释放和引用泄漏。使用 ThreadSanitizer、AddressSanitizer。

### 20.11 性能测试

分别测量 DataReadyEvent 出队、Trigger 匹配、Task Builder、Node Select、Process Select、Task Pool Submit 和 Commit-to-Worker-Start。输出 p50/p95/p99、吞吐、队列深度、CPU、RSS 和引用计数差值。

### 20.12 端到端 Demo 验收

最小 Demo：
1. Producer Task 写入 Bucket 数据。
2. Data SDK Commit 并发布 DataReadyEvent。
3. ImmediateTrigger 命中 Processor。
4. Task Builder 生成 TaskDescriptor。
5. Router 完成节点/进程选择。
6. Task Pool 接收 Task 并唤醒协程。
7. Processor Handler 通过 DataRef 读取数据并输出结果。
8. 所有 DataRef 正确释放。

### 20.13 验收标准

- 所有 P0 单元和契约测试通过。
- 至少一个 DIRECT 一对多 fan-out 场景通过。
- 至少一个 ImmediateTrigger 端到端场景通过。
- 队列满、DataRef 无效、进程停止等失败场景无静默丢任务、无引用泄漏。
- 日志可通过 event_id 关联到 task_id 和最终执行结果。
- 性能报告提供原始数据和分位数，不以单次最优值作为结论。

## 第 21 章 研发计划及待确认事项

### 21.1 研发任务拆解

| 阶段 | 任务 | 交付 |
|---|---|---|
| S0 | 冻结 Data SDK / Task Pool 接口 | 接口头文件、时序和错误码 |
| S1 | Config Loader + Registry | 配置加载和校验测试 |
| S2 | Event Trigger + DIRECT + ImmediateTrigger | 事件匹配单测 |
| S3 | Task Builder + DataRef 生命周期 | TaskDescriptor ABI 和引用测试 |
| S4 | Process Scheduler + Task Pool Adapter | 单进程队列投递 |
| S5 | Node Scheduler + Node Transport Adapter | 单节点实现和多节点接口 |
| S6 | Demo 集成和验收 | Producer → Processor 完整链路 |
| S7 | 性能和稳定性测试 | 报告、问题清单和优化建议 |

### 21.2 模块开发顺序

先冻结上下游接口，再开发核心逻辑。不要先把 Task Pool 内部结构写死在 Scheduler 中，也不要在 DataRef 语义未确定时完成 Task Builder。

### 21.3 上下游接口冻结要求

Data SDK 团队必须确认 DataReadyEvent、DataRef、队列模型、Commit 可见性和 retain/release。Task Pool 团队必须确认 TaskDescriptor ABI、try_submit 原子语义、队列满、唤醒和所有权转移。

### 21.4 模块独立测试

Config/Registry、Trigger、Task Builder、Node/Process Router、Adapters 均需有 Mock 单测。核心模块不能依赖真实 Data SDK 或 Pool 才能编译。

### 21.5 集成联调计划

先单节点单进程，再单节点多进程，最后多节点。每阶段保留事件和 Task trace，便于定位是 Trigger、节点路由、进程准入还是 Pool 入队问题。

### 21.6 Demo 交付物

- Scheduler 核心库和公共头文件。
- app.json、func.json 示例。
- Producer / Processor 示例 SO。
- Mock Data SDK、Mock Task Pool。
- 端到端启动脚本和测试用例。
- 接口契约测试报告、性能报告和问题清单。

### 21.7 待确认技术问题

| 编号 | 问题 | 需要确认方 | 影响 |
|---|---|---|---|
| Q-01 | DataRef 是 region+offset 还是 opaque handle？ | Data SDK | ABI、跨进程解析 |
| Q-02 | DataRef retain/release 是否跨进程安全？ | Data SDK | 生命周期 |
| Q-03 | DataReadyQueue 是 MPSC 还是 MPMC？确认机制是什么？ | Data SDK | Consumer 并发模型 |
| Q-04 | 事件队列满时是否支持持久待发布和重试？ | Data SDK | 可靠性 |
| Q-05 | DataRef 是否支持跨节点远程读取？ | Data SDK | Node Scheduler fallback |
| Q-06 | Task Pool 是否提供原子 try_submit？ | Task Pool | 入队与所有权 |
| Q-07 | Pool 是否负责 Task 完成后释放 DataRef？ | Task Pool / Data SDK | 避免双重释放 |
| Q-08 | Handler ABI 的最终签名和 TaskContext 字段？ | Task Pool / 业务开发 | SO 兼容性 |
| Q-09 | ProcessStatus 的容量指标由谁上报？ | Task Pool | 进程级调度 |
| Q-10 | Node Scheduler 是独立服务还是本地库？ | 架构团队 | 节点级部署 |
| Q-11 | DIRECT 和 Bucket Trigger 是否允许同一事件双路 fan-out？ | 需求方 | 路由优先级 |
| Q-12 | Task 超时、失败重试由谁负责？ | Task Pool / 业务方 | 执行可靠性 |

以上问题中 Q-01～Q-08 是进入真实集成前的 P0 接口冻结项；其余问题可在单节点 Demo 阶段同步确认。
