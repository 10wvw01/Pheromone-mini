# 第一部分：总体设计（第 1～3 章）

[返回 V0.5 主文档](../V0.5-完整软件设计方案.md)

## 第 1 章 项目背景与需求分析

### 1.1 业务背景与本期流程

SMC Actor 接收外部消息，通过 SDK 将数据写入 Data Bucket。Data SDK 在数据写入成功后通知 Event Trigger；Event Trigger 根据注册的 Immediate / ByName 规则判断是否触发函数，构建 Task 并交给 Task Router；Task Router 将 Task 提交给下游 Task Coroutine Pool。

| 步骤 | 行为 | 责任方 |
|---|---|---|
| ① | SMC Actor 处理外部消息，调用 SDK | 上游业务团队 |
| ② | Data SDK 将对象写入共享内存或消息载体 | Data Bucket SDK 团队 |
| ③ | SDK 通知数据就绪事件；Event Trigger 匹配规则 | 上游通知 + 本模块 |
| ④ | 命中后还原目标函数及输入，构建 Task | 本模块 |
| ⑤ | Task Router 向本进程任务队列提交 Task，并尝试唤醒一个协程 | 本模块调用下游接口 |
| ⑥ | 协程取出 Task，加载 SO 并调用 handler | Task Coroutine Pool 团队 |

本模块只负责步骤③、④、⑤中的调度与 Trigger 逻辑，不负责 Actor、对象存储、底层消息传输或任务执行。

### 1.2 V0.5 研发边界

本期由本模块实现四个逻辑模块：

1. **App Registry**：接收上游传入的单份 app.json，完成解析、校验、注册，并维护内部函数索引和 Bucket→Trigger 索引。
2. **Event Trigger**：接收 DataReadyEvent，按 Bucket 查找规则，执行 Immediate / ByName 匹配。
3. **Task Builder**：将每条命中规则还原为独立 TaskDescriptor，正确处理 Inline Payload 或 DataRef。
4. **Task Router**：向下游 Task Coroutine Pool 的本进程任务队列提交 Task；队列满时只记录“需要进程间分发”的日志，不实施跨进程分发。

Task Coroutine Pool、TaskQueue、工作协程、SO 加载和 handler 执行均由下游团队负责。共享内存分配、对象写入、对象索引、1KB 阈值判断及数据传输均由 Data Bucket SDK 团队负责。

### 1.3 注册与运行时边界

上游的配置注册入口只有 `register_app(config_json)`。不向上游分别暴露 Function Registry、Trigger Registry 或单独的 Trigger 注册 API。

- app.json 是应用注册的唯一配置文件，包含应用信息、函数清单、Bucket 清单和 Trigger 清单。
- App Registry 在 `register_app` 内部解析 JSON、校验引用并构建只读索引；Config Loader 不作为独立对外模块或独立注册入口。
- Function Registry、Trigger Registry 是 App Registry 内部的数据索引，不是上游独立管理的组件。
- 运行时数据事件通过统一的 `event_trigger_notify` 接口进入 Event Trigger；这是数据通知接口，不是第二套注册机制。

`app_name` 是 App Registry 中全局唯一的注册 KEY，不代表业务逻辑实体。一个进程可注册多个 app；每个 app 内的函数名、Bucket 和 Trigger 在该 app 作用域内解析。

### 1.4 功能需求

- 从单份 app.json 注册应用、SO 函数、资源/执行元数据、Bucket 和 Trigger。
- 每个 SO 固定导出无状态入口函数 `handler`。
- Trigger Primitive 仅支持 Immediate 和 ByName。
- 同一个 Bucket 可以关联多个 Trigger；一次事件可命中多条规则，并为每条命中规则生成独立 Task。
- Task 输入同时支持小数据 Inline Payload 和大数据 Shared-Memory DataRef。
- Task Router 只向本进程协程池任务队列提交；队列满仅日志并返回未接收。
- 对每个 Task 明确描述符复制、数据引用 retain/release 和队列所有权转移。
- 日志能够关联 app、event、trigger、task 和路由结果。

### 1.5 必须遵守的团队约束

| 约束 | 对本模块的影响 |
|---|---|
| 函数必须无状态，入口名固定为 `handler` | JSON 不配置入口名；TaskDescriptor 固定携带 handler 或由下游约定固定符号 |
| APP 不得直接使用文件 I/O、网络 Socket 交换数据 | 业务函数只能通过 Object/Data SDK 接口读写对象；本模块不提供文件/网络 API |
| 小数据直接通过消息传递，大数据进入共享内存，约 1KB 为分界 | SDK 负责选择载体；事件必须显式标记 payload_type，本模块不重复判断阈值 |
| 共享内存对象不可变，但同 Bucket/Key 可被覆盖；覆盖不产生变更通知 | 只有收到显式 DataReadyEvent 才触发；DataRef 必须绑定本次提交的数据版本 |
| 写入大小不得超过创建 Object 的容量 | 由 SDK/Object API 校验；本模块只校验事件声明与引用元数据一致 |
| 一个 Bucket 可被多个 Trigger 关联 | Trigger Registry 使用 Bucket→Trigger 列表，不能使用 Bucket→单个 Trigger |
| SO 固定放在每个节点的 /dev/shm | Function 只登记 so_name；下游框架按 /dev/shm/<so_name> 加载 |
| Task Coroutine Pool 由下游团队负责 | 本模块只调用队列提交与唤醒接口，不实现协程池 |

### 1.6 本期明确不实现

- DIRECT Dependency、DIRECT 独立分发路径及 Dependency Registry。
- BySet、ByBatchSize、ByTime、DynamicGroup、Redundant 等其他 Primitive。
- 节点级、进程级跨节点/跨进程调度，冷热实例选择、负载均衡、心跳和资源状态表。
- Task Coroutine Pool、TaskQueue、工作协程、SO Loader 和业务执行。
- Data Bucket 创建/销毁、共享内存池、对象索引、数据复制和传输机制。
- 1KB 阈值判断、Inline/Shared-Memory 转换、共享内存 GC。
- 动态修改 Trigger、持久化事件日志、自动重试、Exactly-once 和 P0 事件去重。
- 文件 I/O、网络 Socket 的 APP 沙箱或系统调用拦截；本期以接口约束、代码审查和集成验收落实。

### 1.7 术语

| 术语 | 含义 |
|---|---|
| App | 一份由 app.json 描述并注册的函数与 Trigger 配置集合 |
| app_name | App Registry 的全局唯一注册 KEY |
| Function | 一个 SO 对应的无状态 handler 执行单元 |
| Bucket / Key / Session | 数据命名空间、对象键和业务运行上下文 |
| DataReadyEvent | Data SDK 在对象写入成功后通知的事件 |
| Inline Payload | 随事件消息携带的小数据 |
| DataRef | 指向已提交共享内存对象版本的不透明引用 |
| Immediate | Bucket 收到有效数据事件时匹配 |
| ByName | 事件 Key 与配置的 key_name 完全相等时匹配 |
| TaskAction | 一条命中 Trigger 对应的内部待执行动作 |
| TaskDescriptor | 传递给下游任务队列的完整任务描述 |
| Task Coroutine Pool | 下游拥有的任务队列和工作协程执行框架 |

## 第 2 章 Pheromone 源码参考与设计继承

### 2.1 两级调度思想的取舍

Pheromone 的 Coordinator + Local Scheduler 是面向多节点、多执行实例的两级调度。本 Demo 不复制其分布式控制面，也不引入 Node Scheduler / Process Scheduler。仅借鉴其数据驱动、Bucket 组织和本地优先的基本思想：

- 上游数据写入后显式通知，而不是由本模块轮询共享内存。
- Trigger 根据 Bucket/Key 事件匹配函数。
- 命中后构建执行描述并交给本地执行入口。
- 本期本地执行入口就是下游 Task Coroutine Pool 的任务队列。

### 2.2 Data Bucket 的取舍

保留 Bucket、Key、Session 的逻辑标识。Pheromone 的对象命名、共享内存布局和 IPC 实现不照搬。数据由 Data Bucket SDK 管理，本模块只处理 DataReadyEvent 中的载体描述：

- 小数据：Inline Payload，Task Builder 在提交前复制到 TaskDescriptor。
- 大数据：Shared-Memory DataRef，Task Builder 为每个 Task retain 一份引用，不复制实际数据。
- Key 只用于规则匹配和上下文传递；不通过重新查询 Bucket/Key 读取“最新值”替代事件携带的数据版本。

### 2.3 Trigger 的取舍

V0.5 只实现 Immediate 和 ByName：

- Immediate：每个有效数据就绪事件命中该规则。
- ByName：仅当事件 Key 与配置的 key_name 完全相等时命中。
- 两者均为无状态匹配，不维护聚合计数、Key 集合或时间窗口。
- 同 Bucket 多规则按配置顺序逐条匹配，命中即分别生成 Task，不按目标函数去重。

DIRECT 在 Pheromone 中是独立依赖机制，但它不是本 Demo 的需求；V0.5 明确不实现，不保留空的 DIRECT 兼容路径。

### 2.4 源码映射

完整源码路径、原项目行为与裁剪原因见 [附录 A](appendix/A-Pheromone源码映射.md)。原项目能力仅作为研究证据，不自动成为本项目需求。

## 第 3 章 总体软件架构

### 3.1 总体架构

~~~mermaid
flowchart TD
    A["SMC Actor"] --> B["SDK / Data Bucket SDK"]
    B --> C["Object 写入与 Commit"]
    C --> D["DataReadyEvent"]
    subgraph M["单节点 / 单进程：本模块"]
      AR["App Registry<br/>register_app(app.json)<br/>内部 Function / Trigger 索引"]
      ET["Event Trigger<br/>Immediate / ByName"]
      TB["Task Builder<br/>Inline Copy / DataRef Retain"]
      TR["Task Router"]
      AR -.只读配置.-> ET
      AR -.函数元信息.-> TB
      D --> ET --> TB --> TR
    end
    TR -->|"try_enqueue"| Q["下游 Task Coroutine Pool / TaskQueue"]
    TR -->|"QUEUE_FULL：仅日志"| L["PROCESS_DISPATCH_REQUIRED"]
    Q -->|"wake_one"| W["工作协程"]
    W --> H["加载 /dev/shm/<so_name><br/>调用 handler"]
    C -.Inline 或 DataRef.-> TB
~~~

本模块不包含共享内存池和 TaskQueue 的实现。图中的 Inline / DataRef 是事件与任务之间的数据载体，不表示 Scheduler 负责数据存储。

### 3.2 控制流与数据流

**控制流：** 上游调用 register_app → App Registry 校验并发布配置 → SDK Commit 成功后通知 Event Trigger → 按 Bucket 查询规则 → Immediate/ByName 匹配 → Task Builder 生成 TaskDescriptor → Task Router 调用 try_enqueue → 成功后调用 wake_one。

**数据流：** Data SDK 将小数据放入事件消息，或为大数据提供 DataRef。小数据在 Task Builder 中复制到任务描述符；大数据仅传递 DataRef 并 retain。业务 Payload 不经过 JSON，不由 Scheduler 分配或转换。

### 3.3 关键架构原则

1. App Registry 是配置注册的唯一入口；内部 Function/Trigger 索引不独立对上游开放。
2. Trigger 只判断事件是否命中，不访问共享内存内容，不负责数据搬运。
3. 一个 Bucket 对应零到多个 Trigger；一个事件可生成零到多个 Task。
4. Task Builder 对每个命中规则单独构建 Task，输入数据所有权随 Task 明确传递。
5. Task Router 只负责本地队列提交与唤醒尝试，不执行任务、不跨进程分发。
6. Task Coroutine Pool 负责复制/保存队列描述符、取任务、加载 SO、执行 handler 和最终释放数据引用。

### 3.4 初始化、运行与销毁

初始化顺序：

1. 上游初始化 Data Bucket SDK 和下游 Task Coroutine Pool。
2. 创建 App Registry，并提供 Data SDK 与 Pool 的 Adapter。
3. 上游为每个应用调用 register_app，传入完整 app.json 内容。
4. App Registry 完成解析、校验、构建索引并原子发布；任一失败不得留下半注册 App。
5. 所有 App 注册完成后进入运行态，SDK 才能发送 DataReadyEvent。

销毁顺序：先停止 SDK 新通知并等待在途 notify 完成；再销毁 App Registry。已入队 Task 不再引用 Registry，但可能仍持有 DataRef；Data SDK 的引用服务必须存活到下游所有已接收 Task 完成、取消或失败清理。

### 3.5 Task 生命周期边界

~~~mermaid
stateDiagram-v2
    [*] --> EVENT_RECEIVED
    EVENT_RECEIVED --> NO_MATCH
    EVENT_RECEIVED --> MATCHED
    MATCHED --> BUILT
    MATCHED --> BUILD_FAILED
    BUILT --> ENQUEUED
    BUILT --> ROUTE_REJECTED
    ENQUEUED --> RUNNING
    ENQUEUED --> CANCELLED
    RUNNING --> SUCCEEDED
    RUNNING --> FAILED
    RUNNING --> CANCELLED
~~~

本模块负责 EVENT_RECEIVED 至 ENQUEUED / ROUTE_REJECTED；NO_MATCH 是正常结果。入队后的执行状态由下游管理。队列满时 Task 未被接收，不得标记为 ENQUEUED。
