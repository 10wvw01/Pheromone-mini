**版本：** V0.5  
**状态：** 需求基线 / 预研 Demo  
**适用范围：** 调度与 Event Trigger 模块  
**关联设计：** [V0.5 完整软件设计方案](../V0.5-完整软件设计方案.md)  
**关联验收：** [第五部分：需求追踪与测试验收](05-需求追踪与测试验收.md)

## 1. 文档目的

本文档将 V0.5 软件设计方案中的功能要求按模块拆分，明确每项功能的**目标、输入、处理规则、输出、异常行为、责任归属和验收标准**，作为研发拆任务、上下游接口评审、代码审查和测试验收的共同依据。

本文档不是架构设计的替代品，也不是测试用例的替代品：

- 软件设计方案回答“系统如何设计、模块如何协作”。
- 本文档回答“每个模块必须实现什么、哪些行为必须保证”。
- 测试验收方案回答“用什么测试证明需求已满足”。

V0.5 仅覆盖业务流程③④⑤：接收 DataReadyEvent、判断 Trigger、还原 Task、将 Task 提交给下游 Task Coroutine Pool。

## 2. 需求范围与约束

### 2.1 本期功能范围

| 模块 | 本期必须具备的能力 | 实现责任方 |
|---|---|---|
| App Registry | 单一 app.json 注册、校验、原子发布、内部索引 | 本模块 |
| Function / APP 合约 | 函数元信息、固定 handler、无状态和 Object API 约束 | 本模块定义合约；业务/部署落实 |
| Event Trigger | 接收通知、Immediate / ByName 匹配、多 Trigger 枚举 | 本模块 |
| Task Builder | TaskDescriptor 组装、Inline Copy、DataRef Retain | 本模块 |
| Task Router | 本进程 TaskQueue 提交、成功后唤醒、队列满记录需求 | 本模块 |
| Data Bucket SDK | Object 写入/Commit、载体选择、Inline 传输、共享内存和 DataRef | 上游 |
| Task Coroutine Pool | TaskQueue、协程、唤醒、SO 加载、handler 执行和最终释放 | 下游 |

### 2.2 冻结的基础规则

1. 运行范围为单节点、单进程；本模块不承担节点级或进程级调度。
2. Trigger 仅支持 Immediate 和 ByName。
3. 配置只使用一份完整 app.json，由上游调用 `register_app(config_json)`；不使用 function.json。
4. Function Index 和 Trigger Index 是 App Registry 的内部索引，不开放独立注册 API。
5. 一个 Bucket 可以关联多条 Trigger；每条命中规则独立生成一个 Task。
6. 业务 SO 固定部署于 `/dev/shm/<so_name>`，入口固定为无状态 `handler`。
7. APP 只能通过 Object/Data SDK 交换业务数据，不得直接使用文件 I/O、网络 Socket 等旁路通道。
8. Payload 类型由 Data Bucket SDK 决定：`INLINE` 或 `SHARED_MEMORY`。本模块不重复判断 1KB 阈值，不转换载体。
9. 队列满时只记录 `PROCESS_DISPATCH_REQUIRED`，明确 `dispatched=false`；本期不进行实际进程间分发。
10. 不实现 DIRECT Dependency，不保留 DIRECT 专用数据结构、索引、注册入口或执行分支。

### 2.3 优先级与责任标识

- **P0**：V0.5 Demo 必须满足的要求。
- **本模块**：由 Pheromone-mini Scheduler / Trigger 研发实现。
- **上游契约**：由 Data Bucket SDK 提供，本模块通过接口契约测试验证。
- **下游契约**：由 Task Coroutine Pool 提供，本模块通过接口契约测试验证。
- **业务/部署契约**：由业务 SO 或运行环境落实，本模块提供接口约束和检查要求。

## 3. App Registry 功能需求

### 3.1 APP-01：单一 app.json 注册入口

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** 上游必须能够将一份完整 app.json 的 JSON 内容传入 `register_app(registry, config_json, config_size)`，一次性注册一个 App。
- **输入：** app.json 原始 JSON 字符串及长度。
- **处理规则：**
  1. 同一文件中包含 App 元信息、functions、buckets、triggers。
  2. 注册时复制并规范化所需配置；调用返回后不依赖上游 JSON 缓冲区。
  3. 函数、Bucket、Trigger 在同一注册事务中完成校验和发布。
  4. 不要求调用者额外提供 function.json、function_paths 或逐个调用 Function / Trigger 注册 API。
- **输出：** 注册成功或明确的配置错误。
- **验收标准：** 仅提供合法 app.json 即可完成注册；删除 function.json 后不影响注册。

### 3.2 APP-02：app_name 全局唯一

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** App Registry 以 app_name 作为注册 KEY；同一 Registry 中不允许重复注册。
- **处理规则：** 重复 app_name 返回 `DUPLICATE_APP`，不得覆盖原配置，不得产生部分索引。
- **验收标准：** 注册 A 后再次注册同名 A，第二次失败且第一次注册的函数和 Trigger 配置保持不变。

### 3.3 APP-03：注册事务与配置校验

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** App 注册必须原子完成；任何解析、校验或索引构建错误均不得发布半成品。
- **校验范围：**
  - JSON 格式、字段类型、必填字段、重复字段、未知字段和输入长度。
  - app_name、Function、Bucket、Trigger 名称的长度及字符约束。
  - Function 名称在 App 内唯一；Bucket 名称唯一；Trigger 名称在 App 内唯一。
  - Trigger 引用的 Bucket 已声明、目标 Function 已注册。
  - Primitive 仅允许 IMMEDIATE / BY_NAME；ByName 必须提供 key_name，Immediate 不允许 key_name。
  - trigger_option 仅允许 0、1、2。
  - 资源字段数值必须有限、范围合法，整数型字段拒绝小数和溢出。
  - SO 名称必须为安全文件名，不允许绝对路径、目录分隔符或路径穿越。
- **输出：** 成功发布完整 AppRecord，或返回带字段路径的诊断错误。
- **验收标准：** 对非法 JSON、重复字段、未知字段、悬空函数引用、非法 SO 路径等输入，注册失败且 Registry 中不存在该 App。

### 3.4 APP-04：内部 Function Index

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** App Registry 必须根据 app.json 的 functions 构建只读 Function Index，供 Trigger 校验和 Task Builder 查询。
- **索引内容：** Function 名称、so_name、version、resource、execution；入口固定为 `handler`。
- **处理规则：** Function 名称在同一 App 内唯一；不同 app_name 的 App 可以有同名 SO，但配置和索引必须隔离。
- **验收标准：** 能按函数名查到完整静态元信息；不存在独立 Function Registry 注册入口。

### 3.5 APP-05：内部 Trigger Index 与多规则关联

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** App Registry 必须构建 Bucket → Trigger 列表的只读索引。
- **处理规则：**
  1. 一个 Bucket 可以关联零条、一条或多条 Trigger。
  2. 同一 Bucket 下的 Trigger 按 app.json 声明顺序保存。
  3. 每条 Trigger 独立保存 trigger_name、primitive_type、匹配参数、目标 Function 和 input_mode。
  4. 同一目标 Function 被多条 Trigger 指向时仍保留多条规则，不合并。
- **验收标准：** 一个 Bucket 配置 Immediate 与 ByName 两条规则后，索引返回两条独立记录且顺序稳定。

### 3.6 APP-06：固定 SO 文件位置与入口

- **优先级 / 责任方：** P0 / 本模块定义；下游/部署落实加载
- **需求描述：** Function 只声明安全 SO 文件名；SO 固定部署在 `/dev/shm/<so_name>`，所有 SO 固定导出 `handler`。
- **处理规则：**
  - app.json 不配置任意 so_path、目录或 entry。
  - App Registry 只校验 SO 文件名并写入 FunctionConfig / TaskDescriptor。
  - App Registry 不执行 dlopen；由下游 Pool 自动加载和解析 handler。
- **验收标准：** 非法路径被拒绝；TaskDescriptor 中 so_name 和 handler 信息正确；加载行为由下游负责。

### 3.7 APP-07：无状态 Function 与 Object API 合约

- **优先级 / 责任方：** P0 / 业务/部署契约
- **需求描述：** 业务 SO 的 handler 必须无状态、可重入；业务数据交换只能通过约定的 Object/Data SDK API。
- **禁止行为：**
  - 使用可变全局变量保存任务状态或依赖前一次调用结果。
  - 通过文件 I/O、网络 Socket、进程间私有通道等旁路交换业务数据。
  - 长期保存 TaskContext、Inline value 指针或 DataRef 映射视图。
  - 自行释放 Task Pool 持有的 DataRef。
- **验收标准：** 示例 SO 只导出 handler，通过 Object API 写入下游 Bucket；代码审查和集成测试不发现上述违规。V0.5 不承诺提供系统调用沙箱。

## 4. Event Trigger 功能需求

### 4.1 EVT-01：Commit 成功后通知

- **优先级 / 责任方：** P0 / 上游契约
- **需求描述：** Data Bucket SDK 仅在 Object 数据成功 Commit、且后续可按事件载体读取时，向 Event Trigger 发出 DataReadyEvent。
- **处理规则：**
  1. 写入失败或 Commit 失败不得通知。
  2. 通知必须携带 app_name、bucket、key、event_id、payload_type、data_size，以及对应载体字段。
  3. Event Trigger 处理通知时，对应提交数据必须已经可见。
- **验收标准：** 写入失败不产生 Task；Commit 成功后通知可以被处理并读取到该次提交的数据。

### 4.2 EVT-02：Immediate Trigger 匹配

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** Bucket 下配置的 Immediate Trigger 对该 Bucket 的每个合法 DataReadyEvent 命中。
- **处理规则：**
  - 不检查 Key 名称，不累计对象数量，不等待其他对象。
  - 每个事件对每条 Immediate 规则最多产生一个 Task。
  - 不维护跨事件状态。
- **验收标准：** 同一 Bucket 连续收到多个合法事件时，每个事件均分别命中 Immediate 规则。

### 4.3 EVT-03：ByName Trigger 精确匹配

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** ByName Trigger 仅当事件 Key 与配置的 key_name 完全相等时命中。
- **处理规则：**
  - 比较区分大小写，采用完整字符串相等。
  - 不支持前缀、后缀、正则、模糊匹配、通配符或 Key 集合匹配。
  - 不匹配时不生成 Task。
- **验收标准：** Key 与 key_name 完全相等时命中；仅大小写不同、前缀相同或后缀不同均不命中。

### 4.4 EVT-04：同 Bucket 多 Trigger 独立触发

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** Event Trigger 必须遍历该 Bucket 下的全部 Trigger 规则，逐条匹配。
- **处理规则：**
  1. 不因第一条规则命中而停止遍历。
  2. 每条命中规则独立生成 Task。
  3. 即使多条规则目标 Function 相同，也不合并、不去重。
  4. 结果按 Trigger 配置顺序返回。
- **验收标准：** 一个事件同时命中同 Bucket 的 Immediate 和 ByName 规则时，生成两个独立 Task。

### 4.5 EVT-05：只响应显式 DataReadyEvent

- **优先级 / 责任方：** P0 / 本模块 + 上游契约
- **需求描述：** Trigger 只处理 SDK 显式发送的 DataReadyEvent；不主动扫描 Bucket，也不监听未通知的覆盖写。
- **处理规则：**
  - 同 Bucket/Key 再次写入或覆盖，但没有新通知时，不触发新 Task。
  - 一次新 Commit 对应一次新通知时，按当前配置正常匹配。
  - 不通过定时轮询、Key 查询或数据扫描补发事件。
- **验收标准：** 覆盖写但无通知时，Trigger 命中数不增加。

### 4.6 EVT-06：多规则部分成功与结果统计

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** 同一事件命中多条规则时，各规则独立执行 Task Build 和 Enqueue；一条规则失败不得回滚其他规则。
- **结果统计：**
  - `matched`：命中规则数。
  - `enqueued`：成功进入本地队列的 Task 数。
  - `overflow`：因队列满未接收的 Task 数。
  - `failed`：构建失败或 Pool 其他拒绝的 Task 数。
  - 对结果缓冲区足够的合法事件，必须满足 `matched = enqueued + overflow + failed`。
- **处理规则：** 每条规则分别记录 build_status、route_status、task_id；不能用单个总状态掩盖部分成功。
- **验收标准：** 多规则中部分入队、部分队列满、部分构建失败时，逐项结果和计数正确，已入队 Task 不回滚。

### 4.7 EVT-07：Trigger Option 与输入模式

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** Trigger 的 trigger_option 决定 Task 输入视图，不改变 SDK 选择的 Payload 类型。
- **映射规则：**

| trigger_option | 输入模式 | Task / handler 可见内容 |
|---:|---|---|
| 0 | INPUT_VALUE | 仅 value 与长度 |
| 1 | INPUT_KEY_VALUE | Key + value 与长度 |
| 2 | INPUT_KEY_ONLY | 仅 Key，不提供 value |

- **处理规则：** 仅允许 0、1、2；非法值在注册阶段拒绝。KEY_ONLY 不得为了构造 Task 而复制或 retain Payload。
- **验收标准：** 三种配置分别提供正确的 handler 输入视图。

## 5. Payload 与 Task Builder 功能需求

### 5.1 PAY-01：Inline Payload 接入与复制

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** 当 DataReadyEvent 的 payload_type 为 INLINE 时，Task Builder 必须从事件中的 inline_data 构造 Task 自有数据副本。
- **处理规则：**
  1. Inline 指针由 Data SDK 借用给 notify，仅保证在 notify 返回前有效。
  2. 每条命中且需要 value 的 Trigger 都要有独立的 Task 数据副本。
  3. 入队成功后 Pool 持有的是 TaskDescriptor 中的数据副本，而不是 SDK 原始指针。
  4. 原始事件缓冲区在 notify 返回后释放或改写，不得影响已入队 Task。
  5. 超出 ABI 内联容量的 Inline 事件拒绝并返回明确错误；不得静默截断或由 Scheduler 转换成 Shared-Memory。
- **验收标准：** notify 返回后立即释放/改写原始缓冲区，Task 仍能读取完整、正确的字节。

### 5.2 PAY-02：Shared-Memory DataRef 接入与传递

- **优先级 / 责任方：** P0 / 本模块；DataRef 实现由上游提供
- **需求描述：** 当事件载体为 SHARED_MEMORY 时，Task Builder 必须校验 DataRef，并为每个需要 value 的 Task retain 一份引用。
- **处理规则：**
  1. DataRef 是 SDK 定义的不透明引用，不把进程内裸指针当作 DataRef。
  2. 先 validate，再对每条需要 value 的命中规则独立 retain。
  3. 不复制实际共享内存 Payload，只将 DataRef 和 data_size 写入 TaskDescriptor。
  4. 入队成功时，Pool 接管该 Task 的一份引用；入队失败时由 Router release。
  5. Pool 在 Task 执行完成、失败或取消后释放自己持有的引用。
- **验收标准：** 一个大对象命中 N 条需要 value 的规则时，产生 N 次 retain；各 Task 生命周期结束后引用逐份释放。

### 5.3 PAY-03：不重复执行载体选择与阈值判断

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** Scheduler 只根据 DataReadyEvent 显式 payload_type 选择接入路径，不判断数据大小来重新决定传输载体。
- **处理规则：**
  - 不在 Scheduler 中实现 1KB 阈值。
  - 不把 INLINE 转换为 SHARED_MEMORY，也不把 SHARED_MEMORY 转成 Inline。
  - 不实现 SDK 消息传输或共享内存分配。
  - Inline ABI 容量检查只用于防止结构体越界，不是载体选择策略。
- **验收标准：** 对不同 data_size，Scheduler 始终遵循 payload_type；不会自行改变载体类型。

### 5.4 PAY-04：DataRef 绑定不可变提交版本

- **优先级 / 责任方：** P0 / 上游契约（正式联调阻塞项）
- **需求描述：** DataRef 必须绑定产生该事件的具体 Commit 版本；在所有 Task 引用释放前，底层数据必须保持可读且内容不变。
- **处理规则：**
  - 同 Bucket/Key 后续覆盖写不得改变旧 DataRef 指向的数据。
  - 上游可使用版本化对象、Copy-on-Write、引用保护或等价机制实现。
  - Scheduler 不得在 Task 执行时仅凭 Bucket/Key 重新读取“当前最新值”替代原 DataRef。
- **验收标准：** 触发 Task 后覆盖同一 Key，已入队 Task 仍读取原提交版本；否则 T10 不通过，不准入真实端到端验收。

### 5.5 PAY-05：Object 容量由 SDK 强制校验

- **优先级 / 责任方：** P0 / 上游契约
- **需求描述：** APP 通过 Object API 写入时，写入长度不得超过创建 Object 时约定的容量。
- **处理规则：** Data SDK/Object API 必须执行容量校验并返回明确错误；本模块不直接写共享内存、不绕过 Object API 修改容量。
- **验收标准：** 超容量写入被 SDK 拒绝，不发生越界写入或内存破坏。

### 5.6 TSK-01：TaskDescriptor 字段完整

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** 每个命中规则构建的 TaskDescriptor 必须携带执行和输入所需的静态/动态信息。
- **至少包含：** task_id、event_id、app_name、function_name、so_name、固定 entry_name=handler、function_version、session_id、source_function（可选追踪字段）、trigger_name、source_type、resource、execution、bucket/key、input_mode、payload_type、data_size，以及 Inline 副本或 DataRef。
- **处理规则：** task_id 在本进程内唯一；不同规则生成不同 task_id；不得使用进程全局 current_app/current_function 代替 Task 自身字段。
- **验收标准：** 对照 app.json、DataReadyEvent 和命中 Trigger，TaskDescriptor 中字段值正确且任务之间不串线。

### 5.7 TSK-02：Task 不得持有 Inline 临时指针

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** 任何入队 Task 都不得引用 Data SDK 在 notify 期间借出的 Inline 原始地址。
- **验收标准：** 原始缓冲区释放或覆盖后，Task 数据不变；ASan/并发测试无 use-after-free。

### 5.8 TSK-03：每个 Shared-Memory Task 独立 retain

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** 每个需要读取 Shared-Memory value 的 Task 必须持有独立 DataRef 引用。
- **验收标准：** N 个 Task 对应 N 次 retain；每次入队拒绝由 Router 对应 release；成功入队的引用由 Pool 各自释放；无重复释放或泄漏。

### 5.9 TSK-04：KEY_ONLY 不持有 Payload

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** INPUT_KEY_ONLY Task 只携带 Key 及必要的事件/追踪元信息。
- **处理规则：** 不复制 Inline 字节、不 retain DataRef、不 map 共享内存、不向 handler 提供 value。
- **验收标准：** Inline 和 Shared-Memory 两种事件在 KEY_ONLY 下均不产生 Payload Copy 或 DataRef retain。

## 6. Task Router 功能需求

### 6.1 RTE-01：仅提交本进程 TaskQueue

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** Task Router 只向注入的本地 Task Coroutine Pool Adapter 提交 Task。
- **处理规则：** 不选择其他节点或进程，不维护远端队列，不实现 IPC、网络转发或负载均衡。
- **验收标准：** 正常入队只调用本地 try_enqueue；不存在跨进程发送调用。

### 6.2 RTE-02：try_enqueue 原子准入与描述符复制

- **优先级 / 责任方：** P0 / 下游契约
- **需求描述：** Pool 的 try_enqueue 必须将容量判断、准入和 TaskDescriptor 复制作为一个原子操作。
- **处理规则：**
  - 返回 ENQUEUE_OK：Task 已完整进入队列，Pool 已复制描述符并接管其 DataRef。
  - 返回任何拒绝状态：Task 未进入队列，Pool 未保存描述符，也未接管 DataRef。
  - 并发生产者不得超卖队列容量或出现半条 Task。
- **验收标准：** 并发压力和故障注入下，接受/拒绝结果与队列内容一致，引用所有权明确。

### 6.3 RTE-03：入队成功后尝试唤醒

- **优先级 / 责任方：** P0 / 本模块调用、下游实现
- **需求描述：** 仅当 try_enqueue 返回 ENQUEUE_OK 时，Router 才调用 wake_one。
- **处理规则：** 入队失败不调用 wake_one；唤醒结果作为独立字段记录，不覆盖 enqueue 结果。
- **验收标准：** 入队成功调用一次 wake_one；入队拒绝不调用 wake_one。

### 6.4 RTE-04：队列满只记录进程间分发需求

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** Pool 返回 ENQUEUE_QUEUE_FULL 时，本模块不缓存、不重试、不转发 Task。
- **处理规则：**
  - 返回该 Task 未接收。
  - 若 Task 持有 DataRef，由 Router 释放本次 retain。
  - 记录 `PROCESS_DISPATCH_REQUIRED`，日志必须包含 `dispatched=false`。
  - 不调用 IPC、网络或其他进程的调度接口。
- **验收标准：** 队列满时无 Task 进入队列、无 DataRef 泄漏、日志明确且无真实进程间分发。

### 6.5 RTE-05：Pool 其他拒绝状态与引用回收

- **优先级 / 责任方：** P0 / 本模块 + 下游契约
- **需求描述：** Pool 未就绪、资源不足、非法 Task、内部错误必须与队列满区分。
- **处理规则：** 每种拒绝状态映射为明确 route_status；只要 Pool 未返回 ENQUEUE_OK，均视为未接管描述符和 DataRef，由 Router 负责释放本次 retain。
- **验收标准：** 各拒绝码映射准确，不误记为 overflow；引用最终平衡。

### 6.6 RTE-06：无等待协程不改变入队成功

- **优先级 / 责任方：** P0 / 本模块 + 下游契约
- **需求描述：** 入队成功后即使 wake_one 返回 WAKE_NO_WAITER，也不能将 Task 视为入队失败。
- **处理规则：**
  - Task 仍留在 Pool 队列。
  - 不重复 enqueue，不释放 Pool 已接管的引用。
  - wake_one 返回 WAKE_ERROR 时只记录唤醒异常，不能撤销入队结果。
- **验收标准：** WAKE_NO_WAITER / WAKE_ERROR 不改变 enqueued 计数和 DataRef 所有权。

## 7. API、生命周期与可靠性需求

### 7.1 API-01：Registry 生命周期

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** 对外提供 Registry create、register_app、seal、notify、destroy 的明确生命周期。
- **处理规则：**
  1. 创建 Registry 时注入 Data SDK / Pool Adapter。
  2. 注册阶段允许注册多个不同 app_name 的 App。
  3. seal 后配置只读，拒绝新的注册。
  4. 运行期允许并发 notify。
  5. destroy 前停止新通知并等待所有在途 notify 完成。
  6. 不允许在 handler 回调或 notify 调用栈内销毁 Registry。
- **验收标准：** 生命周期非法调用返回明确错误；并发 notify 和安全销毁不产生悬空引用。

### 7.2 API-02：Data SDK Adapter 契约

- **优先级 / 责任方：** P0 / 上游契约
- **需求描述：** Data SDK 必须提供 DataRef validate / retain / release 能力和 Inline 缓冲区生命周期承诺。
- **处理规则：**
  - validate 不增加引用。
  - retain 成功恰好增加一份引用；失败不得增加。
  - release 恰好释放一份已 retain 引用。
  - Inline 数据至少在 event_trigger_notify 返回前有效且不可变。
  - Shared-Memory 基础 DataRef 在 notify 处理期间有效。
- **验收标准：** Mock 和真实 SDK 契约测试能证明 retain/release 平衡、失败语义和数据可读性。

### 7.3 API-03：Task Pool Adapter 契约

- **优先级 / 责任方：** P0 / 下游契约
- **需求描述：** Pool 必须提供 try_enqueue 和 wake_one，且明确所有权转移时点。
- **处理规则：** 仅 ENQUEUE_OK 表示描述符复制完成、队列接收成功和 DataRef 所有权转移；其他返回均不得接管。wake_one 仅在成功入队后调用。
- **验收标准：** 对接 Mock / 真实 Pool 后，接受、拒绝、唤醒和 DataRef 清理行为符合契约。

### 7.4 REL-01：并发事件隔离与引用平衡

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** 多线程并发 notify、多 App、多 Session、多 Bucket 事件不得发生任务上下文串线。
- **处理规则：**
  - 每次 notify 使用独立事件视图、临时 Task 和结果状态。
  - AppRecord / 索引在 seal 后只读。
  - Task ID 使用原子方式生成。
  - 不使用全局 current_app/current_function/current_event。
  - 每条 Task 的 DataRef 所有权独立计算。
- **验收标准：** 并发压力下 event_id、task_id、app_name、session_id、trigger_name 与输入数据一一对应；引用计数归零。

### 7.5 REL-02：安全退出与无悬空引用

- **优先级 / 责任方：** P0 / 本模块 + 上下游契约
- **需求描述：** Registry 销毁和 Task 完成不得导致在途 notify、Pool Task 或 DataRef 悬空。
- **处理规则：** Registry 只在停止新通知并排空在途 notify 后销毁；已经入队的 TaskDescriptor 必须独立于 Registry 内存；Pool 持有的 DataRef 由 Pool 生命周期管理至 Task 清理完成。
- **验收标准：** destroy 与并发 notify、池内待执行 Task 的边界测试无 use-after-free、double-free 或引用泄漏。

## 8. 可观测性与性能需求

### 8.1 OBS-01：结构化日志关联

- **优先级 / 责任方：** P0 / 本模块
- **需求描述：** 关键注册、匹配、构建、路由和唤醒结果必须可通过关联 ID 追踪。
- **关键字段：** app_name、event_id、task_id、session_id、bucket、trigger_name、target_function、payload_type、data_size、route_status、wake_status、duration_ns。
- **处理规则：**
  - 记录 APP 注册成功/失败、事件非法/未命中、Trigger 命中、Task 构建失败、入队成功/拒绝、队列满、唤醒无等待者/失败。
  - 不记录业务 Payload、DataRef 敏感内容或完整对象数据。
  - 队列满日志必须包含 `dispatched=false`。
- **验收标准：** 能按 event_id 还原一次事件命中的所有规则和 Task 结果；日志中无业务 Payload。

### 8.2 PERF-01：热路径性能基线

- **优先级 / 责任方：** P0 / 本模块；SDK/Pool 分段提供数据
- **需求描述：** 建立注册路径、事件通知、Trigger 匹配、Task 构建、入队和唤醒的分段性能基线。
- **测量场景：** Immediate、ByName 命中/未命中、单/多 Trigger、Inline、Shared-Memory、KEY_ONLY、队列正常/饱和。
- **统计指标：** 吞吐、p50/p95/p99、样本数、CPU/RSS、notify 延迟、Task Build / Enqueue 延迟、Inline 复制字节、DataRef retain/release 次数、队列满比例。
- **验收标准：** 固定硬件、编译选项、并发度、队列容量和数据规模，输出可复现报告；未实测前不承诺微秒级 SLA。

## 13. 需求完成判定

一项需求只有同时满足以下条件，才能标记为完成：

1. 责任方已明确，依赖的上下游接口已冻结。
2. 设计文档中的数据结构、状态和错误行为与实现一致。
3. 对应测试用例通过，且测试结果可复现。
4. 对于上游/下游契约，必须有真实 SDK / Pool 的契约验证；Mock 通过不能替代真实联调。
5. 涉及 DataRef 的路径完成 retain/release 计数核对。
6. 队列满、部分成功、唤醒无等待者等边界状态均有明确测试结果。
7. 不得以“代码已编译”或“Mock 返回成功”作为整项需求验收通过的唯一依据。

V0.5 的最终验收以本需求列表、五部分 21 章设计方案和 T01–T34 测试验收结果共同为准。
