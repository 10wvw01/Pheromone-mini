# 第三部分：API 接口规范（V0.6）

[返回 V0.6 主文档](../V0.6-完整软件设计方案.md)

> 本文是 Pheromone-mini V0.6 的跨模块 API Contract。上游 Data Bucket SDK、下游 Task Coroutine Pool 和本模块研发均以本文的接口方向、C 原型、参数语义、返回码、内存所有权及调用时序为对接依据。本文描述的是进程内 C11 API / ABI，不是 HTTP、RPC 或网络协议。

## 1. 文档范围与接口边界

### 1.1 参与方

| 参与方 | 职责 | 与本模块的接口关系 |
|---|---|---|
| 框架启动器 / 上游配置调用方 | 创建调度模块、加载 app.json、完成启动初始化 | 调用本模块提供的生命周期 API |
| Data Bucket SDK | Commit 数据、生成 DataReadyEvent、管理共享内存 DataRef | 调用本模块通知 API；向本模块提供 DataRef Adapter |
| Pheromone-mini 调度模块 | App Registry、DIRECT、Event Trigger、Task Builder、Task Router、Delay Queue | 本文定义的 API 提供方 |
| Task Coroutine Pool | Function 静态注册、任务准入入队、队列消费、协程唤醒和执行 | 向本模块提供 Pool Adapter API |
| Function Handler | 接收 TaskContext、处理输入、通过 Object API 写出数据 | 遵循 Pool / Object SDK 提供的执行 ABI |

### 1.2 接口方向

~~~mermaid
flowchart LR
    BOOT["框架启动器"] -->|"调用：create / register_app / seal / destroy"| PM["Pheromone-mini"]
    SDK["Data Bucket SDK"] -->|"调用：event_trigger_notify"| PM
    PM -->|"回调：validate / retain / release"| SDK
    PM -->|"回调：register_function / unregister_function / try_enqueue"| POOL["Task Coroutine Pool"]
    POOL -->|"创建 TaskContext 并调用 handler"| HANDLER["Function Handler"]
    HANDLER -->|"send_object"| SDK
~~~

### 1.3 本文接口分组

| 分组 | API 提供方 | API 使用方 | API 数量 | 说明 |
|---|---|---|---:|---|
| A. 本模块对外 API | Pheromone-mini | 框架启动器、Data Bucket SDK | 5 | 本模块必须实现并导出的 API |
| B. 下游 Pool API | Task Coroutine Pool | Pheromone-mini | 3 | Pool 必须实现并通过 Adapter 注入 |
| C. DataRef API | Data Bucket SDK | Pheromone-mini | 3 | SDK 必须实现并通过 Adapter 注入 |
| D. Handler 执行 ABI | Task Coroutine Pool / Object SDK | Function Handler | 2 | Pool 调用 Handler；Handler 使用 Object API |

**边界约束：**

1. 本模块不实现 Data Bucket、共享内存池和底层数据搬运；数据写入和 DataRef 生命周期由 Data Bucket SDK 负责。
2. 本模块不实现 Task Coroutine Pool、协程唤醒和 Handler 执行；任务容量判断、入队、消费者发现和执行由 Pool 负责。
3. 本模块只向 Pool 调用原子 try_enqueue，不再单独调用 wake_one。
4. 本期没有 Node Scheduler、Process Scheduler、跨进程转发或跨节点转发 API。
5. Function / Trigger 配置统一来自 app.json；不提供独立 function.json 注册 API，也不提供运行时动态 Trigger 更新 API。

## 2. API 清单

### 2.1 A 组：本模块提供给上游的 API

| API ID | API 名称 | 调用方 | 调用阶段 | 功能 |
|---|---|---|---|---|
| PM-API-001 | pm_registry_create | 框架启动器 | 初始化 | 创建 Registry，注入 DataRef 与 Pool Adapter |
| PM-API-002 | register_app | 框架启动器 / 配置加载器 | 初始化 | 注册一份完整 app.json |
| PM-API-003 | pm_registry_seal | 框架启动器 | 初始化结束 | 结束注册，发布只读运行态 |
| PM-API-004 | event_trigger_notify | Data Bucket SDK | 运行期 | 通知一次成功 Commit，执行 DIRECT / Trigger 判断并路由任务 |
| PM-API-005 | pm_registry_destroy | 框架启动器 | 关闭 | 停止通知、等待在途调用、释放 Registry 及 Router 持有资源 |

### 2.2 B 组：下游 Task Coroutine Pool 必须提供的 API

以下 API 不是 Pheromone-mini 对外导出的函数，而是 Pool 通过 pm_task_pool_adapter_t 注入的回调。

| API ID | API 名称 | 调用方 | 功能 |
|---|---|---|---|
| POOL-API-001 | register_function | Pheromone-mini 注册流程 | 注册 SO 对应的静态 resource / execution 配置 |
| POOL-API-002 | unregister_function | Pheromone-mini 注册事务回滚 | 撤销本次事务中新注册的 Function 配置 |
| POOL-API-003 | try_enqueue | Task Router | 原子执行容量判断和任务入队，并返回是否接管任务 |

### 2.3 C 组：上游 Data Bucket SDK 必须提供的 API

以下 API 通过 pm_data_ref_adapter_t 注入。本模块只调用，不负责实现 DataRef 存储与引用计数。

| API ID | API 名称 | 调用方 | 功能 |
|---|---|---|---|
| DATA-API-001 | validate | Task Builder | 校验 DataRef 有效性及数据长度 |
| DATA-API-002 | retain | Task Builder | 为一个需要 Value 的 Task 增加一份 DataRef 引用 |
| DATA-API-003 | release | Task Router / Pool 资源交接前后 | 释放本模块持有的一份 DataRef 引用 |

### 2.4 D 组：Handler 执行 ABI

| API ID | 名称 | 提供方 | 使用方 | 功能 |
|---|---|---|---|---|
| HANDLER-ABI-001 | handler | Function SO | Task Coroutine Pool | 固定的 SO 执行入口 |
| OBJECT-API-001 | send_object | Object SDK，经 TaskContext 注入 | Function Handler | 提交输出对象；SDK Commit 成功后通知 Event Trigger |

## 3. 公共类型与返回码

### 3.1 DataRef 句柄

~~~c
typedef struct {
    uint64_t opaque_token;
} pm_data_ref_t;
~~~

pm_data_ref_t 是不透明句柄。上面的 token 仅用于表达接口形态，不规定 Data SDK 的真实二进制布局。调用方不得解读 token、转换为裸指针或自行释放其底层内存。

### 3.2 本模块公共状态码

~~~c
typedef enum {
    PM_OK = 0,
    PM_ERR_INVALID_ARGUMENT = -1,
    PM_ERR_CONFIG = -2,
    PM_ERR_DUPLICATE_APP = -3,
    PM_ERR_DUPLICATE_BUCKET = -4,
    PM_ERR_DUPLICATE_FUNCTION = -5,
    PM_ERR_UNKNOWN_BUCKET = -6,
    PM_ERR_UNKNOWN_FUNCTION = -7,
    PM_ERR_INVALID_DEPENDENCY = -8,
    PM_ERR_INVALID_TRIGGER = -9,
    PM_ERR_INVALID_PAYLOAD = -10,
    PM_ERR_DATA_REF = -11,
    PM_ERR_NO_MEMORY = -12,
    PM_ERR_REGISTRY_SEALED = -13,
    PM_ERR_POOL_REGISTER = -14,
    PM_ERR_INTERNAL = -15,
    PM_ERR_GLOBAL_SCHEDULER_CONFIG_CONFLICT = -16
} pm_status_t;
~~~

| 返回码 | 含义 | 典型场景 |
|---|---|---|
| PM_OK | 成功 | API 执行成功；通知无匹配也返回成功 |
| PM_ERR_INVALID_ARGUMENT | 参数非法 | 必填指针为空、长度不合法 |
| PM_ERR_CONFIG | 配置或生命周期状态错误 | JSON 不合法、Registry 尚未 Seal 就收到运行期通知 |
| PM_ERR_DUPLICATE_APP | App 重复 | Registry 已存在同名 App |
| PM_ERR_DUPLICATE_BUCKET | Bucket 重复 | 当前 Registry 的不同 App 声明相同 Bucket |
| PM_ERR_DUPLICATE_FUNCTION | Function 重复 | 单 App 内 Function / SO 名称冲突 |
| PM_ERR_UNKNOWN_BUCKET | Bucket 未注册 | 通知引用不存在的 Bucket |
| PM_ERR_UNKNOWN_FUNCTION | Function 未注册 | source_function 或目标 SO 不存在 |
| PM_ERR_INVALID_DEPENDENCY | DIRECT 配置非法 | 来源或目标 Function 引用错误 |
| PM_ERR_INVALID_TRIGGER | Trigger 配置非法 | Trigger Primitive、Bucket 或目标配置错误 |
| PM_ERR_INVALID_PAYLOAD | Payload 非法 | 类型、长度或数据指针不匹配 |
| PM_ERR_DATA_REF | DataRef 操作失败 | validate / retain 失败或引用无效 |
| PM_ERR_NO_MEMORY | 内存不足 | Registry、索引或任务副本分配失败 |
| PM_ERR_REGISTRY_SEALED | Registry 已封存 | Seal 后仍调用 register_app |
| PM_ERR_POOL_REGISTER | Pool 静态注册失败 | register_function 返回非成功结果 |
| PM_ERR_INTERNAL | 内部处理失败 | 索引异常、任务构建或路由内部错误 |
| PM_ERR_GLOBAL_SCHEDULER_CONFIG_CONFLICT | 进程级配置冲突 | 不同 App 的 Delay Queue 配置不一致 |

### 3.5 通知结果结构

~~~c
typedef struct {
    size_t direct_matched;
    size_t trigger_matched;
    size_t enqueued;
    size_t delayed;
    size_t rejected;
    size_t failed;
} pm_notify_result_t;
~~~

| 字段 | 统计口径 |
|---|---|
| direct_matched | 本次通知命中的 DIRECT 目标数 |
| trigger_matched | 本次通知命中的 Trigger 规则数 |
| enqueued | 成功被 Pool 接收的 Task 数 |
| delayed | 进入 Delay Queue 等待重试的 Task 数 |
| rejected | 最终拒绝且不再重试的 Task 数 |
| failed | 构建或路由过程中发生处理失败的 Task 数 |

该结构是单次 event_trigger_notify 调用的结果，不是全局累计统计。调用前由本模块清零；调用返回后由调用方读取。

## 4. A 组：Pheromone-mini 对外 API 规格

### 4.1 PM-API-001：创建 Registry

**功能：** 创建调度模块 Registry，注入 DataRef Adapter 和 Task Pool Adapter，建立后续注册和运行所需的上下文。

~~~c
pm_status_t pm_registry_create(
    pm_registry_t **out,
    const pm_data_ref_adapter_t *data_adapter,
    const pm_task_pool_adapter_t *pool_adapter);
~~~

| 参数 | 方向 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| out | OUT | pm_registry_t ** | 是 | 输出 Registry 句柄；失败时置为 NULL |
| data_adapter | IN | const pm_data_ref_adapter_t * | 是 | Data SDK 提供的 validate / retain / release 回调表 |
| pool_adapter | IN | const pm_task_pool_adapter_t * | 是 | Pool 提供的 register / unregister / try_enqueue 回调表 |

**返回值：** PM_OK 表示创建成功；失败返回 PM_ERR_INVALID_ARGUMENT、PM_ERR_NO_MEMORY 或 PM_ERR_CONFIG。

**调用约束：**

1. 必须在 register_app 之前调用。
2. 两个 Adapter 的结构体内容由本模块在调用期间复制；其 ctx 指向的对象及回调代码必须持续有效，直到 pm_registry_destroy 返回。
3. Adapter 的必需回调不得为空。
4. 一个 Registry 对应一个进程内调度实例；进程级 Delay Queue 配置由该 Registry 管理。

**使用示例：**

~~~c
pm_registry_t *registry = NULL;
pm_data_ref_adapter_t data_adapter = make_data_adapter();
pm_task_pool_adapter_t pool_adapter = make_pool_adapter();

pm_status_t rc = pm_registry_create(
    &registry, &data_adapter, &pool_adapter);
if (rc != PM_OK) {
    /* 记录初始化失败，不得继续注册或通知 */
}
~~~

### 4.2 PM-API-002：注册 App 配置

**功能：** 解析、校验并原子注册一份完整 app.json，建立 App、Function、DIRECT Dependency、Bucket 和 Trigger 索引，并将 Function 静态配置注册给 Pool。

~~~c
pm_status_t register_app(
    pm_registry_t *registry,
    const char *config_json,
    size_t config_size);
~~~

| 参数 | 方向 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| registry | IN | pm_registry_t * | 是 | 已创建且尚未 Seal 的 Registry |
| config_json | IN | const char * | 是 | UTF-8 app.json 字节缓冲区 |
| config_size | IN | size_t | 是 | JSON 缓冲区字节数，不包含额外终止符要求 |

**返回值：** PM_OK 表示该 App 完整注册；失败返回对应配置错误或 PM_ERR_POOL_REGISTER。

**处理规则：**

1. 只接收 app.json；Function、DIRECT、Bucket、Trigger 均在同一配置中声明，不提供独立注册 API。
2. 本模块在函数返回前完成 JSON 解析，并深拷贝后续运行期需要的配置字符串和数组；调用方可在返回后释放 config_json。
3. 校验 app_name、so_name、Bucket、DIRECT 来源与目标、Trigger 引用及输入模式。
4. app_name 在 Registry 内全局唯一；Bucket 在 Registry 管理的全部 App 之间全局唯一。
5. 每个 so_name 对应 /dev/shm 下的物理 SO 文件名。不同 App 复用同一 so_name 时，resource / execution 必须完全一致。
6. 每个唯一 so_name 在注册阶段调用一次 Pool 的 register_function；相同配置重复注册应幂等，冲突配置必须拒绝。
7. 注册采用事务语义：任一步骤失败，不发布候选 App 的任何索引；撤销本事务中新注册的 Pool Function。已被其他已注册 App 使用的 so_name 不得被回滚注销。
8. scheduler.delay_queue 是进程级配置：首个成功注册的 App 建立全局配置，后续 App 的 enabled、retry_interval_ms、max_wait_ms 必须完全一致，否则返回 PM_ERR_GLOBAL_SCHEDULER_CONFIG_CONFLICT。
9. Seal 后调用 register_app，返回 PM_ERR_REGISTRY_SEALED。

**使用示例：**

~~~c
const char app_json[] = "{ /* 完整 app.json */ }";
pm_status_t rc = register_app(registry, app_json, sizeof(app_json) - 1U);
if (rc != PM_OK) {
    /* 根据状态码定位 JSON、引用或 Pool 注册问题 */
}
~~~

### 4.3 PM-API-003：封存 Registry

**功能：** 结束启动期配置注册，将 Registry 切换为只读运行态，使运行期通知可以安全并发查询索引。

~~~c
pm_status_t pm_registry_seal(pm_registry_t *registry);
~~~

| 参数 | 方向 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| registry | IN | pm_registry_t * | 是 | 已创建的 Registry |

**返回值：** PM_OK 表示封存成功；非法参数返回 PM_ERR_INVALID_ARGUMENT；重复封存或状态不允许时返回 PM_ERR_REGISTRY_SEALED。

**调用约束：**

1. 所有 app.json 注册完成后调用一次。
2. Seal 成功后，不允许新增或修改 App、Function、DIRECT、Bucket、Trigger 配置。
3. Seal 成功后才允许调用 event_trigger_notify。
4. 运行期索引只读；多个线程可以并发调用 event_trigger_notify。

### 4.4 PM-API-004：提交数据就绪通知

**功能：** 接收 Data Bucket SDK 对一次成功 Commit 的通知，执行 DIRECT 优先判断或 Bucket Trigger 匹配，构建 TaskInvocation 并交给 Task Router。

~~~c
pm_status_t event_trigger_notify(
    pm_registry_t *registry,
    const pm_data_ready_event_t *event,
    pm_notify_result_t *result);
~~~

#### 4.4.1 入参与出参

| 参数 | 方向 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| registry | IN | pm_registry_t * | 是 | 已 Seal 的 Registry |
| event | IN | const pm_data_ready_event_t * | 是 | 本次 Commit 的数据就绪事件 |
| result | OUT | pm_notify_result_t * | 是 | 本次调用的匹配、入队、延时、拒绝和失败计数 |

#### 4.4.2 DataReadyEvent 结构

~~~c
typedef struct {
    const char *bucket;
    const char *key;
    const char *session_id;
    const char *source_function;

    pm_event_payload_type_t payload_type;
    uint64_t data_size;

    union {
        struct {
            const void *data;
            size_t size;
        } inline_payload;

        pm_data_ref_t shared_memory;
    } payload;
} pm_data_ready_event_t;
~~~

| 字段 | 类型 | 必填 | 规格 |
|---|---|---|---|
| bucket | const char * | 是 | 全局唯一 Bucket 名称；用于定位所属 App 和 Trigger 列表 |
| key | const char * | 是 | 本次 Commit 的对象 Key；ByName 按完全相等、区分大小写匹配 |
| session_id | const char * | 是 | 业务 Session 标识，透传至 TaskInvocation |
| source_function | const char * | 条件必填 | Function Handler 写对象时由 SDK 从 TaskContext 注入 so_name；外部 SMC Actor 可为 NULL |
| payload_type | pm_event_payload_type_t | 是 | PM_EVENT_INLINE 或 PM_EVENT_SHARED_MEMORY |
| data_size | uint64_t | 是 | 本次 Commit 的数据字节数 |
| payload.inline_payload.data | const void * | INLINE 时 | Inline 数据地址；非零长度时不得为空 |
| payload.inline_payload.size | size_t | INLINE 时 | 必须与 data_size 一致 |
| payload.shared_memory | pm_data_ref_t | SHARED_MEMORY 时 | 指向本次 Commit 不可变数据版本的 DataRef |

**明确不传递：** app_name、event_id、trigger_name、primitive_type、trigger_option、target_function、active_trigger_names、IP、response_address、request_id。Trigger 规则由 Registry 内部查找；事件追踪序号由本模块内部生成。

#### 4.4.3 返回值与处理结果

| 返回值 | 语义 |
|---|---|
| PM_OK | 事件格式合法且处理完成；无匹配也是成功 |
| PM_ERR_INVALID_ARGUMENT | registry、event 或 result 指针非法 |
| PM_ERR_CONFIG | Registry 尚未 Seal |
| PM_ERR_UNKNOWN_BUCKET | bucket 未注册 |
| PM_ERR_UNKNOWN_FUNCTION | 非空 source_function 不属于该 Bucket 所属 App 的已注册 Function |
| PM_ERR_INVALID_PAYLOAD | payload_type、data_size、Inline 指针或长度不匹配 |
| PM_ERR_DATA_REF | SHARED_MEMORY DataRef 校验或 retain 失败 |
| PM_ERR_NO_MEMORY | 任务副本、内部对象或队列节点分配失败 |
| PM_ERR_INTERNAL | 其他内部处理错误 |

合法事件中某条规则的任务构建或路由失败，不回滚此前已经成功入队或进入 Delay Queue 的其他任务；result 保留本次已完成工作的计数，并通过失败状态 / failed 字段报告部分失败。

#### 4.4.4 匹配和路由顺序

1. 校验 Registry 状态、事件必填字段、Bucket 和 Payload。
2. 通过全局 Bucket Index 定位 owning App 及该 Bucket 的 Trigger 列表。
3. 若 source_function 非空，校验其属于 owning App 的已注册 Function。
4. 若 source_function 存在 DIRECT 目标，按 DIRECT 独立路径为每个目标生成 TaskAction，本次事件不再进入 Immediate / ByName Trigger 匹配。
5. 若没有 DIRECT 目标，按配置顺序遍历该 Bucket 的全部 Trigger：Immediate 对每次显式通知命中；ByName 仅在 event.key 与 key_name 完全相等时命中。
6. 每条命中规则独立构建 TaskInvocation；不按目标 so_name 去重。
7. Task Router 调用 Pool 的 try_enqueue。只有 PM_POOL_NO_CAPACITY 可以进入 Delay Queue；其他拒绝或错误按本规范终止并释放资源。

#### 4.4.5 线程安全与内存生命周期

- event_trigger_notify 可由多个线程并发调用；Registry 查询路径必须只读且线程安全。
- event、其中的字符串以及 Inline 缓冲区由 SDK 借用给本模块，至少保持有效至本次调用返回。
- Inline 数据需要进入 Task 时，本模块必须为每个 Value Task 独立复制；不得把 SDK 的临时指针直接交给异步队列。
- SHARED_MEMORY 数据需要进入 Task 时，本模块先调用 validate，再为每个 Value Task 独立 retain 一份 DataRef。
- KEY_ONLY 不复制 Value，也不 retain DataRef。
- 返回后，SDK 可以释放本次通知使用的 Inline 缓冲区；DataRef 基础引用仍由 SDK 按其生命周期管理。

### 4.5 PM-API-005：销毁 Registry

**功能：** 关闭调度模块实例，停止接收新通知，等待在途通知结束，并释放 Registry、索引、Delay Queue 和本模块仍持有的任务资源。

~~~c
void pm_registry_destroy(pm_registry_t *registry);
~~~

| 参数 | 方向 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| registry | IN | pm_registry_t * | 否 | 待销毁的 Registry；NULL 按空操作处理 |

**返回值：** 无。

**调用约束：**

1. 框架应先停止上游 Commit 通知入口，再调用 destroy。
2. destroy 必须阻止新的通知进入，并等待已进入的 event_trigger_notify 退出。
3. 清理 Delay Queue 中尚未被 Pool 接管的任务；释放 Router 持有的 Inline 副本和 DataRef。
4. 不得释放已由 Pool ACCEPTED 接管的任务资源；这部分由 Pool 在任务执行结束、失败或取消时释放。
5. destroy 不负责停止或销毁 Task Coroutine Pool，也不负责卸载仍被 Pool 使用的 SO。
6. destroy 返回后，Registry 及其内部索引不可再使用；Adapter 的 ctx 可以在确认其他模块不再使用后释放。

## 5. B 组：下游 Task Coroutine Pool API 规格

### 5.1 Pool Adapter 结构

本模块通过以下回调表访问下游 Pool：

~~~c
typedef struct {
    void *ctx;

    pm_pool_register_result_t (*register_function)(
        void *ctx,
        const pm_function_runtime_config_t *config);

    pm_pool_register_result_t (*unregister_function)(
        void *ctx,
        const char *so_name);

    pm_pool_submit_result_t (*try_enqueue)(
        void *ctx,
        const pm_task_invocation_t *task);
} pm_task_pool_adapter_t;
~~~

Pool 必须在 Registry 创建前完成初始化，并将三个回调及 ctx 注入本模块。回调函数在 Registry 生命周期内保持有效。

### 5.2 POOL-API-001：注册静态 Function 配置

**功能：** 在 App 注册阶段，将每个唯一 so_name 对应的资源和执行配置注册到 Pool。每个 Task 不再重复传递这些静态字段。

~~~c
pm_pool_register_result_t register_function(
    void *ctx,
    const pm_function_runtime_config_t *config);
~~~

**入参：**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| ctx | void * | 是 | Pool 实例上下文 |
| config | const pm_function_runtime_config_t * | 是 | Function 静态配置 |

静态配置结构：

~~~c
typedef struct {
    double cpu_cores;
    uint64_t memory_mb;
    uint8_t gpu_required;
    uint32_t gpu_device_count;
    uint64_t gpu_memory_mb;
    uint64_t disk_mb;
    uint64_t network_mbps;
} pm_function_resource_t;

typedef struct {
    const char *type;
    int32_t priority;
    const uint32_t *affinity;
    size_t affinity_count;
    uint32_t max_concurrency;
    uint8_t reuse;
} pm_function_execution_t;

typedef struct {
    const char *so_name;
    pm_function_resource_t resource;
    pm_function_execution_t execution;
} pm_function_runtime_config_t;
~~~

| 字段 | 类型 | 说明 |
|---|---|---|
| so_name | const char * | /dev/shm 下的 SO 文件名；不包含路径，不允许路径穿越 |
| resource.cpu_cores | double | CPU 核资源声明 |
| resource.memory_mb | uint64_t | 内存资源声明，单位 MB |
| resource.gpu_required | uint8_t | 是否需要 GPU |
| resource.gpu_device_count | uint32_t | GPU 设备数量 |
| resource.gpu_memory_mb | uint64_t | GPU 显存声明，单位 MB |
| resource.disk_mb | uint64_t | 磁盘资源声明，单位 MB |
| resource.network_mbps | uint64_t | 网络带宽声明，单位 Mbps |
| execution.type | const char * | Pool 执行类型 |
| execution.priority | int32_t | 调度优先级 |
| execution.affinity | const uint32_t * | CPU / 执行资源亲和配置数组 |
| execution.affinity_count | size_t | affinity 元素数量 |
| execution.max_concurrency | uint32_t | 最大并发数 |
| execution.reuse | uint8_t | 是否允许执行资源复用 |

**出参 / 返回值：**

| 返回值 | 语义 |
|---|---|
| PM_POOL_REGISTER_OK | 注册成功 |
| PM_POOL_REGISTER_INVALID | so_name 或静态配置非法 |
| PM_POOL_REGISTER_CONFLICT | 同一 so_name 已注册，但 resource / execution 不一致 |
| PM_POOL_REGISTER_ERROR | Pool 内部注册失败 |

**Pool 必须保证：**

1. 在回调返回前深拷贝 config 及其中的字符串、affinity 数组；不得保留调用方临时指针。
2. 相同 so_name、相同 resource / execution 重复注册时幂等成功。
3. 相同 so_name、不同 resource / execution 必须返回 CONFLICT。
4. 该配置不包含执行超时字段；本期不支持 resource.timeout_ms。
5. SO 固定导出无状态 handler，Pool 根据 so_name 加载 /dev/shm/<so_name>。

**调用时机：** register_app 的注册事务期间；不是每次 Task 入队时调用。

### 5.3 POOL-API-002：注销静态 Function 配置

**功能：** 仅用于 App 注册事务失败时，回滚本次事务中新注册的 Function 配置。

~~~c
pm_pool_register_result_t unregister_function(
    void *ctx,
    const char *so_name);
~~~

| 参数 | 方向 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| ctx | IN | void * | 是 | Pool 实例上下文 |
| so_name | IN | const char * | 是 | 待撤销注册的 SO 文件名 |

**返回值：** 使用 pm_pool_register_result_t。OK 表示注销成功；INVALID 表示参数非法；ERROR 表示 Pool 内部错误。

**调用规则：**

1. 本期不提供运行期 Function 热卸载能力。
2. 只有本次 App 注册事务首次引入、且没有被其他已注册 App 引用的 so_name 才允许回滚注销。
3. 如果同一 so_name 已被已有 App 使用，候选 App 注册失败时不得注销该 SO 的既有配置。
4. Pool 不应因 unregister_function 而误释放其他已接收任务正在使用的执行资源。

### 5.4 POOL-API-003：原子任务准入与入队

**功能：** Task Router 将构建完成的 TaskInvocation 提交给 Pool。Pool 在一个原子操作或同一临界区内完成容量判断和入队。

~~~c
pm_pool_submit_result_t try_enqueue(
    void *ctx,
    const pm_task_invocation_t *task);
~~~

**TaskInvocation 结构：**

~~~c
typedef struct {
    const char *so_name;
    const char *session_id;

    pm_input_mode_t input_mode;
    const char *key;

    pm_task_payload_type_t payload_type;
    uint64_t data_size;

    union {
        struct {
            const void *data;
            size_t size;
        } inline_payload;

        pm_data_ref_t shared_memory;
    } payload;
} pm_task_invocation_t;
~~~

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| so_name | const char * | 是 | Pool 定位 /dev/shm 下的 SO，并调用固定 handler |
| session_id | const char * | 是 | 业务 Session |
| input_mode | pm_input_mode_t | 是 | VALUE / KEY_VALUE / KEY_ONLY |
| key | const char * | 条件必填 | KEY_VALUE 或 KEY_ONLY 时必须提供 |
| payload_type | pm_task_payload_type_t | 是 | NONE / INLINE / SHARED_MEMORY |
| data_size | uint64_t | 是 | Value 字节数；NONE 时必须为 0 |
| payload.inline_payload.data | const void * | INLINE 时 | Inline Value 地址 |
| payload.inline_payload.size | size_t | INLINE 时 | 必须与 data_size 一致 |
| payload.shared_memory | pm_data_ref_t | SHARED_MEMORY 时 | 本模块已 retain 的 DataRef |

**字段组合约束：**

| input_mode | key | payload_type | 含义 |
|---|---|---|---|
| PM_INPUT_VALUE | NULL | INLINE / SHARED_MEMORY | 只传 Value |
| PM_INPUT_KEY_VALUE | 非空 | INLINE / SHARED_MEMORY | 传 Key + Value |
| PM_INPUT_KEY_ONLY | 非空 | NONE | 只传 Key，不持有 Value |

DIRECT 固定使用 PM_INPUT_VALUE。Trigger 的 trigger_option 映射为：0 → PM_INPUT_VALUE，1 → PM_INPUT_KEY_VALUE，2 → PM_INPUT_KEY_ONLY。

**返回值与任务所有权：**

| 返回值 | 是否接管任务 | Task Router 后续动作 |
|---|---|---|
| PM_POOL_ACCEPTED | 是 | 不再释放 Task 所携带的 Inline 副本 / DataRef |
| PM_POOL_NO_CAPACITY | 否 | Delay Queue 开启时暂存并重试；关闭时拒绝并释放 |
| PM_POOL_NOT_READY | 否 | 终止当前任务并释放资源，不进入 Delay Queue |
| PM_POOL_INVALID_TASK | 否 | 终止当前任务并释放资源，不进入 Delay Queue |
| PM_POOL_ERROR | 否 | 终止当前任务并释放资源，不进入 Delay Queue |

**Pool 必须保证：**

1. 容量检查与入队原子完成；禁止本模块先查询空位、再单独 enqueue。
2. ACCEPTED 返回前，复制 TaskInvocation 描述符及所有字符串；INLINE 必须复制数据字节。
3. ACCEPTED 时接管本模块已经 retain 的一份 DataRef 引用；Pool 不得要求 Router 再额外 retain。
4. 非 ACCEPTED 时不得保留任何调用方指针，不得复制并长期持有数据，也不得接管 DataRef。
5. Pool 内部负责让已入队任务被消费者发现并完成协程唤醒；本模块不调用独立 wake_one。
6. Pool 在 Handler 执行结束、失败或取消后，释放其持有的 Inline 副本和 DataRef。
7. try_enqueue 必须支持多线程并发调用。

### 5.5 Pool 消费与唤醒责任

Pool 的 API 契约不止于“队列写入成功”。PM_POOL_ACCEPTED 必须代表任务已进入可被消费者发现的状态。Pool 自身必须负责：

- 队列可见性与生产者 / 消费者同步；
- 已入队任务的协程唤醒或消费者调度；
- 从 TaskInvocation 构建 TaskContext；
- 根据 so_name 加载或复用 SO；
- 调用固定 handler；
- 维护任务执行状态和释放任务资源。

本模块不提供 wake_one、notify_worker 或其他独立唤醒调用。

## 6. C 组：Data Bucket SDK 必须提供的 DataRef API

### 6.1 DataRef Adapter 结构

~~~c
typedef struct {
    void *ctx;

    int (*validate)(
        void *ctx,
        pm_data_ref_t ref,
        uint64_t data_size);

    int (*retain)(
        void *ctx,
        pm_data_ref_t ref);

    void (*release)(
        void *ctx,
        pm_data_ref_t ref);
} pm_data_ref_adapter_t;
~~~

SDK 必须在 Registry 创建前提供完整回调。回调及 ctx 在 Registry 销毁前保持有效。

### 6.2 DATA-API-001：validate

**功能：** 校验 DataRef 是否有效、是否仍指向本次 Commit 对应的数据版本，以及其真实长度是否与 data_size 一致。

~~~c
int validate(
    void *ctx,
    pm_data_ref_t ref,
    uint64_t data_size);
~~~

| 参数 | 方向 | 类型 | 说明 |
|---|---|---|---|
| ctx | IN | void * | Data SDK 上下文 |
| ref | IN | pm_data_ref_t | 待校验的不透明 DataRef |
| data_size | IN | uint64_t | 事件声明的数据长度 |

**返回值约定：** 0 表示有效；非 0 表示无效或校验失败。

**副作用：** 不增加引用计数、不转移所有权、不延长 DataRef 生命周期。

### 6.3 DATA-API-002：retain

**功能：** 为一个即将进入 Task 的 Shared-Memory Value 增加一份独立引用，保证异步排队和执行期间数据仍然有效。

~~~c
int retain(
    void *ctx,
    pm_data_ref_t ref);
~~~

| 参数 | 方向 | 类型 | 说明 |
|---|---|---|---|
| ctx | IN | void * | Data SDK 上下文 |
| ref | IN | pm_data_ref_t | 待增加引用的数据句柄 |

**返回值约定：** 0 表示成功增加一份引用；非 0 表示失败，失败时不得留下未报告的引用增量。

**调用规则：**

1. Task Builder 在 validate 成功后调用 retain。
2. N 个需要 Value 的 Task 必须分别 retain N 次。
3. KEY_ONLY 不调用 retain。
4. retain 成功后，该引用由 Task Builder / Router 持有；Pool ACCEPTED 后转由 Pool 持有。

### 6.4 DATA-API-003：release

**功能：** 释放调用方持有的一份 DataRef 引用。

~~~c
void release(
    void *ctx,
    pm_data_ref_t ref);
~~~

| 参数 | 方向 | 类型 | 说明 |
|---|---|---|---|
| ctx | IN | void * | Data SDK 上下文 |
| ref | IN | pm_data_ref_t | 待释放的数据句柄 |

**返回值：** 无。

**调用规则：**

- Task Builder retain 成功后，若任务构建失败，必须由本模块 release。
- try_enqueue 非 ACCEPTED 时，DataRef 仍归 Router，Router 负责 release 或暂存重试。
- try_enqueue 返回 ACCEPTED 后，引用所有权转移给 Pool；本模块不得再次 release。
- Pool 在 Handler 完成、失败或取消后 release。
- 每一次成功 retain 必须且只能对应一次 release。

### 6.5 Data SDK 事件通知约束

1. SDK 只能在 Object Commit 成功后调用 event_trigger_notify；失败写入不得通知。
2. 同 Bucket / Key 覆盖写但没有产生新的成功 Commit 通知，不触发新 Task。
3. DataRef 必须绑定本次 Commit 的不可变数据版本；后续覆盖写不得污染已 retain 的旧版本。
4. INLINE 缓冲区至少在 event_trigger_notify 返回前有效。
5. Data SDK 负责决定 INLINE / SHARED_MEMORY 的载体选择阈值；本模块只按 payload_type 处理，不重复判断阈值。
6. Handler 写对象时，SDK 必须从当前 TaskContext 注入 source_function；外部 SMC Actor 写入允许为 NULL。

## 7. D 组：Handler 执行 ABI 与 Object API

### 7.1 HANDLER-ABI-001：固定 Handler 入口

**功能：** Pool 加载 SO 后调用统一入口，避免每个 Function 另行配置入口符号。

~~~c
typedef int (*pm_handler_fn)(
    const pm_task_context_t *ctx);

int handler(const pm_task_context_t *ctx);
~~~

TaskContext 结构：

~~~c
typedef int (*pm_object_send_fn)(
    const pm_task_context_t *task_ctx,
    const char *bucket,
    const char *key,
    const void *data,
    size_t size);

struct pm_task_context {
    const char *source_function;
    const char *session_id;
    pm_input_mode_t input_mode;
    const char *key;
    const void *value;
    size_t value_size;
    pm_object_send_fn send_object;
    void *object_ctx;
};
~~~

| 字段 | 提供方 | 说明 |
|---|---|---|
| source_function | Pool | 当前执行 SO 的 so_name；供 Object SDK 注入输出事件 |
| session_id | Pool | 来自 TaskInvocation |
| input_mode | Pool | 来自 TaskInvocation |
| key | Pool | KEY_VALUE / KEY_ONLY 模式下有效 |
| value | Pool | INLINE 或 Shared-Memory 映射后的只读 Value 视图 |
| value_size | Pool | Value 字节数 |
| send_object | Object SDK / Pool 注入 | Handler 写对象的回调 |
| object_ctx | Object SDK / Pool 注入 | Object SDK 上下文 |

**调用约束：**

1. 所有 Function SO 固定导出 handler。
2. Handler 返回 0 表示本次 Handler 执行成功；非 0 表示执行失败，由 Pool 记录任务失败。
3. TaskContext、key、value 视图只在 handler 调用期间有效；Handler 不得在返回后保存这些指针。
4. Handler 只能通过 Object API 交换业务数据，不使用文件 I/O 或网络 Socket 作为旁路数据通道。

### 7.2 OBJECT-API-001：send_object

**功能：** Function Handler 将处理结果写入指定 Bucket / Key。Object SDK 完成数据写入和 Commit；Commit 成功后构造 DataReadyEvent 并调用 event_trigger_notify。

~~~c
int send_object(
    const pm_task_context_t *task_ctx,
    const char *bucket,
    const char *key,
    const void *data,
    size_t size);
~~~

| 参数 | 方向 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| task_ctx | IN | const pm_task_context_t * | 是 | 当前 Handler 上下文 |
| bucket | IN | const char * | 是 | 目标 Bucket |
| key | IN | const char * | 是 | 目标对象 Key |
| data | IN | const void * | 条件必填 | 待写入数据；size 非零时不得为空 |
| size | IN | size_t | 是 | 数据长度 |

**返回值约定：** 0 表示对象写入及 Commit 成功；非 0 表示写入或 Commit 失败。只有 Commit 成功才允许产生 DataReadyEvent 通知。

**来源注入：** Object SDK 从 task_ctx->source_function 获取当前 so_name，并填入 DataReadyEvent.source_function；Handler 不需要也不允许自行伪造来源函数名。

## 8. 典型调用流程与示例

### 8.1 启动期：创建、注册、封存

~~~c
pm_registry_t *registry = NULL;
pm_data_ref_adapter_t data_adapter = make_data_adapter();
pm_task_pool_adapter_t pool_adapter = make_pool_adapter();

if (pm_registry_create(&registry, &data_adapter, &pool_adapter) != PM_OK) {
    return INIT_FAILED;
}

if (register_app(registry, app_json, app_json_size) != PM_OK) {
    pm_registry_destroy(registry);
    return INIT_FAILED;
}

if (pm_registry_seal(registry) != PM_OK) {
    pm_registry_destroy(registry);
    return INIT_FAILED;
}

/* 启动完成，Data SDK 可以开始发送 Commit 通知 */
~~~

### 8.2 运行期：Data SDK 通知一次成功 Commit

~~~c
pm_data_ready_event_t event = {
    .bucket = bucket_name,
    .key = object_key,
    .session_id = current_session_id,
    .source_function = source_so_name, /* 外部 Actor 可为 NULL */
    .payload_type = PM_EVENT_SHARED_MEMORY,
    .data_size = committed_size,
    .payload.shared_memory = committed_data_ref
};

pm_notify_result_t result;
pm_status_t rc = event_trigger_notify(registry, &event, &result);

if (rc != PM_OK) {
    /* 记录通知处理错误；result 仍可用于诊断已完成的部分工作 */
}
~~~

### 8.3 运行期：Pool 接收任务

~~~c
pm_pool_submit_result_t try_enqueue(
    void *ctx,
    const pm_task_invocation_t *task)
{
    /* 必须在同一原子操作 / 临界区内完成容量检查与入队 */
    if (!pool_is_ready(ctx)) {
        return PM_POOL_NOT_READY;
    }

    if (!pool_has_capacity_and_enqueue_atomically(ctx, task)) {
        return PM_POOL_NO_CAPACITY;
    }

    /* 实现必须保证入队前已复制描述符 / Inline，且接管 DataRef */
    return PM_POOL_ACCEPTED;
}
~~~

上例中的 pool_is_ready / pool_has_capacity_and_enqueue_atomically 是 Pool 内部实现示意，不属于本模块要求新增的外部 API。

### 8.4 关闭期：停止通知并销毁

~~~c
stop_data_sdk_notifications();
pm_registry_destroy(registry);
registry = NULL;
/* 确认 Pool 不再使用 Adapter ctx 后，再释放 Adapter 上下文 */
~~~

    participant POOL as Task Coroutine Pool
    participant H as Function Handler

    BOOT->>PM: pm_registry_create(adapters)
    BOOT->>PM: register_app(app.json)
    PM->>POOL: register_function(config)
    POOL-->>PM: REGISTER_OK
    BOOT->>PM: pm_registry_seal()
    SDK->>SDK: Object Commit 成功
    SDK->>PM: event_trigger_notify(DataReadyEvent)
    PM->>PM: DIRECT 优先 / Immediate 或 ByName 匹配
    PM->>PM: Task Builder 构建 TaskInvocation
    PM->>POOL: try_enqueue(TaskInvocation)
    alt ACCEPTED
        POOL-->>PM: ACCEPTED（接管任务）
        POOL->>POOL: 内部队列消费与协程唤醒
        POOL->>H: handler(TaskContext)
        H->>SDK: send_object(...)
        SDK->>SDK: Object Commit 成功
    else NO_CAPACITY
        POOL-->>PM: NO_CAPACITY（不接管）
        PM->>PM: Delay Queue 重试或按配置拒绝
    else 其他拒绝
        POOL-->>PM: NOT_READY / INVALID_TASK / ERROR
        PM->>PM: 记录错误并释放 Router 持有资源
    end
~~~

## 9. 内存所有权与生命周期契约

### 9.1 所有权总表

| 阶段 | Inline 数据 | Shared-Memory DataRef |
|---|---|---|
| SDK 调用 notify | SDK 借用，至少有效至 notify 返回 | SDK 持有基础引用 |
| Task Builder | 每个 Value Task 独立复制 | 每个 Value Task 独立 retain |
| Router / Delay Queue | Router 持有副本 | Router 持有已 retain 的引用 |
| Pool 返回 ACCEPTED | Pool 已复制 Inline，接管任务 | Pool 接管该份已 retain 引用 |
| Pool 返回非 ACCEPTED | Router 继续持有或释放副本 | Router 继续持有、重试或 release |
| Handler 执行结束 | Pool 释放副本 | Pool release |
| KEY_ONLY | 不复制 Inline | 不 retain DataRef |

### 9.2 不可违反的所有权规则

1. API 入参中的普通指针默认只在本次调用期间借用；除非接口明确规定接管，否则不得跨调用保存。
2. Pool 返回 ACCEPTED 是任务描述符、Inline 副本及 DataRef 引用的所有权转移点。
3. Pool 返回非 ACCEPTED 时，所有权不转移；Pool 不得保存任何入参指针或 DataRef。
4. 每一次成功 retain 必须且只能有一次 release。
5. Delay Queue 中的任务由 Router 持有；超时、关闭、队列满或最终拒绝时必须释放。
6. Pool 接管的任务不得由 Router 在之后再次释放。

## 10. 并发、重入与调用顺序

| API | 并发要求 | 调用顺序 / 约束 |
|---|---|---|
| pm_registry_create | 不要求并发 | 每个 Registry 首先调用 |
| register_app | 启动期串行调用 | create 之后、seal 之前 |
| pm_registry_seal | 启动期串行调用 | 所有 App 注册完成后 |
| event_trigger_notify | 必须支持多线程并发 | seal 之后、destroy 开始之前 |
| pm_registry_destroy | 与其他控制面 API 不并发 | 停止通知源后调用；等待在途通知退出 |
| Pool register / unregister | 启动期由本模块串行调用 | 仅注册事务期间 |
| Pool try_enqueue | 必须支持多线程并发 | 运行期调用；容量判断与入队原子 |
| DataRef validate / retain / release | 必须支持并发调用 | 按 DataRef 生命周期契约执行 |

**重入约束：**

- DataRef Adapter 回调不得反向调用 Registry 生命周期 API。
- Pool Adapter 的 register / unregister 回调不得重入 register_app。
- try_enqueue 不得在返回前同步执行 Handler；它只负责准入和入队，执行由 Pool 消费侧完成。
- event_trigger_notify 不得持有 Registry 全局写锁等待 Handler 完成。

## 11. 上下游责任边界与联调验收

### 11.1 本模块负责

- 导出 A 组五个 API。
- 解析 app.json，构建只读 Registry 索引。
- 实现 DIRECT 独立依赖路径和 Immediate / ByName Trigger 匹配。
- 构建最小 TaskInvocation，管理 Inline 复制和 DataRef retain / release。
- 调用 Pool try_enqueue，处理容量不足、Delay Queue、失败和资源释放。

### 11.2 Data Bucket SDK 负责

- 成功 Commit 后调用 event_trigger_notify。
- 提供 DataRef validate / retain / release。
- 保证 DataRef 绑定不可变 Commit 版本。
- 保证 Inline 缓冲区在 notify 返回前有效。
- 从 TaskContext 注入 source_function。
- 提供 Object API 并在 Commit 成功后产生通知。

### 11.3 Task Coroutine Pool 负责

- 提供 register_function / unregister_function / try_enqueue 三个回调。
- 保证静态配置复制、冲突检测和注册回滚语义。
- 保证 try_enqueue 的容量检查和入队原子。
- ACCEPTED 时复制任务描述符及 Inline，并接管 DataRef。
- 自行负责消费者发现、协程唤醒、SO 加载、TaskContext 构建、Handler 执行和资源释放。
