## 第 1 章 功能需求列表概述

### 1.1 业务背景与本期链路

业务流程如下：

| 步骤 | 行为 | 责任方 |
|---|---|---|
| ① | SMC Actor 处理外部消息，调用 SDK 写入数据 | 上游业务团队 |
| ② | SDK 调用 Data Bucket SDK，将 Object 写入共享内存或其数据载体 | 上游 Data SDK |
| ③ | 数据 Commit 成功后，上游调用 event_trigger_notify，传入事件信息、来源函数和数据地址 | 上游 SDK / 本模块 |
| ④ | 本模块判断 DIRECT 或 Bucket Trigger 路径，匹配规则并构建目标函数参数 | 本模块 |
| ⑤ | Task Router 检查目标 Function 的 CPU / Memory 资源，资源满足后调用下游 try_enqueue | 本模块 / 下游 Pool |
| ⑥ | Task Coroutine Pool 消费队列、唤醒协程、加载 SO 并执行目标函数 | 下游 Pool |

本模块负责③④⑤，不负责 SMC Actor、Object 存储、共享内存底层、Task Coroutine Pool 的协程实现或业务函数执行。

### 1.3 研发边界与团队职责

**本模块负责：**

1. App Registry：内部加载 app.json，构建 Function、Bucket、DIRECT Dependency 和 Trigger 索引。
2. DIRECT Dependency：按来源 func_name 查找目标 func_name，独立生成任务。
3. Event Trigger：按 Bucket 找到规则，匹配 Immediate / ByName。
4. Task Builder：将事件中的 key、data_addr、data_size 组装为 arguments[]。
5. Task Router：先检查 CPU / Memory 资源，再调用原子 try_enqueue；管理本地 Delay Queue。
6. 资源不足时不调用 Pool，预留资源不足上报分支。

**上游 Data Bucket SDK 负责：**

- Object 创建、容量校验、写入和 Commit。
- 数据地址和长度的生成与传递。
- 调用 event_trigger_notify。
- 提供 Session 生命周期管理；Session 结束且所有相关任务完成或终止后，回收数据。
- Function 输出对象时，从当前 TaskContext 注入 source_func_name；外部 SMC Actor 写入时可不提供。

**下游 Task Coroutine Pool 负责：**

- 接收启动阶段的静态 Function 配置。
- 运行期通过 try_enqueue 原子准入并入队。
- 复制并持有 TaskInvocation 所需的字符串和参数描述符，不复制、不释放 data_addr 指向的数据内容。
- 队列消费、协程创建 / 等待 / 唤醒。
- 根据 so_name 加载 SO，根据 func_name 定位函数符号。
- 构造 TaskContext 并执行目标函数。

### 1.4 冻结的基础约束

| 约束 | 设计要求 |
|---|---|
| 调度实例 | 单进程、单个实例；内部唯一 Registry |
| 配置 | 模块内部加载 app.json；不向上游客户暴露配置注册生命周期 API |
| App | app_name 用于配置作用域；Bucket 在当前调度实例全部 App 范围内全局唯一 |
| Function | so_name 与 func_name 分离；func_name 在当前 App 内唯一 |
| SO | so_name 是安全文件名；一个 SO 可以导出多个函数 |
| 函数入口 | 不固定为 handler；使用 dlsym(handle, func_name) |
| DIRECT | 独立依赖路径；source_func_name → target func_name[] |
| Trigger | 仅 Immediate、ByName |
| 多 Trigger | 一个 Bucket 可以关联多个 Trigger |
| DataReadyEvent | 仅 bucket、key、session_id |
| 通知参数 | source_func_name、data_addr、data_size 独立传入 |
| 数据 | 统一地址传递；不区分大小数据包 |
| Task 参数 | key 必须；arguments[] 当前 argc=1 |
| 输入模式 | 0=Value，1=Key+Value，2=Key Only；DIRECT 固定 Value |
| 数据生命周期 | Session 结束且相关任务全部完成或终止后，上游回收 |
| DataRef | 不存在；不提供 validate / retain / release |
| Pool Adapter | 仅 try_enqueue |
| 资源准入 | Task Router 在 try_enqueue 前检查 CPU / Memory |
| 协程 | Pool 内部管理消费和唤醒；本模块不调用 wake_one |
| 延时 | app.json 中进程级全局 Delay Queue 配置 |
| 超时 | 不定义 Function 执行超时，不实现 Rerun |

### 1.5 本期明确不实现

- Rerun、Function 执行超时、resource.timeout_ms。
- wake_one 或由本模块发起的协程唤醒。
- BySet、ByBatchSize、ByTime、DynamicGroup、Redundant 等其他 Trigger Primitive。
- Node / Process Scheduler、Warm / Cold Executor、跨进程和跨节点任务分发。
- Data Bucket 底层存储、共享内存池、数据地址分配和底层搬运。
- DataRef、引用计数和 Scheduler 主动调用 Data SDK 查询数据。
- Task Coroutine Pool、TaskQueue、协程和 SO 执行实现。
- 动态 Trigger 更新、持久化事件日志、Exactly-once 和事件去重。
- 本期资源不足的具体上报实现；只定义分支和 TODO。

### 1.6 术语

| 术语 | 含义 |
|---|---|
| App | 由 app.json 描述的一组 Function、Bucket、Dependency 和 Trigger 配置 |
| Registry | 模块内部唯一的只读运行时配置与索引 |
| so_name | 动态库文件名，用于定位并加载 .so |
| func_name | .so 内函数符号名称，用于 dlsym 和逻辑 Function 标识 |
| source_func_name | 本次数据的生产函数名称，用于 DIRECT 匹配 |
| DIRECT Dependency | 来源 func_name 到目标 func_name 的独立依赖关系 |
| Bucket | 全局唯一的数据逻辑命名空间 |
| DataReadyEvent | 对一次成功 Commit 的最小通知，包含 bucket、key、session_id |
| TaskArgument | 一项函数输入，包含 key、data_addr、data_size |
| TaskInvocation | 提交给 Task Coroutine Pool 的一次函数调用描述 |
| Delay Queue | 本地 Pool 无容量时暂存待提交任务的延时队列 |

## 第 2 章 Pheromone 源码参考与裁剪

V0.6 复用 Pheromone 的以下语义：

- DIRECT 是独立依赖路径，不伪装成 Bucket Trigger。
- DIRECT 根据 source function 查找 target functions。
- Bucket 对应 Trigger 列表；Immediate / ByName 按规则匹配。
- Scheduler / Task Builder 将命中的数据对象转换为函数参数列表。
- Task Invocation 将函数标识和参数一起交给 Executor / Pool。
- Executor 根据函数标识定位执行入口，并在调用前准备函数参数。

本项目针对单进程单节点范围进行裁剪：

- 不实现 Coordinator、节点级调度、跨节点数据位置同步和远程数据传输。
- 不复制 Pheromone 的 INLINE / SHARED_MEMORY 双载体与 arg_flag 数据定位方式；本项目统一传递 data_addr + data_size。
- 不复制 DataRef 生命周期接口；上游按 Session 生命周期保证数据地址有效。
- Pheromone 以函数名作为逻辑依赖标识；本项目保留这一点，DIRECT 只使用 source_func_name / target func_name。so_name 仅负责物理动态库加载。
- 保留参数列表思想；当前一个事件对应一个 TaskArgument，使用 argc=1。

具体源码映射见 [附录 A](appendix/A-Pheromone源码映射.md)。

## 第 3 章 总体软件架构

### 3.1 核心模块架构

~~~mermaid
flowchart TD
    A["app.json"] --> B["内部 App Registry / JSON Parser"]
    B --> C["Function Index：func_name -> so_name + runtime config"]
    B --> D["Global Bucket Index"]
    B --> E["DIRECT Index：source_func_name -> target func_name[]"]
    D --> F["Bucket -> Trigger[]"]
    G["event_trigger_notify"] --> H["Event Dispatcher"]
    H --> I{"source_func_name 有 DIRECT 目标？"}
    E --> I
    I -->|是| J["DIRECT Dependency"]
    I -->|否| K["Event Trigger：Immediate / ByName"]
    F --> K
    J --> L["Task Builder：arguments[]"]
    K --> L
    L --> M["Task Router：CPU / Memory 预检查"]
    M --> N["try_enqueue"]
    N --> O["Task Coroutine Pool"]
    M --> P["全局 Delay Queue"]
    P --> M
~~~

### 3.2 关键控制流与数据流

**启动控制流：**

1. 模块内部加载 app.json。
2. JSON Parser 校验 App、Function、Bucket、DIRECT、Trigger 和资源配置。
3. 建立全局 Bucket 索引、App 内 Function 索引、DIRECT 索引和 Trigger 索引。
4. 将 Function 静态配置按 so_name + func_name 交付给 Pool 的启动期注册机制。
5. 所有配置成功后发布只读 Registry；初始化失败则不接收运行期事件。

**运行时数据流：**

1. Data SDK 完成 Object Commit 后调用 event_trigger_notify。
2. 本模块根据 Bucket 全局索引定位所属 App。
3. source_func_name 有 DIRECT 目标时，生成 DIRECT Task；本次事件跳过 Bucket Trigger。
4. source_func_name 为空或没有 DIRECT 目标时，按 Bucket 获取 Trigger[] 并逐条匹配。
5. Task Builder 为每个命中目标构建独立 TaskInvocation.arguments[]。
6. Task Router 查询 Function 资源配置并检查当前 CPU / Memory。
7. 资源不足时不调用 try_enqueue，进入资源不足 TODO 分支；资源满足时调用原子 try_enqueue。
8. Pool 自行消费队列并管理协程；Pool 根据 so_name / func_name 定位并执行函数。

### 3.3 架构原则

- **配置与事件分离：** app.json 描述静态依赖和触发规则；事件只描述一次数据提交及其数据视图。
- **Bucket 全局寻址：** Bucket → App → Trigger[]，事件不携带 app_name。
- **Function 双标识：** so_name 负责加载动态库，func_name 负责函数符号定位和逻辑依赖匹配。
- **DIRECT 与 Trigger 分离：** DIRECT 是依赖路径；Immediate / ByName 是 Bucket Trigger Primitive。
- **参数与路由分离：** Task Builder 构建 arguments[]；Task Router 只负责资源准入和提交。
- **地址借用：** 调度模块和 Pool 不拥有数据内存；Session 生命周期保证地址有效。
- **本地边界明确：** Task Router 不创建或唤醒协程，不实现远程分发。
- **资源准入前置：** CPU / Memory 预检查与 Pool 队列容量检查分离。
- **失败可解释：** 参数非法、内部异常、资源不足和队列无容量分别处理，不混为一个错误状态。
