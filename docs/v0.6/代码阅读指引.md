# V0.6 代码阅读指引

第一次阅读时，建议跟踪一条数据通知从应用配置、规则匹配到任务入队的过程。先读下面的 1–4 节，再按需要深入 Linux 资源采集和测试。上游 SDK 管理数据和会话，触发引擎匹配规则并检查资源，下游任务池接收并执行任务。 [总体设计第 3 章](01-总体设计.md)

## 1. 从两个公共入口开始

先看 `TriggerInit` 和 `EventTriggerNotify`。前者在启动时注册应用，后者在 SDK 成功提交数据后接收通知。接着看 `DataReadyEvent`、`TaskInvocation` 和 `TaskPool.TryEnqueue`，确认通知携带哪些字段，以及任务池最终接收什么。最后看 `wiring.Install` 和 `engine.New`，找到任务池、资源采集器和时钟的装配位置。 [公共 API](../../api/api.go) · [公共类型](../../internal/contract/types.go) · [运行时装配](../../internal/wiring/wiring.go) · [接口设计第 10–11 章](03-接口与协作设计.md)

## 2. 跟踪应用配置如何注册

打开端到端测试的 `app.json`，先找 `functions`、`buckets`、`dependencies` 和 `triggers`。再沿 `Runtime.Init → config.Parse → Runtime.publish` 读代码。JSON 字段和引用校验先在临时配置中完成，跨应用冲突检查全部通过后才更新运行时索引。重点看数据桶名称如何跨应用保持唯一，以及为什么所有应用都要在首条有效通知之前注册。 [测试配置](../../tests/mocke2e/testdata/app.json) · [配置解析](../../internal/config/config.go) · [JSON 校验](../../internal/config/json.go) · [运行时初始化](../../internal/engine/engine.go) · [设计第 5 章](02-核心模块详细设计.md)

## 3. 跟踪一条通知如何生成任务

在 `Runtime.Notify` 里，先看 `beginNotify` 如何校验数据桶、来源函数和数据参数，再看直接依赖与数据桶规则的选择顺序。用同一份测试配置跟踪两条通知：

1. 向 `input` 发送数据。它匹配 `IMMEDIATE` 规则，生成函数 `A` 的任务。
2. `A` 提交 `output` 数据时，来源函数名命中 `A → B` 的 `DIRECT` 依赖，因此生成 `B` 的任务并跳过 `output` 上触发 `C` 的规则。也可以用 `named` 数据桶对照 `BY_NAME`，它只匹配键 `ready`。

随后检查任务的 `Function`、`InputMode`、`SessionID` 和单项 `Args`。每个命中项有独立的任务描述，`DataAddr` 指向的数据由上游 SDK 保持有效，直至相关任务结束。 [事件处理](../../internal/engine/engine.go) · [端到端用例中的 pipeline 与 byName](../../tests/mocke2e/scenarios_test.go) · [设计第 6–8 章](02-核心模块详细设计.md)

## 4. 跟踪入队、重试和关闭

按 `router.submit → attempt → TaskPool.TryEnqueue` 阅读首次提交路径，再按 `deferTask → schedule → run → attempt` 阅读重试路径。资源不足、采集失败或任务池暂时无容量时，由延时配置决定是否重试。队列中的任务保留首次延时确定的期限，每次重试重新检查资源。随后看 `Runtime.Close` 和 `router.close`，确认关闭如何阻止新通知、取消待处理任务并等待在途调用。 [任务路由和重试](../../internal/engine/router.go) · [运行时关闭](../../internal/engine/engine.go) · [工程设计第 14 章](04-工程实现设计.md)

## 5. 深入资源采集和测试

阅读资源代码时，先看 `Evaluate` 的输入和判定，再看 `Linux.Read` 如何构造快照。沿 `sampleBase → readBase → groups` 追踪 CPU、内存与 cgroup 限额。采样间隔和共享缓存位于 `sample.go`，GPU、磁盘和网卡的可选采集入口位于 `Linux.Read`。 [资源判定](../../internal/resource/resource.go) · [Linux 采集](../../internal/resource/linux.go) · [CPU 和内存](../../internal/resource/base_linux.go) · [cgroup](../../internal/resource/cgroup_linux.go) · [双采样与缓存](../../internal/resource/sample.go)

| 要验证的问题 | 先读的测试 |
|---|---|
| 配置何时被拒绝，失败是否影响已注册应用 | `TestConfig`、`TestInitialization`、`TestPublication` |
| 直接依赖与数据桶规则如何选择，任务池何时接收 | `TestMockAcceptance` 下的 `pipeline`、`byName` 和 `fanOut` |
| 资源何时恢复，重试何时结束 | `TestMockAcceptance` 下的 `recoverResources`、`expiry` 和 `deadlineDuringProbe` |
