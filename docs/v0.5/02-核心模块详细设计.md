[返回 V0.5 主文档](../V0.5-完整软件设计方案.md) · [公共 C 接口](appendix/C-C接口与Task-ABI.md)

## 第 4 章 Function 与 Task 执行规范

### 4.1 Function 与 Task

Function 是 app.json 中注册的静态 SO 配置；Task 是一次具体执行请求。同一个 Function 可以被多个 Trigger 关联，也可以由同一个 Bucket 的多条规则触发。每次命中规则生成独立 Task，Task ID 与 Event ID 不同。

每个 Task 当前只携带一个输入对象；不实现多输入聚合、跨 Bucket 等待或任务 DAG 汇聚。

### 4.2 SO 名称、部署目录与入口

- `functions[].name` 是完整 SO 文件名，例如 `producer.so`，必须以 `.so` 结尾。
- 每个节点的 SO 固定放在 `/dev/shm` 目录下；下游框架按 `/dev/shm/<so_name>` 自动加载。
- App Registry 只校验安全文件名并把 so_name 写入 FunctionConfig / TaskDescriptor，不执行 dlopen，不查找其他目录。
- 所有 SO 的导出入口固定为 `handler`；JSON 不配置 entry，不支持自定义入口名。
- 同名 SO 不允许运行时原地替换。升级应停止相关执行、替换文件并按团队部署流程重新注册/启动。
- 部署方负责文件权限、可信来源、CPU 架构、动态库依赖和 /dev/shm 的可执行映射策略。若挂载 noexec 导致加载失败，由环境/下游团队处理。

### 4.3 无状态与 APP 使用约束

每个 SO 导出 `int handler(const task_context_t *ctx)`。函数必须无状态、可重入，不得依赖前一次调用留下的可变全局状态，不得依赖固定线程或固定协程。只读常量可以共享；任务状态应放在本次调用栈或通过 Object API 显式读写。

APP 不得直接通过文件 I/O、网络 Socket 或其他旁路方式交换业务数据；只能使用约定的 Object/Data SDK 接口操作对象。该规则属于业务 SO 的开发与运行契约，本模块不实现系统调用沙箱；通过代码审查、构建检查及集成测试落实。

handler 不得长期保存 ctx、value 映射指针或 SDK 临时对象；不得自行释放 Task Pool 持有的 DataRef。handler 返回后，所有借用视图失效。

### 4.4 输入与资源元信息

TaskContext 至少提供 app_name、task_id、event_id、session_id、function_name、input_mode、key/value 视图及 Object API。value 由下游在 handler 执行期间准备：Inline Payload 使用队列内副本；Shared-Memory Payload 由下游通过 Data SDK 映射 DataRef。handler 返回后解除映射并释放对应引用。

resource / execution 字段在 V0.5 作为函数静态元数据传递给下游，不代表本模块实现 CPU/GPU 配额、线程绑定、优先级队列、超时强杀或复用策略。

## 第 5 章 单一 app.json 配置协议

### 5.1 为什么只保留一个 JSON

V0.5 只使用一份 app.json。此前将应用拓扑与单函数补充元数据拆成 app.json / function.json，会产生重复注册、覆盖优先级和配置不一致问题；而当前 Demo 的函数数量、固定 handler、固定 SO 目录和 Trigger 规则均可在应用级配置中完整表达，没有必要拆成两个文件。

上游将完整 JSON 内容传给 `register_app(config_json)`。App Registry 在一次注册事务中解析、校验并建立全部内部索引。不存在独立 function.json，也不需要调用者再传 function_paths。

### 5.2 顶层结构

~~~json
{
  "app_name": "smc_demo",
  "description": "单进程数据驱动示例",
  "version": "1.0.0",
  "functions": [],
  "buckets": [],
  "triggers": []
}
~~~

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| app_name | string | 是 | App Registry 全局唯一注册 KEY，不代表业务实体 |
| description | string | 否 | 应用说明 |
| version | string | 是 | 应用配置版本 |
| functions | array | 是 | 至少一个函数，函数名在 App 内唯一 |
| buckets | array(string) | 是 | 本 App 使用的逻辑 Bucket 名称，名称唯一 |
| triggers | array(object) | 是 | Trigger 清单，可为空 |

V0.5 不包含 dependencies 字段：本 Demo 不实现 DIRECT Dependency，函数间数据驱动关系完全由 Bucket + Trigger 描述。也不包含 function.json、function_paths、node_schedule、process_schedule 或独立注册 Function/Trigger 的字段。

### 5.3 Function 配置

每个 functions 元素：

| 字段 | 类型 | 约束 |
|---|---|---|
| name | string | 必填；安全 SO 文件名，含 .so |
| description | string | 可选 |
| version | string | 可选；缺省继承 App version |
| resource | object | 必填；至少 cpu_cores、memory_mb、timeout_ms |
| resource.cpu_cores | number | 有限且大于 0 |
| resource.memory_mb | integer | 大于 0，单位 MB |
| resource.timeout_ms | integer | 大于 0，单位 ms |
| resource.gpu.required | boolean | 可选，默认 false |
| resource.gpu.device_count / memory_mb | integer | 可选，默认 0；required=false 时必须为 0 |
| resource.disk_mb / network_mbps | integer | 可选，默认 0 |
| execution.type | string | 可选，仅作为元数据 |
| execution.priority | integer | 可选，默认 0 |
| execution.affinity | array(integer) | 可选，默认空数组；元素非负且不重复 |
| execution.max_concurrency | integer | 可选，默认 0 表示未指定；显式值必须大于 0 |
| execution.reuse | boolean | 可选，默认 false；仅元数据 |

不允许配置 entry、so_path、任意目录、函数级 dependencies 或函数级 triggers。入口固定 handler，路径由框架固定解析为 /dev/shm/<name>。

### 5.4 Bucket 与 Trigger 配置

Bucket 是逻辑命名空间声明，不由 App Registry 创建物理共享内存。每个 Trigger 必须引用已声明 Bucket 和已注册 Function。

| 字段 | 类型 | 约束 |
|---|---|---|
| bucket | string | 必填；必须在 buckets 中声明 |
| trigger_name | string | 必填；App 内唯一 |
| primitive_type | string | 仅 IMMEDIATE / BY_NAME |
| primitive.function | string | 必填；目标函数名必须存在 |
| primitive.key_name | string | BY_NAME 必填；IMMEDIATE 禁止填写 |
| trigger_option | integer | 0 / 1 / 2；缺省 0 |

同一 Bucket 可以在 triggers 中出现多次，表示关联多个独立 Trigger。规则按 app.json 中的先后顺序匹配；同一事件命中多条规则，就生成多条 Task，不按目标函数去重。

字符串比较区分大小写。ByName 对原始 Key 做完全相等比较，不支持前缀、正则、模糊匹配或 Session 聚合。

### 5.5 Trigger Option / 输入模式

JSON 保留数值字段 trigger_option；App Registry 将其转换为内部 input_mode：

| trigger_option | 内部模式 | handler 可见输入 |
|---:|---|---|
| 0 | INPUT_VALUE | 仅 value 与长度 |
| 1 | INPUT_KEY_VALUE | key + value 与长度 |
| 2 | INPUT_KEY_ONLY | 仅 key，不提供 value |

TaskDescriptor 可保留 Bucket、Key、Session、DataRef 和数据长度用于定位、诊断及生命周期；INPUT_KEY_ONLY 不复制 Inline Payload，也不 retain Shared-Memory DataRef。输入模式不是访问控制或安全隔离机制。

### 5.6 配置校验与错误处理

- 拒绝非法 JSON、重复字段、未知字段、错误类型、尾随非空白内容和超长输入；不得静默忽略未知配置。
- app_name、函数名、Bucket 名、Trigger 名和 Key 均校验 NUL、长度和字符约束；SO 名仅允许安全文件名，不允许路径分隔符、路径穿越或绝对路径。
- 函数名在同一 App 内唯一；Bucket 名唯一；Trigger 名在同一 App 内唯一。
- 每个 Trigger 的 Bucket 必须已声明，目标 Function 必须已注册。
- IMMEDIATE 不允许 key_name；BY_NAME 必须有非空 key_name。
- trigger_option 只允许 0、1、2。
- 资源数值必须有限、范围正确；整数型字段拒绝小数和溢出。
- 明确拒绝 DIRECT、未知 Primitive、function.json 相关字段及调度策略字段。
- 注册失败不得发布部分 App；释放所有临时配置和索引，并返回 JSON 路径级诊断。

### 5.7 示例和版本策略

完整 app.json 见 [附录 B](appendix/B-JSON配置协议示例.md) 和 [examples/app.json](examples/app.json)。配置在注册时复制并规范化；调用者在 register_app 返回后可释放原始 JSON 缓冲区。V0.5 仅支持注册阶段装载，不支持运行时动态修改单条 Trigger；重新配置采用停止通知、排空/清理旧任务引用、销毁并重新注册的流程。

## 第 6 章 App Registry 模块详细设计

### 6.1 职责

App Registry 是本模块唯一的配置注册与管理模块，负责：

1. 接收上游 app.json 内容。
2. 在 register_app 内部解析 JSON 并验证结构。
3. 校验函数、Bucket、Trigger 的跨引用关系。
4. 构建内部 Function Index 和 Trigger Index。
5. 以 app_name 为全局唯一 KEY 原子发布 AppRecord。
6. 为 Event Trigger / Task Builder 提供只读查询。

JSON Parser / Config Validation 是 App Registry 的内部实现步骤，不是独立对上游开放的 Config Loader 服务。App Registry 不加载 SO、不创建 Bucket、不启动协程。

### 6.2 注册事务

~~~mermaid
flowchart TD
    A["register_app(config_json)"] --> B["解析单份 JSON"]
    B --> C["校验 App / Function / Bucket / Trigger"]
    C --> D["构建 Function Index"]
    D --> E["构建 Bucket → Trigger 列表"]
    E --> F{"全部成功？"}
    F -->|是| G["以 app_name 原子发布"]
    F -->|否| H["释放临时对象并返回错误"]
~~~

所有对象先构建在临时注册记录中；只有完整成功才写入 App Registry。app_name 已存在时返回 DUPLICATE_APP，不覆盖已注册配置。一个进程可以注册多个不同 app_name 的 App。

### 6.3 内部数据结构

- AppRecord：app_name、description、version、函数数组、Bucket 清单、Trigger 数组及索引。
- Function Index：so_name → FunctionConfig；FunctionConfig 含 version、resource、execution，entry 固定 handler。
- Trigger Index：bucket → 按配置顺序排列的 TriggerConfig 列表。
- TriggerConfig：trigger_name、primitive_type、target_function_index、key_name、input_mode。
- 不存在 Dependency Index / Dependency Registry。

Function 名称仅在 App 内唯一；不同 App 可包含同名 SO，但它们的 app_name 和配置记录互相隔离。

### 6.4 注册与查询生命周期

注册阶段可使用互斥锁保护 AppRecord 发布；进入运行态后配置只读，Event Trigger 并发查询不需要对每次匹配持全局写锁。所有 App 注册完成后调用 app_registry_seal（或由宿主等价地冻结注册阶段），之后禁止注册/替换。notify 期间不得释放 AppRecord；destroy 前必须停止新通知并等待在途调用结束。

### 6.5 内部查询接口（设计）

~~~c
const app_record_t *app_registry_find_app(
    const app_registry_t *registry, const char *app_name);

const function_config_t *app_function_find(
    const app_record_t *app, const char *so_name);

size_t app_trigger_list_by_bucket(
    const app_record_t *app, const char *bucket,
    const trigger_config_t **out_rules);
~~~

以上是私有内部接口示意，不作为上游注册 API。普通未命中、未知 App、未知 Bucket 和内部索引损坏必须区分。

## 第 7 章 内部 Function / Trigger 索引设计

### 7.1 为什么不是三个独立 Registry

上游提交的是一份完整 App 配置，函数与 Trigger 在同一注册事务内相互引用。因此 App Registry 统一管理 AppRecord，并在内部建立 Function Index 和 Trigger Index。把 Function Registry、Trigger Registry 单独开放，会产生多次注册顺序、跨接口部分成功和拓扑不一致问题；本期没有这种必要。

### 7.2 Function Index

按 so_name 查找 FunctionConfig。函数项包含名称、描述、版本、资源和执行元数据。so_name 是文件名，不是完整路径；路径由下游框架固定解析。entry_name 固定为 handler，不从 JSON 读取。

### 7.3 Trigger Index

以 Bucket 为 Key，Value 是有序 TriggerConfig 列表。一个 Bucket 可没有 Trigger，也可关联多条 Trigger。列表保留 app.json 声明顺序，不做目标函数去重。Immediate 和 ByName 都在注册阶段将目标函数名解析为函数索引，避免热路径重复字符串查找。

### 7.4 索引构建复杂度与并发

P0 可以采用排序数组或哈希表；优先保证注册时校验和热路径查询正确。Bucket 查询后遍历该 Bucket 的 K 条 Trigger，匹配复杂度 O(K)。注册后索引不可变，支持多线程/协程并发只读。索引构建失败时整个 App 注册失败。

## 第 8 章 Event Trigger 模块详细设计

### 8.1 职责与主流程

Event Trigger 接收 SDK 的 DataReadyEvent，校验事件基本信息及 Payload 描述，按 app_name 找 AppRecord，按 Bucket 找 Trigger 列表，逐条执行 Primitive 匹配。每条命中规则产生一条 TaskAction，交给 Task Builder。Event Trigger 不读写 Object，不扫描共享内存，不判断 1KB 阈值，不搬运数据，不执行 handler。

### 8.2 DataReadyEvent 语义

事件必须来自一次成功的 Object Commit。至少包含 event_id、app_name、bucket、key、session_id、payload_type、data_size，以及与载体对应的 inline_data 或 data_ref。source_function 可选，仅用于来源追踪和上下文传递，不参与路由；不再存在 tgt_function。

外部 Actor 写入时 source_function 可为空；handler 通过 Object API 写入新对象时，SDK 可从 TaskContext 注入 source_function。没有显式 DataReadyEvent 的覆盖写不触发 Trigger。

### 8.3 事件校验

- event_id 非零，app_name 已注册，Bucket 已在 App 中声明。
- key、session_id 按接口约定校验；source_function 若提供，必须是本 App 已注册 Function。
- payload_type 必须为 INLINE 或 SHARED_MEMORY。
- INLINE：inline_size 必须等于 data_size；数据长度不得超过接口声明的 Inline 容量；非零长度时 inline_data 不得为空。
- SHARED_MEMORY：必须携带有效 DataRef；不得同时携带 Inline Payload。
- 对需要 value 的匹配规则，调用 Data SDK validate 检查引用和长度；KEY_ONLY 不要求保留或映射 Payload。
- 事件中的 data_size 是真实字节数，不由 Scheduler 重新推导。

### 8.4 匹配流程

~~~mermaid
flowchart TD
    A["DataReadyEvent"] --> B["查 app_name"]
    B --> C["校验 Bucket / Payload"]
    C --> D["查询 Bucket Trigger 列表"]
    D --> E{"逐条匹配"}
    E -->|IMMEDIATE| M["命中"]
    E -->|BY_NAME 且 key 相等| M
    E -->|BY_NAME 且 key 不等| N["不命中"]
    M --> F["TaskAction"]
    N --> E
    F --> G["Task Builder → Task Router"]
~~~

Immediate 对每个有效数据就绪事件匹配；ByName 只做 key 与 key_name 的完全相等比较。两者均无状态，不维护历史事件、计数或 Session 聚合。

### 8.5 同 Bucket 多 Trigger

Trigger Index 返回该 Bucket 的全部规则。Event Trigger 按顺序逐条匹配：

- 未命中规则不生成 Task。
- 每条命中规则独立生成 Task，即使多个 Trigger 指向同一个 Function，也不合并。
- 一条规则构建/投递失败不撤销其他规则已经成功入队的 Task。
- 结果按配置顺序返回，便于上游定位哪条规则被接受或拒绝。

### 8.6 覆盖写与事件通知边界

同一 Bucket/Key 再次调用 send_object 可能覆盖该 Key 当前指向的数据，但若 SDK 没有发送新的 DataReadyEvent，Event Trigger 不会重新匹配，也不会推断发生了更新。Scheduler 不轮询、不比较内容、不合成变更通知。

每个已通知事件的 DataRef 必须标识本次 Commit 的不可变数据版本。若底层 Bucket/Key 存储槽可被覆盖，Data SDK 必须在旧引用仍被 retain 时通过版本化对象、Copy-on-Write 或等价机制保证旧 DataRef 继续指向旧数据；不能让已排队 Task 在执行时重新解析 Key 并意外读到新值。该机制属于 Data SDK，不由本模块实现。

### 8.7 核心匹配伪代码

~~~c
static bool primitive_match(const trigger_config_t *rule,
                            const data_ready_event_t *event)
{
    switch (rule->primitive_type) {
    case TRIGGER_IMMEDIATE:
        return true;
    case TRIGGER_BY_NAME:
        return strcmp(rule->key_name, event->key) == 0;
    default:
        return false; /* 注册阶段已拒绝未知类型 */
    }
}
~~~

### 8.8 结果容量、部分失败与重复通知

先统计匹配数量，再检查调用者结果缓冲区容量；容量不足时返回所需数量且不发生任何 retain/入队副作用。容量足够后按规则顺序逐项构建和投递。P0 不自动去重、不自动重试；相同 event_id 再次通知可能产生重复 Task。上游不得因部分成功而盲目重放整个事件。

## 第 9 章 Task Builder 详细设计

### 9.1 输入与输出

输入为 TaskAction、AppRecord 中目标 FunctionConfig、DataReadyEvent 和新 Task ID；输出为完整 TaskDescriptor。描述符必须拥有全部字符串和小数据副本，不得保存 Event 指针、临时 JSON 指针或 Registry 指针。

### 9.2 两种 Payload 的组装规则

| 输入情况 | Task Builder 行为 | TaskDescriptor |
|---|---|---|
| INPUT_VALUE / INPUT_KEY_VALUE + INLINE | 校验长度并复制实际字节 | 内嵌 Inline Payload 副本 |
| INPUT_VALUE / INPUT_KEY_VALUE + SHARED_MEMORY | validate 后 retain 一份 | 仅保存原 DataRef 与长度，不复制数据 |
| INPUT_KEY_ONLY | 不复制 Payload、不 retain DataRef | 仅保存 Key / Bucket / Session 等元信息 |

Task Builder 不比较 data_size 与 1KB，不把 Inline 转换为 Shared Memory，也不反向映射大对象。

### 9.3 多 Trigger 的独立所有权

同一事件命中 N 条 Trigger 时，Task Builder 生成 N 个独立 TaskDescriptor：

- Inline：每个 Task 获得自己的字节副本；SDK 的事件缓冲区在 notify 返回后即可释放。
- Shared Memory：每个需要 value 的 Task 单独 retain 一次；每份引用分别由 Router 或 Pool 接管/释放。
- KEY_ONLY：不持有 Payload，不产生数据引用计数。

不能让多个 Task 共享一个会随 notify 返回而失效的 Inline 指针。

### 9.4 构建顺序

1. 校验目标 FunctionConfig 和输入模式。
2. 初始化 TaskDescriptor，复制 app/function/trigger/event/session 等身份字段。
3. 设置 so_name、固定 entry_name=handler、resource 和 execution。
4. 根据 input_mode / payload_type 复制 Inline 或 retain DataRef。
5. 构建成功后交给 Task Router；任何失败均清理已取得的资源。

Task ID 使用进程内原子递增非零 uint64_t。重启后不保证全局唯一，日志需结合进程实例 ID。

## 第 10 章 Task Router 详细设计

### 10.1 职责与路由策略

Task Router 只向当前进程的 Task Coroutine Pool 提交 Task。它不实现任务队列、不管理协程、不加载 SO、不执行 handler，也不选择节点或其他进程。

### 10.2 入队与唤醒接口

建议下游提供两个语义清晰的操作：

1. `try_enqueue(task)`：原子检查容量并复制/保存 TaskDescriptor。成功表示已入队并接管该 Task 对应的 DataRef；队列满或其他拒绝表示未入队、未接管引用。
2. `wake_one()`：仅在 try_enqueue 成功后调用，尝试唤醒一个等待协程。没有等待者不是入队失败，Task 仍留在队列中；下游负责避免入队与睡眠竞态导致丢唤醒。

若下游最终只提供一个等价的 submit API，由 Adapter 封装成同样的所有权与结果语义；本模块不自行实现队列同步。

### 10.3 路由流程

~~~mermaid
flowchart TD
    A["TaskDescriptor 已构建"] --> B["try_enqueue(task)"]
    B -->|成功| C["Pool 接管描述符 / DataRef"]
    C --> D["wake_one()"]
    D --> E["返回 LOCAL_ENQUEUED"]
    B -->|QUEUE_FULL| F["记录 PROCESS_DISPATCH_REQUIRED"]
    F --> G["Router 释放本 Task DataRef"]
    G --> H["返回未接收"]
    B -->|其他拒绝| I["Router 释放本 Task DataRef"]
    I --> J["返回具体失败"]
~~~

### 10.4 队列满语义

队列满时：

- 不阻塞等待队列腾出空间。
- 不创建本地二级等待队列。
- 不执行真实进程间分发。
- 输出 `PROCESS_DISPATCH_REQUIRED` 日志，标记 `dispatched=false`。
- 返回未接收，并释放本 Task 已 retain 的 DataRef。
- 其他拒绝（Pool 未就绪、资源不足、非法 Task、内部错误）不误报为进程间分发需求。

### 10.5 唤醒失败与所有权

try_enqueue 成功即代表任务已被接收。wake_one 返回“没有等待者”时正常结束；若发生其他唤醒异常，记录独立日志/指标，但不能把已入队 Task 报告为未接收，也不能释放 Pool 已接管的 DataRef 或重新提交同一 Task。下游必须保证队列可被后续工作协程继续消费。

### 10.6 资源准入边界

本期“本地资源足够”的最小判断就是下游队列接受 Task。若 Pool 能提供额外资源准入结果，可由 Adapter 透传；本模块不自行采集 CPU/MEM、实现配额或选择执行实例。忙碌协程不等于无资源，只要队列可接收即可入队。
