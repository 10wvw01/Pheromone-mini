# Pheromone-mini V0.6 分功能需求列表

[返回 V0.6 主文档](../V0.6-完整软件设计方案.md)

## 1. 文档目的

本文将 V0.6 冻结设计拆解为可实现、可测试、可验收的功能需求。需求以 Pheromone 的 DIRECT、Bucket Trigger 和函数参数传递机制为基础，适配单进程单调度实例和统一数据地址传递。

## 2. 范围、角色与优先级

### 2.1 角色

- **上游 Data Bucket SDK：** Commit 数据、提供 bucket/key/session_id、source_func_name、data_addr、data_size，调用通知 API，并负责 Session 生命周期。
- **本模块：** JSON Parser、App Registry、DIRECT Dependency、Event Trigger、Task Builder、Task Router、Delay Queue。
- **下游 Task Coroutine Pool：** 静态 Function 配置注册、try_enqueue、队列消费、协程调度、SO 加载和函数执行。

### 2.2 本期基础规则

- 单进程、单个调度实例；Registry 为模块内部唯一实例。
- 对上游只暴露 event_trigger_notify。
- DataReadyEvent 仅 bucket、key、session_id。
- source_func_name、data_addr、data_size 作为通知函数独立参数。
- 数据统一通过 data_addr + data_size 传递，不区分大小数据包。
- 不存在 DataRef、INLINE / SHARED_MEMORY、validate / retain / release。
- key 在 TaskArgument 中必须存在。
- so_name 用于 dlopen，func_name 用于 dlsym；func_name 在当前 App 内唯一。
- DIRECT 只按 source_func_name → target func_name 匹配。
- Pool Adapter 运行期只包含 try_enqueue。
- Task Router 在 try_enqueue 前执行 CPU / Memory 资源预检查。
- 资源不足不调用 try_enqueue，进入 TODO 上报分支；Pool NO_CAPACITY 才进入 Delay Queue。
- 不实现 Rerun、resource.timeout_ms、跨进程和跨节点调度。

## 3. App Registry / JSON Parser 需求

### APP-01：内部加载 app.json
- **优先级：** P0
- **行为：** 模块启动时内部加载 app.json，解析、校验并构建唯一 Registry。
- **验收：** 配置加载失败时不开放 event_trigger_notify；不向上游暴露 Registry 创建、注册、封存、销毁 API。

### APP-02：Bucket 全局唯一
- **优先级：** P0
- **行为：** Bucket 在当前 Registry 的全部 App 范围内全局唯一。
- **验收：** event.bucket 能唯一定位所属 App。

### APP-03：Function 双标识
- **优先级：** P0
- **行为：** 每个动态 Function 配置 so_name、func_name、resource、execution。
- **验收：** so_name 与 func_name 独立保存；一个 SO 可配置多个函数。

### APP-04：Function 名称唯一性
- **优先级：** P0
- **行为：** func_name 在当前 App 内全局唯一。
- **验收：** 同一 App 重复 func_name 拒绝；不同 App 同名 func_name 可通过 Bucket 所属 App 隔离。

### APP-05：Function 符号与资源校验
- **优先级：** P0
- **行为：** so_name 是安全文件名；func_name 非空；resource / execution 合法。
- **验收：** Function 入口以 so_name + func_name 组合定位；不要求固定 handler。

### APP-06：Pool 静态 Function 配置
- **优先级：** P0
- **行为：** 启动阶段按 Function 配置交付 so_name、func_name、resource、execution。
- **验收：** Pool 可按 so_name 复用 dlopen Handle，并按 func_name 独立 dlsym；同一组合跨 App 复用时配置一致。

### APP-07：DIRECT / Trigger 引用校验
- **优先级：** P0
- **行为：** dependencies 和 triggers 的函数引用必须指向当前 App 已注册的 func_name。
- **验收：** 未注册函数引用导致初始化失败。

### APP-08：全局索引
- **优先级：** P0
- **行为：** 建立 Bucket Index、App 内 Function Index、DIRECT Index 和 Trigger Index。
- **验收：** 运行期无需重新解析 JSON。

## 4. DIRECT Dependency 需求

### DIR-01：DIRECT 独立路径
- **优先级：** P0
- **行为：** DIRECT 不作为 Trigger Primitive，单独维护依赖索引。
- **验收：** DIRECT 路径与 Immediate / ByName 路径分离。

### DIR-02：来源 Function 识别
- **优先级：** P0
- **输入：** event_trigger_notify 的 source_func_name。
- **行为：** Function 写出对象时，SDK 从 TaskContext 注入当前 func_name；外部 Actor 可传 NULL。
- **验收：** 不需要 source_so_name；source_func_name 只按当前 App 的 func_name 索引。

### DIR-03：目标函数展开
- **优先级：** P0
- **行为：** source_func_name 对应多个 target func_name 时，每个目标生成独立 Task。
- **验收：** 每个 Task 携带对应目标 so_name + func_name。

### DIR-04：DIRECT 优先级
- **优先级：** P0
- **行为：** 存在 DIRECT 目标时走 DIRECT，跳过本次 Bucket Trigger；无 DIRECT 目标或来源为空时进入 Bucket Trigger。
- **验收：** 不同时执行 DIRECT 和 Bucket Trigger。

### DIR-05：DIRECT 输入模式
- **优先级：** P0
- **行为：** DIRECT 使用 PM_INPUT_VALUE。
- **验收：** TaskArgument 包含必填 key、data_addr、data_size。

## 5. Event Trigger 需求

### EVT-01：Commit 成功后通知
- **优先级：** P0
- **行为：** 仅数据 Commit 成功后调用 event_trigger_notify。
- **验收：** 通知携带正确的 bucket、key、session_id、source_func_name、data_addr、data_size。

### EVT-02：最小 DataReadyEvent
- **优先级：** P0
- **字段：** bucket、key、session_id。
- **行为：** source_func_name、data_addr、data_size 不放入结构体，作为独立参数。
- **验收：** DataReadyEvent 不存在 registry、payload_type、DataRef、app_name 等字段。

### EVT-03：Immediate
- **优先级：** P0
- **行为：** Bucket 收到有效事件时命中 Immediate。
- **验收：** 目标 func_name 正确。

### EVT-04：ByName
- **优先级：** P0
- **行为：** Bucket 和 Key 完全匹配时命中。
- **验收：** 非匹配 Key 不触发。

### EVT-05：同 Bucket 多 Trigger
- **优先级：** P0
- **行为：** 每条命中 Trigger 独立生成 Task。
- **验收：** 不漏触发、不合并不同目标。

### EVT-06：DIRECT 与 Trigger 路径隔离
- **优先级：** P0
- **行为：** 按 DIR-04 优先级处理。
- **验收：** DIRECT 命中时不再执行 Bucket Trigger。

### EVT-07：事件参数校验
- **优先级：** P0
- **行为：** bucket、key、session_id 必须非空；data_size 大于 0 时 data_addr 不得为空。
- **验收：** 非法参数返回 PM_ERR_INVALID_ARGUMENT。

## 6. Task Builder 需求

### TSK-01：输入模式映射
- **优先级：** P0
- **行为：** trigger_option 0 / 1 / 2 分别映射 Value / Key+Value / Key Only；DIRECT 固定 Value。
- **验收：** input_mode 不再控制数据载体类型。

### TSK-02：TaskArgument 构建
- **优先级：** P0
- **字段：** key、data_addr、data_size。
- **行为：** 当前一次事件构建一个 TaskArgument，argc=1。
- **验收：** key 必须；data_addr 与 data_size 与通知参数一致。

### TSK-03：TaskInvocation 构建
- **优先级：** P0
- **字段：** session_id、so_name、func_name、input_mode、argc、argv。
- **行为：** 每个目标 Function 独立构建 TaskInvocation。
- **验收：** TaskInvocation 不携带 DataRef、payload_type、固定 handler 或 Trigger 内部元数据。

### TSK-04：异步元数据复制
- **优先级：** P0
- **行为：** 复制 key、session_id 等异步任务需要持有的字符串；不复制 data_addr 指向的数据。
- **验收：** notify 返回后调用方释放临时字符串，不影响排队任务；data_addr 仍由上游保证有效。

### TSK-05：多目标数据地址共享
- **优先级：** P0
- **行为：** 多个命中目标使用同一 data_addr，但拥有独立 TaskInvocation / argv 描述符。
- **验收：** 任一任务完成不导致其他任务数据失效。

## 7. Task Router 需求

### RTE-01：Function 资源查询
- **优先级：** P0
- **行为：** 根据 so_name + func_name 查询 Function 静态资源需求。
- **验收：** 查询不到配置不得提交任务。

### RTE-02：CPU / Memory 可用资源预检查
- **优先级：** P0
- **行为：** 在 try_enqueue 前查询 CPU / Memory 限额和使用量。
- **实现参考：** /proc/self/cgroup 定位 cgroup；读取 cgroup v1 / v2 CPU、Memory 统计；/proc/meminfo 作为宿主机参考或兜底。
- **验收：** 资源满足才进入 try_enqueue。

### RTE-03：资源不足分支
- **优先级：** P0（上报实现 TODO）
- **行为：** CPU 或 Memory 不足时不调用 try_enqueue，记录 RESOURCE_INSUFFICIENT。
- **验收：** 资源不足与 Pool 队列无容量分开统计；本期不进入 Delay Queue。

### RTE-04：原子 try_enqueue
- **优先级：** P0
- **行为：** 单次 try_enqueue 完成 Pool 容量判断和入队。
- **验收：** 不拆成 capacity query + enqueue。

### RTE-05：Pool 返回码
- **优先级：** P0
- **返回：** ACCEPTED、NO_CAPACITY、ERROR。
- **验收：** ACCEPTED 表示 Pool 接收；NO_CAPACITY 表示未接收；ERROR 表示内部错误。

### RTE-06：成功入队所有权
- **优先级：** P0
- **行为：** Pool 接管 TaskInvocation 元数据副本；不接管、不释放 data_addr 指向的数据内存。
- **验收：** Router 释放自己的描述符副本后，Pool 仍可正确执行。

### RTE-07：全局 Delay Queue
- **优先级：** P0
- **行为：** 仅 Pool 返回 NO_CAPACITY 时使用进程级 Delay Queue。
- **验收：** enabled、retry_interval_ms、max_wait_ms 语义一致。

### RTE-08：延时到期
- **优先级：** P0
- **行为：** 达到 max_wait_ms 后记录 TASK_DELAY_EXPIRED 并终止任务。
- **验收：** 释放 Router 自有元数据，不释放 data_addr。

### RTE-09：不调用 wake_one
- **优先级：** P0
- **行为：** 本模块不主动唤醒协程。
- **验收：** Pool 内部保证成功入队任务最终可被消费者发现。

## 8. 上下游协作需求

### API-01：唯一上游通知 API
- **优先级：** P0
- **行为：** 本模块对上游只暴露 event_trigger_notify。
- **验收：** 不要求上游调用 Registry 创建、注册、封存和销毁 API。

### API-02：Pool Adapter 精简
- **优先级：** P0
- **行为：** 运行期 Pool Adapter 只包含 try_enqueue。
- **验收：** 不存在 register_function / unregister_function / wake_one Adapter 回调。

### API-03：SO 与函数符号分离
- **优先级：** P0
- **行为：** so_name 用于 dlopen，func_name 用于 dlsym。
- **验收：** 不固定导出 handler；一个 SO 可导出多个函数。

### API-04：Function ABI
- **优先级：** P0
- **行为：** Function 接收 TaskContext，TaskContext 包含 session_id、input_mode、argc、argv。
- **验收：** 参数地址、Key、长度和输入模式正确。

### API-05：Session 数据生命周期
- **优先级：** P0
- **行为：** 上游保证 Session 结束且所有相关任务完成或终止后才回收数据。
- **验收：** 多目标、Delay Queue、异步执行场景均无悬空数据地址。

## 9. 可观测性与安全

### OBS-01：结构化日志
- **行为：** 日志可包含 trace_seq、app_name、bucket、key、session_id、source_func_name、so_name、func_name、route_path、trigger_name、resource_check、cpu_available、memory_available、pool_result、delay_state 和 elapsed_ms。
- **约束：** 内部诊断字段不得因此进入公共 ABI。

### SAFE-01：SO 名称校验
- **行为：** so_name 只能是安全文件名，不允许路径穿越或任意路径加载。

### SAFE-02：Function 符号校验
- **行为：** func_name 必须属于当前 App 注册的 Function；Pool 必须在静态注册阶段验证 dlsym 结果。

### SAFE-03：数据地址借用
- **行为：** Scheduler / Pool 不得释放 data_addr；上游按 Session 生命周期保证地址有效。

## 10. 本期明确不实现

- DataRef、validate、retain、release 和引用计数。
- INLINE / SHARED_MEMORY 双载体和大小阈值选择。
- Scheduler 主动调用 Data SDK 查询数据。
- Rerun、Function 执行超时、resource.timeout_ms。
- wake_one。
- BySet、ByBatchSize、ByTime、DynamicGroup、Redundant。
- Node / Process Scheduler、Warm / Cold Executor、跨进程和跨节点分发。
- Task Coroutine Pool 内部协程、队列和 SO Loader 实现。
- 资源不足的具体外部上报实现（本期 TODO）。

## 11. 需求完成判定

满足以下条件视为 V0.6 调度与 Trigger 设计需求闭环：

1. app.json 能解析并建立唯一 Registry。
2. Function 通过 so_name + func_name 独立定位。
3. DIRECT 只按 func_name 匹配。
4. Immediate / ByName 匹配正确。
5. event_trigger_notify 只接收最小事件结构和独立数据参数。
6. Task Builder 构建正确的 arguments[]。
7. Task Router 先检查 CPU / Memory，再调用 try_enqueue。
8. Pool Adapter 只包含 try_enqueue。
9. 数据地址在 Session 所有相关任务终态前保持有效。
10. 不存在 DataRef 和双数据载体机制。
