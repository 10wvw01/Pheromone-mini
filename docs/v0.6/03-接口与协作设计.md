# 第三部分：接口与协作设计

[返回 V0.6 主文档](../V0.6-完整软件设计方案.md)

本部分严格分成两部分：第一部分定义本模块向上游 Data Bucket SDK 提供的接口；第二部分定义本模块向下游 Task Coroutine Pool 提交的内容及对下游接口的要求。

## 第一部分：我们向上游提供的接口

## 第 10 章 上游 API 规格

### 10.1 API 总览

| API | 调用方 | 用途 |
|---|---|---|
| pm_registry_create | 框架启动器 | 创建 Registry 并注入 Data SDK / Pool Adapter |
| register_app | 上游配置调用方 | 传入完整 app.json，注册 App、Function、DIRECT、Bucket、Trigger |
| pm_registry_seal | 框架启动器 | 完成启动期注册并切换只读运行态 |
| event_trigger_notify | Data Bucket SDK | 对一次成功 Commit 发送 DataReadyEvent |
| pm_registry_destroy | 框架关闭器 | 停止通知、等待在途调用结束并释放 Registry |

上游业务只需要使用 register_app 和 event_trigger_notify。Function / Trigger 不提供独立注册 API。

### 10.2 register_app

C 原型：

~~~c
pm_status_t register_app(
    pm_registry_t *registry,
    const char *config_json,
    size_t config_size);
~~~

| 项目 | 规格 |
|---|---|
| 功能 | 解析、校验并原子注册一份 app.json |
| 入参 registry | 已创建的 Registry |
| 入参 config_json | UTF-8 JSON 字节缓冲区 |
| 入参 config_size | JSON 字节数 |
| 出参 | pm_status_t |
| 成功 | App、Function、DIRECT、Bucket、Trigger 索引全部发布 |
| 失败 | 不发布部分配置；释放临时对象并返回错误 |

配置只保留 app.json。注册成功后配置只读；本期不提供运行时动态 Trigger 更新。

### 10.3 DataReadyEvent：Data SDK 必须提供的最小字段

C 结构：

~~~c
typedef struct {
    const char *bucket;
    const char *key;
    const char *session_id;

    /* Function handler 写对象时由 SDK 从 TaskContext 注入；
       外部 SMC Actor 写对象时允许为 NULL。 */
    const char *source_function;

    pm_event_payload_type_t payload_type;
    uint64_t data_size;

    union {
        struct {
            const void *data;
            size_t size;
        } inline_payload;

        pm_data_ref_t shared_memory;
    } payload;
} pm_data_ready_event_t;
~~~

| 字段 | 要求 | 用途 |
|---|---|---|
| bucket | 必须 | 全局唯一 Bucket 名称；定位 App 和 Trigger[] |
| key | 必须 | ByName 精确匹配及可选 Key 输入 |
| session_id | 必须 | 区分业务执行上下文 |
| source_function | 条件必需 | Function handler 写对象时提供，用于 DIRECT 索引查找；外部 Actor 可为空 |
| payload_type | 必须 | INLINE / SHARED_MEMORY |
| data_size | 必须 | 本次 Commit 的真实数据长度 |
| inline_payload.data / size | INLINE 必须 | 小数据字节及长度 |
| shared_memory | SHARED_MEMORY 必须 | 指向本次 Commit 版本的 DataRef |

**不需要传递：** app_name、event_id、trigger_name、primitive_type、trigger_option、target_function、tgt_function、active_trigger_names、ips、response_address、request_id。Trigger 配置由 App Registry 内部查询；event_id 由本模块内部生成 trace 序号，不要求 Data SDK 提供。

### 10.4 event_trigger_notify

C 原型：

~~~c
pm_status_t event_trigger_notify(
    pm_registry_t *registry,
    const pm_data_ready_event_t *event,
    pm_notify_result_t *result);
~~~

| 项目 | 规格 |
|---|---|
| 功能 | 接收一次成功 Commit 通知，执行 DIRECT 优先判断或 Bucket Trigger 匹配，构建并路由 Task |
| 入参 registry | 已 seal 的只读 Registry |
| 入参 event | Data SDK 提供的 DataReadyEvent |
| 出参 result | 匹配、入队、延时、拒绝和失败计数 |
| 成功 | 合法事件处理完毕；无匹配也是成功 |
| 失败 | 非法事件、未知 Bucket、DataRef 错误或内部错误 |

结果计数至少包含 direct_matched、trigger_matched、enqueued、delayed、rejected、failed。一个事件可能生成多个 Task；单条规则失败不回滚其他已成功任务。

### 10.5 Data SDK 协作约束

1. 必须在 Object Commit 成功后调用 event_trigger_notify；失败写入不得通知。
2. Bucket 名称在当前 Registry 管理的全部 App 之间全局唯一；SDK 不传 app_name。
3. Function handler 通过 Object API 写对象时，SDK 必须从当前 TaskContext 注入 source_function；外部 SMC Actor 写入可传 NULL。
4. source_function 若非空，必须是该 Bucket 所属 App 中注册的 SO 名称；DIRECT 索引优先查找。
5. SDK 决定约 1KB 的载体选择规则；本模块只按 payload_type 分支，不重新判断阈值。精确边界由双方冻结。
6. INLINE 缓冲区至少在 event_trigger_notify 返回前有效。
7. SHARED_MEMORY DataRef 必须提供 validate / retain / release，且绑定本次 Commit 的不可变数据版本。
8. 同 Bucket/Key 覆盖写但未产生新 Commit 通知时，不触发新 Task；已 retain 的旧 DataRef 不得被覆盖内容污染。

### 10.6 DataRef Adapter

本模块需要 Data SDK 提供：

~~~c
typedef struct {
    void *ctx;
    int (*validate)(
        void *ctx, pm_data_ref_t ref, uint64_t data_size);
    int (*retain)(void *ctx, pm_data_ref_t ref);
    void (*release)(void *ctx, pm_data_ref_t ref);
} pm_data_ref_adapter_t;
~~~

validate 不增加引用；retain 成功增加一份引用；release 释放一份引用。DataRef 是不透明值，不允许把裸进程指针作为跨模块引用。

## 第二部分：我们向下游传递的内容及接口要求

## 第 11 章 Task Coroutine Pool 协作规格

### 11.1 下游实际需要知道什么

Pheromone Local Scheduler → Executor 的执行消息核心是函数标识、Session、参数模式和参数内容；Trigger 规则、Bucket Trigger 名称和上游路由元数据不需要传到 Executor。

V0.6 采用同样的分层原则：

- Function 静态配置：注册阶段每个 SO 一次性提供。
- Task Invocation：每次执行只提供最小动态参数。
- DIRECT / Immediate / ByName 的来源信息留在本模块，不下传。

### 11.2 静态 Function 注册接口

C 原型：

~~~c
pm_pool_register_result_t task_pool_register_function(
    void *pool_ctx,
    const pm_function_runtime_config_t *config);

pm_pool_register_result_t task_pool_unregister_function(
    void *pool_ctx,
    const char *so_name);
~~~

| 入参 | 说明 |
|---|---|
| so_name | /dev/shm 下的 SO 文件名 |
| resource | 函数级资源声明 |
| execution | 函数级执行元数据 |

该接口在 App 注册阶段调用，不随每个 Task 重复传递。resource 不包含执行超时字段。相同 so_name 在不同 App 复用时，必须使用相同 resource / execution；Pool 对相同配置的重复注册应幂等，对冲突配置应拒绝。注册事务回滚时调用 unregister_function；若该 SO 仍被其他已注册 App 引用，不得提前注销。

### 11.3 TaskInvocation：每次任务的最小内容

C 结构：

~~~c
typedef struct {
    const char *so_name;
    const char *session_id;

    pm_input_mode_t input_mode;
    const char *key; /* 仅 KEY_VALUE / KEY_ONLY 时需要 */

    pm_task_payload_type_t payload_type;
    uint64_t data_size;

    union {
        struct {
            const void *data;
            size_t size;
        } inline_payload;

        pm_data_ref_t shared_memory;
    } payload;
} pm_task_invocation_t;
~~~

| 字段 | 必要性 | 说明 |
|---|---|---|
| so_name | 必须 | 下游定位 SO，入口固定 handler |
| session_id | 必须 | 业务 Session |
| input_mode | 必须 | INPUT_VALUE / INPUT_KEY_VALUE / INPUT_KEY_ONLY |
| key | 条件必需 | Key+Value 或 Key Only |
| payload_type | 必须 | NONE / INLINE / SHARED_MEMORY |
| data_size | 必须 | 输入数据字节数；NONE 时为 0 |
| inline_payload | 条件必需 | Inline 字节及长度 |
| shared_memory | 条件必需 | DataRef |

**明确不传：** app_name、bucket、event_id、task_id、source_function、trigger_name、source_type、primitive_type、trigger_option、resource、execution、entry_name、handler_name。以上信息已由本模块完成解析，或属于静态配置，或由下游内部生成/管理。

### 11.4 原子资源准入与入队

C 原型：

~~~c
pm_pool_submit_result_t task_pool_try_enqueue(
    void *pool_ctx,
    const pm_task_invocation_t *task);
~~~

返回值：

| 返回值 | 语义 | 是否接管任务 |
|---|---|---|
| PM_POOL_ACCEPTED | 已原子完成容量判断和入队 | 是 |
| PM_POOL_NO_CAPACITY | 当前无可接收位置 | 否 |
| PM_POOL_NOT_READY | Pool 未初始化或不可接收 | 否 |
| PM_POOL_INVALID_TASK | 参数或任务格式非法 | 否 |
| PM_POOL_ERROR | 下游内部错误 | 否 |

**原子性要求：** Pool 必须在同一原子操作/临界区内完成容量检查和入队，不允许本模块先查询空位再单独 enqueue。

**所有权要求：**

- ACCEPTED：Pool 在返回前复制完整 TaskInvocation；复制 Inline 数据；接管 Router 已 retain 的 DataRef。
- 非 ACCEPTED：Pool 不保留 TaskInvocation 指针，不复制、不接管 DataRef。
- Pool 执行结束、失败或取消后释放其持有的 Inline 副本和 DataRef。
- Pool 内部负责队列消费和协程唤醒，不提供给本模块调用的单独唤醒接口。

### 11.5 Task Router 的延时行为

只有 PM_POOL_NO_CAPACITY 进入 Delay Queue。Pool 未就绪、任务非法和内部错误不作为容量不足重试。

- Delay Queue 开启：Router 暂存 TaskInvocation 和 DataRef，按 retry_interval_ms 重试。
- 重试成功：Pool 接管。
- 达到 max_wait_ms：Router 记录 TASK_DELAY_EXPIRED 并释放。
- Delay Queue 关闭：Router 记录 PROCESS_DISPATCH_REQUIRED，dispatched=false，并释放。
- 本期不执行进程间或节点间转发。

### 11.6 下游必须保证

1. 静态 Function 注册接口可校验 so_name、resource、execution。
2. so_name 映射到 /dev/shm/<so_name>，SO 固定导出 handler。
3. try_enqueue 的容量判断与入队原子。
4. ACCEPTED 代表 Pool 已复制必要描述符并接管 DataRef。
5. 拒绝时不保留任何调用方指针或引用。
6. Pool 自行确保成功入队的任务能被内部消费者发现，不依赖本模块发起唤醒。
7. Pool 创建 handler TaskContext 时，将 TaskInvocation.so_name 写入 TaskContext.source_function；Object SDK 使用该字段注入函数输出事件。
8. handler 输入视图仅在 handler 调用期间有效。
