# 第四部分：工程实现设计（第 15～18 章）

## 第 15 章 并发与可靠性设计

### 15.1 并发模型

- DataReadyQueue 生产者可以来自多个 Actor/SDK 调用线程。
- 每个 Scheduler Process 默认一个事件消费线程；若采用多消费者，Data SDK 队列必须明确支持对应并发模型。
- Event Trigger 可以并发处理不同事件；ImmediateTrigger 无可变聚合状态。
- Task Router 支持多个事件线程并发提交。
- Task Pool 自己负责 TaskQueue 和协程唤醒的并发安全。

### 15.2 Registry 只读访问

初始化完成后 RegistrySnapshot 不可变。热路径只读查询；配置更新（P1）采用新快照构建、校验、原子切换、旧快照延迟释放，禁止原地修改 map。

### 15.3 多生产者并发事件通知

DataReadyQueue 的 MPSC/MPMC 模型由 Data SDK 定义。Scheduler Consumer 必须遵循队列的 acquire/release 协议。事件被取出后，Scheduler 先校验再处理，不得在队列内长时间执行 Task Pool 网络调用；如需异步投递，必须有独立的有界队列和明确回压。

### 15.4 Task 并发投递

Node/Process 状态是调度快照，不能替代最终准入。最终容量由目标 Task Pool try_submit 原子确认。状态快照过期时允许出现一次提交失败，但不能出现超出池容量的成功提交。

### 15.5 重复事件处理

DataReadyEvent 必须有稳定 event_id。去重键为 event_id + route_id（DIRECT 目标或 trigger_id）+ target_function_id。去重表有固定容量和 TTL，达到上限时采用可观测的淘汰策略。V0.3 仅保证进程生命周期内的有界去重，不保证进程重启后的 exactly-once。

### 15.6 DataRef 生命周期安全

每个 Task 输入引用必须在 TaskDescriptor 创建前 retain。所有失败分支必须释放已 retain 的引用。成功提交后引用所有权转给 Task Pool。使用 generation 防止对象释放后同一共享内存 offset 被复用造成 ABA。

### 15.7 部分投递失败

fan-out 不做全有或全无事务。每个目标独立提交，返回逐目标结果。若未来要求原子 fan-out，需要引入持久化任务组和补偿机制，不属于本期。

### 15.8 异常处理与资源清理

异常包括配置错误、DataRef 无效、内存分配失败、Node 不可达、Process 不可用、Task Pool 队列满、Pool 停止和 IPC 失败。所有异常统一映射 SchedulerError；清理代码使用单一出口或资源 guard 模式的 C 等价实现，避免多分支漏释放。

### 15.9 可靠性边界

- Data SDK 负责已 Commit 事件不丢失或可重试。
- Scheduler 负责明确反馈接收结果和释放未转移引用。
- Task Pool 负责已接收任务的排队和执行生命周期。
- 本期不提供跨节点持久化 Exactly-once。
- 若进程在 DataReadyEvent 消费后、确认前崩溃，Data SDK 必须通过事件重放/租约超时重新投递；Scheduler 依赖 event_id 去重。

## 第 16 章 性能设计

### 16.1 调度关键路径

T0 数据 Commit；T1 DataReadyEvent 发布；T2 Scheduler 取事件；T3 Trigger 匹配完成；T4 TaskDescriptor 构建完成；T5 Node 选择完成；T6 Process 选择完成；T7 Task Pool 接收；T8 Worker 开始执行。

端到端调度延迟为 T8-T0；模块内部耗时分别记录，避免只看一个总耗时无法定位瓶颈。

### 16.2 配置预解析及索引

Function、Dependency、Trigger 的字符串匹配全部在启动时构建索引。热路径不遍历原始 JSON，不解析文件，不做 SO 加载。

### 16.3 查询效率

- Function Registry：function_id 哈希查询。
- Dependency Registry：source_function_id 哈希查询，目标集合顺序存储。
- Trigger Registry：bucket_id 哈希查询，规则数组顺序遍历。
- DataRef：只校验必要字段，不映射 Payload。

### 16.4 减少运行时内存分配

P0 允许使用 calloc/free 保证实现简单；性能阶段再引入 TaskDescriptor 对象池、输入数组小对象优化和批量回收。禁止为了减少分配而复用仍被 Task Pool 持有的对象。

### 16.5 减少锁竞争

Registry 只读；ImmediateTrigger 无状态；去重表分片锁；Node/Process 状态采用快照或细粒度锁；TaskQueue 锁完全由 Pool 管理。

### 16.6 数据零拷贝协作

Scheduler 不复制 Payload。DataRef 只传输小型元数据；跨进程时序列化句柄而非指针。若跨节点 DataRef 不能直接读取，必须由 Data SDK 提供远程读取，不允许 Scheduler 自己复制数据。

### 16.7 TaskDescriptor 传递开销

TaskDescriptor 应尽量小，输入以 DataRef 数组表示；字符串可通过 Registry 中的 function_id 引用减少重复复制，但跨进程传输时必须序列化完整必要字段或版本化 ID。

### 16.8 性能测量指标

- Event throughput、Task throughput。
- Commit-to-Event、Event-to-Trigger、Trigger-to-Task、Task-to-Queue、Queue-to-Start 延迟。
- p50、p95、p99。
- Trigger match miss/hit、fan-out 数量、duplicate 数。
- Node/Process 选择耗时、队列深度、队列满比例。
- DataRef retain/release 数量和未释放引用数。
- CPU、RSS、锁等待和内存分配次数。

## 第 17 章 日志与可观测性设计

### 17.1 日志等级

ERROR：数据引用损坏、配置错误、所有权协议违规。WARN：容量不足、队列满、远程节点不可达、重复事件。INFO：启动、配置代数、任务接收、任务完成。DEBUG：Trigger 匹配过程和细粒度路由候选。

### 17.2 统一日志字段

timestamp_mono_ns、level、module、event_id、task_id、app_id、function_id、trigger_id、bucket_id、key、session_id、node_id、pid、pool_id、queue_depth、status、error_code、duration_ns。

### 17.3 关键日志点

- 配置加载成功/失败及 config_generation。
- DataReadyEvent 入队、出队、校验失败。
- DIRECT 目标展开或 ImmediateTrigger 命中。
- TaskDescriptor 构建、DataRef retain。
- Node/Process 选择及候选容量。
- Task Pool try_submit 结果和所有权转移。
- Task 执行开始/结束回报和 DataRef release。

### 17.4 指标

建议暴露：
- scheduler_events_total{result}
- scheduler_tasks_built_total{route_kind}
- scheduler_tasks_submitted_total{result}
- scheduler_trigger_matches_total{trigger_type}
- scheduler_route_duration_seconds{level}
- scheduler_queue_depth{pool}
- scheduler_dataref_outstanding
- scheduler_event_dedup_total
- scheduler_resource_available{node,pid}

指标标签禁止直接使用高基数 event_id、task_id、key、session_id；这些字段只写日志和 Trace。

### 17.5 Trace 关联

以 event_id 为上游 Trace 关联键；一个事件 fan-out 多个 Task 时，每个 Task 使用独立 task_id，并记录 parent_event_id。跨节点传递时保留 trace_id、span_id。

## 第 18 章 C 语言工程设计

建议结构：

### 18.2 公共头文件

公共头文件只放稳定 ABI 类型和函数声明。内部 HashMap、Dedup、RegistrySnapshot 等实现细节放在 src/private 头文件，避免形成不必要的外部依赖。

### 18.3 源文件职责

每个 .c 文件只负责一个模块；模块间通过头文件接口调用。Event Trigger 不 include Task Pool 内部头文件，只依赖 task_router.h。

### 18.4 第三方依赖

- C11 编译器和 POSIX pthread。
- JSON 解析库：cJSON 或 yyjson，最终二选一。
- 日志：优先接入宿主日志接口；若无统一日志，提供轻量适配层。
- 测试：CTest + 单元测试框架；必要时使用 AddressSanitizer、UndefinedBehaviorSanitizer 和 ThreadSanitizer。
- 不将 C++ STL 作为 C 模块依赖。

### 18.5 CMake 构建

拆分 scheduler_core、scheduler_adapters、scheduler_demo、scheduler_tests。scheduler_core 不链接具体 Data SDK 或 Task Pool 实现；通过 Adapter 在集成阶段链接真实实现。

### 18.6 编译与集成

核心模块可在无真实共享内存和协程池环境下通过 Mock 编译测试。集成阶段替换 Data SDK Adapter 和 Task Pool Adapter，不应修改 Event Trigger / Task Builder 核心逻辑。

### 18.7 Task SO 编译与部署

Producer/Processor 使用统一 Task ABI 编译为共享库。CI 检查导出符号、ABI 版本、依赖库和架构一致性。SO 部署使用版本化目录。

### 18.8 Mock Data Bucket SDK

Mock 实现写入普通内存块并生成 DataRef，模拟 Commit-before-notify、事件队列满、retain/release 和 generation 变化。

### 18.9 Mock Task Pool

Mock 实现容量、队列深度、try_submit、wake_one 计数和执行完成回调。必须覆盖“入队成功但没有等待协程”的情况。

### 18.10 Demo 运行方式

Demo 至少提供单节点、单进程、一个 Producer、一个 ImmediateTrigger、一个 Processor 的端到端链路；第二阶段增加多进程模拟；第三阶段接入 Node Scheduler 真实节点状态。
