# 第四部分：工程实现设计（第 15～18 章）

[返回 V0.5 主文档](../V0.5-完整软件设计方案.md)

## 第 15 章 并发与可靠性设计

### 15.1 并发模型

本模块是单进程 C11 库，不创建专用调度线程。App Registry 在注册阶段写入，seal 后只读；多个线程/协程可以并发调用 event_trigger_notify。每次 notify 使用独立的栈上事件视图、TaskAction、TaskDescriptor 和结果缓冲区。

共享状态仅包括只读 AppRecord、原子 Task ID 计数器和必要的生命周期状态。不得用进程全局 current_app/current_function 表示当前任务；source_function 必须来自事件或 TaskContext。

### 15.2 App 注册与运行态切换

- register_app 在注册阶段执行完整 JSON 校验和临时索引构建。
- AppRecord 发布必须原子完成；重复 app_name 返回冲突，不覆盖旧配置。
- seal 后禁止注册、替换或删除 App，运行期 Registry 只读。
- seal 与 notify 的并发由宿主生命周期约束：必须先完成所有注册，再开启 DataReadyEvent 通知。
- destroy 前停止新通知并等待所有在途 notify 完成；不得在 handler 回调中销毁 Registry。

本期不做在线配置热更新。需要变更配置时，由宿主停止通知、排空或终止相关任务、释放引用后重新注册。

### 15.3 Payload 与引用生命周期

**Inline：**

1. Data SDK 在 notify 期间保持 inline_data 有效且不可变。
2. Task Builder 对每条需要 value 的命中规则复制 Inline 字节。
3. try_enqueue 成功后 Pool 复制/保存完整 TaskDescriptor。
4. notify 返回后 SDK 可以释放事件缓冲区；Task 不再引用该缓冲区。
5. 队列拒绝时只释放 TaskDescriptor 临时副本，不调用 DataRef release。

**Shared Memory：**

1. Data SDK 在 notify 期间持有基础 DataRef。
2. 每条需要 value 的命中规则单独 retain 一次。
3. try_enqueue 成功时 Pool 接管该份引用；失败时 Router release。
4. Pool 在执行完成、失败或取消时 release。
5. 同 Bucket/Key 覆盖写不得使已 retain 的 DataRef 指向新版本。

KEY_ONLY 不复制 Inline Payload，也不 retain DataRef。

### 15.4 多 Trigger 部分成功

一个事件可命中多条规则。每条规则独立执行 build → enqueue：

- 已成功入队的 Task 不因其他规则失败而回滚。
- 单条规则 build 失败、队列满或 Pool 拒绝，只影响该条 Task。
- Inline 每条 Task 独立复制；Shared-Memory 每条 Task 独立 retain。
- 结果按 Trigger 配置顺序返回，matched = enqueued + overflow + failed。

### 15.5 重复通知、重试与去重

P0 不实现事件去重、自动重试、持久化事件日志或 Exactly-once。相同 event_id 再次 notify，可能再次产生 Task。上游不得因一条事件部分成功而盲目重放全部规则。

队列满的 Task 本次未接收；本期只记录 PROCESS_DISPATCH_REQUIRED，不缓存、不转发、不重试。后续若需重试或有界去重，作为独立需求评估，不在 V0.5 隐式实现。

### 15.6 覆盖写边界

SDK 对相同 Bucket/Key 的覆盖写若不发出新通知，Event Trigger 不会感知该变化。已有 Task 必须通过其 DataRef 读取事件发生时对应的不可变版本。若 Data SDK 当前实现不能 pin 住版本，则这是 T10 的接口阻塞项，不能通过 Scheduler 在执行时重新读 Key 来规避。

### 15.7 异常与安全

非法配置、未知 App/Bucket/Function、Payload 形态错误、DataRef 无效、内存不足、队列满、Pool 未就绪和唤醒异常分别记录。数据 Commit 成功不等于 Task 已入队；Task 入队成功不等于 handler 执行成功。

无状态和 Object API 约束属于 APP 合约。P0 不实现系统调用沙箱；业务 SO 的代码审查必须检查可变全局状态、文件 I/O、网络 Socket 和旁路数据交换。

## 第 16 章 性能设计

### 16.1 热路径边界

热路径从 event_trigger_notify 进入开始，到全部命中项完成 enqueue 尝试并返回结束。JSON 解析、索引构建、SO 检查和资源配置读取均在注册阶段完成。

### 16.2 复杂度与数据复制

- app_name 查询：App Registry 索引查询，目标平均 O(1)（依实现）。
- Bucket 查询：Trigger Index 查询，目标平均 O(1)。
- 规则匹配：对该 Bucket 的 K 条规则顺序扫描，O(K)。
- Task 构建/路由：对 M 条命中规则执行 O(M)。
- Inline：每条需要 value 的 Task 复制 data_size 字节；这是小数据载体的必要所有权复制。
- Shared Memory：不复制业务 Payload，只执行 validate/retain/release 和描述符复制。
- KEY_ONLY：不复制 Payload、不 retain DataRef。

不能笼统宣称“全链路零拷贝”；应分别统计 Inline 复制字节数、Shared-Memory retain 次数和描述符复制次数。

### 16.3 内存与锁

注册后索引只读，notify 不获取全局注册写锁。Task ID 使用原子递增。Inline 最大容量由公共 ABI 常量定义，超过容量的事件必须由 SDK 以 Shared-Memory DataRef 形式提供；Scheduler 不将超限 Inline 自动转换为共享内存。

TaskDescriptor 大小与协程栈预算需实测；若固定内联数组导致描述符过大，可由上下游共同冻结可变长尾随存储，但不能退化为借用 SDK 临时指针。

### 16.4 性能评测

固定硬件、编译选项、并发度、队列容量、Bucket 数、每 Bucket Trigger 数、命中率、fan-out 数、Payload 类型和数据大小。预热后分别测：

- Immediate 命中、ByName 命中/未命中。
- 单 Trigger 与同 Bucket 多 Trigger。
- Inline 小数据复制路径。
- Shared-Memory DataRef retain 路径。
- KEY_ONLY 路径。
- 正常入队、队列满和 Pool 未就绪。

报告吞吐、p50/p95/p99、样本数、CPU/RSS、队列满比例、每 Task 复制字节数、retain/release 次数、notify 延迟。SDK 传输耗时、Scheduler 处理耗时、Pool 排队和执行耗时分开统计。无实测数据不承诺微秒级 SLA。

## 第 17 章 日志与可观测性设计

### 17.1 结构化日志字段

建议字段：level、module、monotonic_ns、app_name、event_id、task_id、session_id、source_function、bucket、key（按需脱敏）、trigger_name、target_function、primitive_type、payload_type、data_size、input_mode、route_status、wake_status、duration_ns。

禁止记录业务 Payload、DataRef 原始敏感内容或完整对象数据。

### 17.2 关键日志

| 场景 | 级别 | 事件名 |
|---|---|---|
| App 注册成功/失败 | INFO / ERROR | APP_REGISTERED / APP_REGISTER_FAILED |
| App 重复注册 | WARN | APP_DUPLICATE |
| DataReadyEvent 非法 | WARN | EVENT_INVALID |
| Trigger 命中 | DEBUG | TRIGGER_MATCHED |
| 无规则命中 | DEBUG | TRIGGER_NO_MATCH |
| Task 构建失败 | WARN | TASK_BUILD_FAILED |
| 本地队列接收 | DEBUG | TASK_ENQUEUED |
| 本地队列满 | WARN | PROCESS_DISPATCH_REQUIRED |
| Pool 其他拒绝 | WARN | POOL_ENQUEUE_REJECTED |
| 唤醒无等待者 | DEBUG | WAKE_NO_WAITER |
| 唤醒异常 | ERROR | WAKE_FAILED |

队列满日志必须包含 `dispatched=false`，明确表示本期没有真实进程间分发。唤醒失败不得覆盖已经成功的入队结果。

### 17.3 指标

- app_register_total / app_register_failed_total
- data_events_total（valid / invalid / no_match）
- trigger_matched_total（immediate / by_name）
- tasks_built_total / tasks_enqueued_total / tasks_overflow_total / tasks_failed_total
- payload_inline_events_total / payload_shared_memory_events_total
- inline_bytes_copied_total / data_ref_retain_total / data_ref_release_total
- wake_signaled_total / wake_no_waiter_total / wake_failed_total
- notify_latency、task_build_latency、enqueue_latency

无需建设独立监控服务；P0 通过宿主指标接口或测试 Harness 采集。

## 第 18 章 C 工程设计

### 18.1 目录建议

~~~text
include/
  task_scheduler.h
src/
  app_registry/
    app_registry.c       # register_app / seal / lookup / destroy
    app_json_parse.c     # App Registry 内部 JSON 解析与校验
    app_index.c          # Function Index / Trigger Index
  trigger/
    event_trigger.c
    immediate_trigger.c
    byname_trigger.c
  task/
    task_builder.c
  router/
    task_router.c
    task_pool_adapter.c
tests/
  unit/
  contract/
  integration/
  mocks/
examples/
  app.json
  producer.c
  processor.c
~~~

没有独立 Config Loader 对外模块、Dependency Registry、DIRECT Handler、Node/Process Scheduler 或 Task Coroutine Pool 实现。

### 18.2 依赖与编译

Linux、C11、CMake、cJSON（仅 App 注册阶段解析）、C11 atomics；仅在确有需要时使用 pthread 保护注册期状态。公开头文件不依赖 cJSON。Data SDK 和 Pool 均通过 Adapter 注入。编译启用 -Wall -Wextra -Werror；测试使用 ASan/UBSan，独立 TSan 压测。

### 18.3 构建目标

建议产出静态库 task_scheduler_core，包含 App Registry、Event Trigger、Task Builder、Task Router。Mock Data SDK 与 Mock Pool 只用于测试，不进入生产库。业务 SO 示例单独编译为 producer.so / processor.so；SO 部署由环境/下游框架负责。

### 18.4 实现顺序

1. 冻结 app.json、DataReadyEvent、Payload 和 DataRef 生命周期。
2. 实现 App Registry 注册事务及内部索引。
3. 实现 Immediate / ByName 匹配和多 Trigger 枚举。
4. 实现 Task Builder 的 Inline Copy / DataRef Retain。
5. 实现 Task Router 的 try_enqueue / wake_one Adapter。
6. 完成 Mock、上下游契约测试和真实联调。

本仓库当前交付为设计文档和接口示例，不代表已存在可运行的 Scheduler 实现。
