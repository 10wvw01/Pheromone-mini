### 12.2 模块依赖规则

- registry 不依赖 Event Trigger、Task Builder 和 Task Router。
- direct_dependency 与 event_trigger 只读取 Registry 索引。
- task_builder 依赖 DataRef Adapter，但不依赖 Pool 内部实现。
- task_router 只依赖 Task Pool Adapter 和 Delay Queue。
- 上下游真实实现通过函数指针 Adapter 注入，单元测试使用 Mock。
- 不在业务路径中使用 C++ 容器、异常、类或模板。

### 12.3 C 语言规范

- 目标标准 C11。
- 公共 ABI 使用固定宽度整数、显式长度和不透明句柄。
- 所有指针参数明确借用或转移语义。
- 不允许把裸共享内存地址当作 DataRef。
- 错误通过枚举返回，不使用 longjmp。
- 字符串长度、数组容量和整数溢出必须校验。
- 公共头文件保持 extern "C" 兼容包装可以由构建系统提供，但示例和实现均使用 C。

## 第 13 章 并发、生命周期与可靠性

### 13.1 Registry 发布

注册过程采用候选对象构建：

1. 在私有内存解析 JSON。
2. 校验 app_name、so_name、Bucket、DIRECT 和 Trigger。
3. 构建所有索引。
4. 检查候选 app.json 的 scheduler.delay_queue 与 Registry 已建立的进程级配置一致；若尚未建立，则暂存为候选全局配置。
5. 注册 Pool Function 静态配置。
6. 原子发布 AppRecord、全局索引和（若尚未建立）进程级 Delay Queue 配置。

注册失败不得留下半个 App。若 Pool 已成功注册部分 Function，必须按注册记录逆序调用下游注销/回滚接口；若下游不支持注销，启动期必须先完成 dry-run 校验并提供明确的失败恢复策略。

Registry seal 后只读。Destroy 前停止新通知，并等待所有在途 notify、Router 和 Delay Queue 项退出。

### 13.2 全局索引与命名

- app_name：全局唯一。
- scheduler.delay_queue：进程级全局单例；后续 App 注册必须与首个成功注册的配置完全一致。
- bucket：跨所有已注册 App 全局唯一。
- so_name：单 App 内唯一；相同物理 SO 在多个 App 复用时，resource / execution 必须一致，Pool 注册幂等。
- trigger_name：App 内唯一。
- DIRECT source / target：必须引用所属 App 已注册的 so_name。
- Bucket Index 保存所属 App 和有序 Trigger[]。

### 13.3 DataReadyEvent 并发

DataReadyEvent 是只读借用视图。SDK 保证 Inline 指针在 notify 返回前有效；Task Builder 在同步构建阶段复制所需字节。DataRef 的 validate / retain / release 必须线程安全，或由 Data SDK 明确提供外部串行化约束。

同一事件的多条 Trigger 可以并发处理，但 V0.6 推荐按配置顺序串行生成 TaskAction，先确保行为确定性；Pool 的并发执行不由本模块控制。

### 13.4 TaskInvocation 所有权状态

~~~mermaid
stateDiagram-v2
    [*] --> BuilderOwned
    BuilderOwned --> RouterOwned: Task 构建完成
    RouterOwned --> PoolOwned: try_enqueue = ACCEPTED
    RouterOwned --> DelayOwned: NO_CAPACITY 且 Delay Queue 启用
    DelayOwned --> PoolOwned: 重试 ACCEPTED
    DelayOwned --> RouterReleased: 超过 max_wait_ms
    RouterOwned --> RouterReleased: 关闭延时 / 终止错误
    PoolOwned --> Released: handler 完成 / 失败 / 取消
    RouterReleased --> [*]
    Released --> [*]
~~~

- Builder 构建阶段失败：释放本次已复制数据和已 retain 的 DataRef。
- Router 正常提交：临时持有 TaskInvocation。
- ACCEPTED：Pool 接管；Router 不再释放 DataRef。
- NO_CAPACITY：所有权仍在 Router；可进入 Delay Queue。
- Delay Queue 超时或终止错误：Router 释放。
- Pool 结束任务：Pool 释放其拥有的数据。

### 13.5 DataRef 覆盖写

DataRef 必须绑定 Commit 版本。SDK 可采用版本化对象、Copy-on-Write、引用保护或等价方案。若旧 DataRef 仍有引用，覆盖写不得复用并污染旧数据。Scheduler 不根据 Bucket/Key 再读取“最新值”替代旧 DataRef。

## 第 14 章 Task Router 与 Delay Queue 实现

### 14.1 原子提交原则

Router 只调用 task_pool_try_enqueue。Pool 内部原子检查可接收位置并入队。不得拆分为 has_free_slot 与 enqueue 两次调用。

只有 PM_POOL_NO_CAPACITY 表示可进入 Delay Queue；PM_POOL_NOT_READY、PM_POOL_INVALID_TASK、PM_POOL_ERROR 均按终止错误处理并释放资源。

### 14.2 Delay Queue 数据结构

建议使用按 next_retry_at_ms 排序的最小堆或时间轮。每项至少保存：

- TaskInvocation 的 Router 自有副本。
- DataRef 所有权状态。
- enqueue_started_at_ms（单调时钟）。
- next_retry_at_ms。
- expires_at_ms。
- retry_count（仅日志诊断，不作为 Function 重执行次数）。

使用单调时钟计算等待时长，不使用系统墙上时钟。不得忙等；由宿主运行时定时驱动到期项处理。队列容量设置实现级上限，达到上限时拒绝新延时项并释放资源。

### 14.3 延时调度状态机

~~~mermaid
stateDiagram-v2
    [*] --> ReadyToSubmit
    ReadyToSubmit --> Accepted: ACCEPTED
    ReadyToSubmit --> CapacityBlocked: NO_CAPACITY
    ReadyToSubmit --> TerminalFailure: 其他错误
    CapacityBlocked --> Delayed: enabled
    CapacityBlocked --> TerminalFailure: disabled
    Delayed --> ReadyToSubmit: retry interval 到期且未超时
    Delayed --> Expired: now >= expires_at
    Accepted --> [*]
    TerminalFailure --> [*]
    Expired --> [*]
~~~

### 14.4 延时到期与拒绝处理

- Delay Queue disabled：记录 PROCESS_DISPATCH_REQUIRED，字段 dispatched=false。
- Delay Queue 满：记录 DELAY_QUEUE_FULL。
- 等待超时：记录 TASK_DELAY_EXPIRED。
- Pool 非容量错误：记录 Pool 错误码，不循环重试。
- 所有终止路径必须释放 Router 持有的 DataRef 和 Inline 内存。

### 14.5 退出清理

Registry 关闭时停止接收新事件；Router 停止接受新 Task；Delay Queue 中未提交任务按关闭策略统一取消并释放；Pool 已接收任务由 Pool 完成自身清理。销毁前确认没有在途 Adapter 回调。

## 第 15 章 错误处理、日志与性能

### 15.1 错误分层

- 配置错误：注册失败，不发布 App。
- 事件错误：拒绝单个 DataReadyEvent，不影响 Registry。
- 单规则错误：记录规则级失败，继续处理其他 Trigger。
- Task 构建错误：释放当前 Task 已持有资源，继续其他独立命中项。
- Pool NO_CAPACITY：进入 Delay Queue 或终止记录。
- Pool 其他错误：终止当前 Task，不当作容量不足重试。
- Delay Queue 超时：记录并释放，不执行 Function 重试。

### 15.2 结构化日志字段

建议字段：trace_seq、app_name（仅内部日志）、bucket、key、session_id、source_function、so_name、route_path（DIRECT / BUCKET_TRIGGER）、trigger_name（仅内部日志）、input_mode、payload_type、pool_result、delay_state、elapsed_ms、dispatched。

上述内部诊断字段不因此进入 DataReadyEvent 或 TaskInvocation ABI。

### 15.3 性能原则

- Registry 只在注册期构建索引，运行期只读。
- Bucket 查找平均 O(1)，遍历该 Bucket 的 K 条 Trigger 为 O(K)。
- DIRECT 查找平均 O(1)，目标数为 D 时构建 O(D) 个 Task。
- Inline 复制仅发生在需要 Value 的 Task。
- Shared-Memory 只 retain 引用，不复制大数据。
- Delay Queue 使用到期队列，不进行全量忙轮询。
- 不引入节点状态、网络调用或跨进程 IPC 热路径。

## 第 16 章 编译、构建与交付

### 16.1 构建目标

- pm_registry：配置解析和索引。
- pm_dependency：DIRECT 匹配。
- pm_trigger：Immediate / ByName。
- pm_task_builder：TaskInvocation 组装与数据所有权。
- pm_router：try_enqueue 和 Delay Queue。
- pm_tests：单元、Mock 集成和上下游契约测试。

### 16.2 编译要求

- C11。
- 开启 -Wall -Wextra -Werror -Wconversion -Wshadow 等适用告警。
- AddressSanitizer / UndefinedBehaviorSanitizer 用于单元测试。
- ThreadSanitizer 用于 Registry 并发只读、DataRef 引用和 Delay Queue 并发测试。
- JSON Parser 必须拒绝重复字段、未知字段和错误类型。

### 16.3 实现顺序

1. 公共 C ABI、错误码和 Mock Adapter。
2. app.json Parser、校验和 Registry。
3. DIRECT Index 与 DIRECT 路径。
4. Immediate / ByName 和多 Trigger。
5. Task Builder 与 Inline / DataRef 生命周期。
6. 原子 Task Pool Adapter。
7. Delay Queue。
8. 端到端 Mock 测试、上下游契约联调和性能基线。
