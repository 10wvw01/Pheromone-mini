# 第三部分：接口与协作设计（V0.6）

[返回 V0.6 主文档](../V0.6-完整软件设计方案.md)

> 本文定义 Pheromone-mini V0.6 的进程内 C API / ABI 和上下游协作契约。接口设计以单进程、单调度实例为前提。上游 Data Bucket SDK 只需要调用 event_trigger_notify；本模块内部完成配置加载、JSON 解析、索引构建和路由。本文不定义 HTTP、RPC 或跨进程协议。

## 1. 文档范围与接口边界

### 1.1 参与方

| 参与方 | 职责 | 与本模块的接口关系 |
|---|---|---|
| 上游 SMC Actor / Data Bucket SDK | 写入并 Commit 数据，提供数据地址和长度，维护 Session 生命周期 | 调用 event_trigger_notify |
| Pheromone-mini | JSON Parser、Registry、DIRECT、Event Trigger、Task Builder、Task Router、Delay Queue | 实现唯一对上游公开的运行期 API |
| Task Coroutine Pool | 静态 Function 配置注册、原子任务入队、队列消费、协程调度、SO 加载和函数执行 | 向本模块提供静态注册能力和 try_enqueue |
| Function | 处理 TaskContext 输入，通过 Object API 写出数据 | 按统一函数 ABI 导出 func_name |

### 1.2 接口方向

~~~mermaid
flowchart LR
    SDK["上游 Data Bucket SDK"] -->|"event_trigger_notify(event, source_func_name, data_addr, data_size)"| PM["Pheromone-mini"]
    PM -->|"启动阶段：FunctionRuntimeConfig[]"| POOL["Task Coroutine Pool"]
    PM -->|"运行阶段：try_enqueue(TaskInvocation)"| POOL
    POOL -->|"dlopen(so_name) / dlsym(func_name) / 调用"| FN["Function"]
    FN -->|"Object API 写入输出；SDK 注入 source_func_name"| SDK
~~~

### 1.3 接口分组与边界

- A 组：本模块提供给上游的 API，仅保留 PM-API-004 event_trigger_notify。
- B 组：下游 Pool 运行期 Adapter，仅保留 POOL-API-001 try_enqueue。
- Pool 静态 Function 配置注册是启动阶段协作，不放入运行期 Adapter。
- 不存在 DataRef Adapter、validate、retain、release 等 Data SDK 回调。
- Function ABI 单独定义 so_name、func_name 和 arguments[] 的执行契约。

Registry 是本模块内部唯一实例。创建、配置加载、封存和销毁均由本模块内部启动 / 关闭流程完成，不作为上游客户 API 暴露。

## 2. API 清单

### 2.1 A 组：本模块提供给上游的 API

| API ID | API 名称 | 调用方 | 调用阶段 | 功能 |
|---|---|---|---|---|
| PM-API-004 | event_trigger_notify | Data Bucket SDK / Object SDK | 每次数据 Commit 成功后 | 提交 Bucket、Key、Session、来源函数和数据地址，触发 DIRECT / Bucket Trigger 判断并路由任务 |

本组不再暴露 pm_registry_create、register_app、pm_registry_seal、pm_registry_destroy 或其他配置生命周期接口。

### 2.2 B 组：下游 Task Coroutine Pool 运行期 API

| API ID | API 名称 | 调用方 | 功能 |
|---|---|---|---|
| POOL-API-001 | try_enqueue | Task Router | 原子检查队列容量并提交完整 TaskInvocation |

Pool Adapter 结构只包含 try_enqueue，不包含 register_function、unregister_function、wake_one 或 DataRef 操作。

### 2.3 Pool 启动阶段静态 Function 配置协作

静态 Function 配置必须在运行期事件到达前交付给 Pool，但它不是运行期 Pool Adapter 回调。

每条配置包含：

| 字段 | 含义 |
|---|---|
| so_name | 动态库文件名，Pool 用于 dlopen |
| func_name | 动态库内的函数符号，Pool 用于 dlsym |
| resource | 该 Function 的 CPU / Memory 等资源需求 |
| execution | 该 Function 的协程、优先级、并发等执行配置 |

注册粒度为 Function，即配置关联到 so_name + func_name。一个 SO 可以包含多个函数；Pool 可以按 so_name 复用 SO Handle，但每个 func_name 独立解析符号并关联自己的 resource / execution。

启动阶段静态配置导入失败时，模块不得进入可接收事件的运行态。具体 Pool 初始化入口由下游 Pool 启动契约提供，不放入 pm_task_pool_adapter_t。

### 2.4 上游必须遵守的数据通知契约

上游在一次成功 Commit 后调用 event_trigger_notify，并传入：
- DataReadyEvent：bucket、key、session_id。
- source_func_name：当前数据生产函数名称；外部 SMC Actor 可传 NULL。
- data_addr：已提交数据的地址。
- data_size：数据长度。

本模块不调用 Data SDK 查询数据，不负责申请、复制、释放数据内存。

## 3. 公共类型与返回码

### 3.1 DataReadyEvent

~~~c
typedef struct {
    const char *bucket;
    const char *key;
    const char *session_id;
} pm_data_ready_event_t;
~~~

| 字段 | 方向 | 必须 | 说明 |
|---|---|---:|---|
| bucket | IN | 是 | 全局唯一 Bucket 名称 |
| key | IN | 是 | 本次 Commit 对象 Key，必须非空 |
| session_id | IN | 是 | 业务 Session 标识 |

DataReadyEvent 不包含 source_func_name、data_addr、data_size、payload_type、DataRef、app_name、event_id、trigger_name 或目标函数。

### 3.2 TaskArgument

~~~c
typedef struct {
    const char *key;
    const void *data_addr;
    size_t data_size;
} pm_task_argument_t;
~~~

| 字段 | 必须 | 说明 |
|---|---:|---|
| key | 是 | 输入对象 Key；无论 input_mode 如何，内部描述符都必须保留 |
| data_addr | 按长度 | 上游提供的数据地址；data_size 大于 0 时不得为空 |
| data_size | 是 | 数据长度 |

当前一次事件对应一个输入数据对象，因此当前基础实现 argc=1。arguments[] 保留 Pheromone 的参数列表语义，为后续多输入扩展留出结构。

### 3.3 输入模式

~~~c
typedef enum {
    PM_INPUT_VALUE = 0,
    PM_INPUT_KEY_VALUE = 1,
    PM_INPUT_KEY_ONLY = 2
} pm_input_mode_t;
~~~

| 值 | 来源 | Handler 输入语义 |
|---:|---|---|
| PM_INPUT_VALUE | trigger_option=0；DIRECT 固定此模式 | Value |
| PM_INPUT_KEY_VALUE | trigger_option=1 | Key + Value |
| PM_INPUT_KEY_ONLY | trigger_option=2 | Key Only |

Key 在 TaskArgument 中始终必填。input_mode 只决定 Pool 向 Function 提供的输入视图，不再决定 INLINE / SHARED_MEMORY，也不改变地址传递方式。

### 3.4 TaskInvocation

~~~c
typedef struct {
    const char *session_id;
    const char *so_name;
    const char *func_name;
    pm_input_mode_t input_mode;
    size_t argc;
    const pm_task_argument_t *argv;
} pm_task_invocation_t;
~~~

| 字段 | 必须 | 说明 |
|---|---:|---|
| session_id | 是 | 任务所属 Session |
| so_name | 是 | 动态库文件名，供 Pool 定位并加载 SO |
| func_name | 是 | SO 内的函数符号名称 |
| input_mode | 是 | Handler 输入视图 |
| argc | 是 | 参数数量；当前基础场景为 1 |
| argv | 是 | 参数数组；当前 argv[0] 包含 key、data_addr、data_size |

TaskInvocation 不包含 app_name、bucket、source_func_name、trigger_name、resource、execution、DataRef 或固定 handler 字段。路由元数据留在本模块；Pool 只接收执行所需信息。

### 3.5 本模块公共状态码

~~~c
typedef enum {
    PM_OK = 0,
    PM_ERR_INVALID_ARGUMENT = -1,
    PM_ERR_INTERNAL = -2
} pm_status_t;
~~~

| 状态码 | 含义 | 典型场景 |
|---|---|---|
| PM_OK | 通知处理完成 | 已完成匹配和路由；未命中 Trigger 也属于正常处理 |
| PM_ERR_INVALID_ARGUMENT | 输入参数非法 | event、bucket、key、session_id 为空；数据长度与地址不匹配；来源函数标识非法 |
| PM_ERR_INTERNAL | 内部处理异常 | Registry 索引异常、任务构建失败或不可恢复的内部错误 |

资源不足、无 Trigger 命中和 Pool 队列无容量是运行期路由结果，不扩展为大量公共 API 状态码。资源不足进入独立 TODO 上报分支；队列无容量按 Delay Queue 策略处理。

### 3.6 Pool 入队返回码

~~~c
typedef enum {
    PM_POOL_ACCEPTED = 0,
    PM_POOL_NO_CAPACITY = 1,
    PM_POOL_ERROR = 2
} pm_pool_submit_result_t;
~~~

| 返回码 | 语义 | Router 行为 |
|---|---|---|
| PM_POOL_ACCEPTED | Pool 已原子入队并接收任务描述符 | Router 释放自己的描述符副本；Pool 负责执行 |
| PM_POOL_NO_CAPACITY | Pool 当前队列无可接收容量，未接管任务 | 按 Delay Queue 配置暂存或终止 |
| PM_POOL_ERROR | Pool 内部错误，未接管任务 | 终止任务并记录内部错误 |

## 4. A 组：本模块对上游 API 规格

### 4.1 PM-API-004：event_trigger_notify

**功能：** 接收 Data Bucket SDK 对一次成功 Commit 的通知，执行 DIRECT 优先判断或 Bucket Trigger 匹配，构建 TaskInvocation.arguments[]，经过 CPU / Memory 资源预检查后提交给 Task Router / Pool。

#### 4.1.1 函数原型

~~~c
pm_status_t event_trigger_notify(
    const pm_data_ready_event_t *event,
    const char *source_func_name,
    const void *data_addr,
    size_t data_size
);
~~~

#### 4.1.2 入参规格

| 参数 | 方向 | 类型 | 必须 | 说明 |
|---|---|---|---:|---|
| event | IN | const pm_data_ready_event_t * | 是 | 只包含 bucket、key、session_id |
| source_func_name | IN | const char * | 否 | 数据生产函数名称，用于 DIRECT；外部 SMC Actor 可为 NULL |
| data_addr | IN | const void * | data_size 大于 0 时必须 | 已 Commit 数据的地址 |
| data_size | IN | size_t | 是 | 数据长度；零长度数据是否允许由上游数据契约决定 |

event->bucket、event->key、event->session_id 必须是非空字符串。key 无条件必填。source_func_name 非 NULL 时必须是当前 Bucket 所属 App 中已注册的 func_name。

#### 4.1.3 出参与返回值

本接口不返回匹配数量或 Task 统计结构，只返回 pm_status_t。

- PM_OK：事件已被正常处理；无 Trigger 命中不视为错误。
- PM_ERR_INVALID_ARGUMENT：输入结构或参数不合法。
- PM_ERR_INTERNAL：内部索引、Task 构建或路由发生不可恢复错误。

资源不足是路由业务分支，不作为公共 API 错误码扩展；本期记录 RESOURCE_INSUFFICIENT 并保留上报 TODO。

#### 4.1.4 处理顺序

1. 校验 event、bucket、key、session_id、data_addr 和 data_size。
2. 根据 bucket 查询全局 Bucket Index，定位所属 App。
3. 如果 source_func_name 非空，校验其属于该 App。
4. 查询 DIRECT Dependency Index。
5. 如果存在 DIRECT 目标，按每个 target func_name 构建 DIRECT Task，input_mode 固定 PM_INPUT_VALUE；本次事件跳过 Bucket Trigger。
6. 如果 source_func_name 为空或不存在 DIRECT 目标，查询 Bucket Trigger[]，逐条执行 Immediate / ByName 匹配。
7. 每条命中规则独立构建 TaskInvocation；当前每个 TaskInvocation 的 argc=1。
8. Task Router 查询 Function 静态资源需求并执行 CPU / Memory 预检查。
9. 资源不足：不调用 try_enqueue，进入资源不足 TODO 分支。
10. 资源满足：调用 try_enqueue；NO_CAPACITY 按 Delay Queue 规则处理。

#### 4.1.5 线程安全与数据生命周期

- Registry 初始化完成后只读，允许多个线程并发调用 event_trigger_notify。
- Task Router 和 Delay Queue 必须支持并发提交。
- event、source_func_name、key、session_id 等调用方字符串至少在本次调用期间有效；Task Builder 必须复制异步任务需要长期持有的字符串。
- data_addr 不复制、不释放；上游必须保证该地址在 Session 结束且所有相关任务完成或终止前有效。
- 一个事件触发多个 Task 时，所有 Task 均可借用同一 data_addr；上游必须等待全部相关任务结束后才能回收。
- 本模块不调用 Data SDK，不执行 DataRef validate / retain / release。

## 5. B 组：下游 Task Coroutine Pool API 规格

### 5.1 Pool Adapter 结构

运行期 Adapter 只包含 try_enqueue：

~~~c
typedef struct {
    void *ctx;
    pm_pool_submit_result_t (*try_enqueue)(
        void *ctx,
        const pm_task_invocation_t *task
    );
} pm_task_pool_adapter_t;
~~~

| 字段 | 方向 | 类型 | 必须 | 说明 |
|---|---|---|---:|---|
| ctx | IN | void * | 是 | Pool 自身上下文，由初始化方注入 |
| try_enqueue | IN | function pointer | 是 | 原子容量检查和任务入队 |

Adapter 不包含 register_function、unregister_function、wake_one 或 DataRef 回调。静态 Function 配置在启动阶段通过独立配置注册机制交付，不属于运行期 Adapter。

### 5.2 POOL-API-001：try_enqueue

**功能：** 原子检查 Pool 队列容量并提交完整 TaskInvocation。

~~~c
pm_pool_submit_result_t task_pool_try_enqueue(
    void *ctx,
    const pm_task_invocation_t *task
);
~~~

入参：

| 参数 | 方向 | 类型 | 必须 | 说明 |
|---|---|---|---:|---|
| ctx | IN | void * | 是 | Pool 上下文 |
| task | IN | const pm_task_invocation_t * | 是 | 完整任务描述，包含 Session、SO、函数符号和 arguments[] |

出参：PM_POOL_ACCEPTED、PM_POOL_NO_CAPACITY 或 PM_POOL_ERROR。

调用语义：

1. try_enqueue 必须原子完成容量判断和入队，不能拆成 query_capacity + enqueue。
2. ACCEPTED 表示 Pool 已复制任务描述符及其需要长期持有的字符串，完成入队；Pool 不复制、不释放 data_addr 指向的业务数据。
3. NO_CAPACITY 表示未接管任务，Pool 不得在返回后继续引用 TaskInvocation、argv 或其字符串。
4. ERROR 表示未接管任务。
5. Pool 成功接收后，必须保证任务最终能被内部消费者发现。
6. Pool 不要求本模块额外调用 wake_one。

### 5.3 Pool 静态 Function 配置注册

静态 Function 配置在模块启动阶段完成，早于 event_trigger_notify 开放。

每个 Function 配置包含 so_name、func_name、resource 和 execution。配置关联到 so_name + func_name：
- so_name 用于 dlopen；相同 so_name 的动态库 Handle 可以复用。
- func_name 用于 dlsym；同一个 SO 可以导出多个不同函数。
- resource / execution 绑定到 Function，不默认认为同一 SO 的所有函数资源需求相同。
- func_name 在当前 App 内唯一；同一 so_name + func_name 被多个 App 复用时配置必须一致。

静态注册失败则模块初始化失败，不进入运行态。该启动阶段配置导入不增加运行期 Pool Adapter 回调。

### 5.4 Pool 消费与唤醒责任

- Pool 负责队列消费者、协程创建、等待、唤醒和任务完成。
- Pool 根据 TaskInvocation.so_name 定位 SO，调用 dlopen。
- Pool 在该 SO Handle 上根据 TaskInvocation.func_name 调用 dlsym。
- Pool 按统一 Function ABI 构造 TaskContext 并调用函数入口。
- Pool 不负责释放 data_addr 指向的上游数据内存。

## 6. Function 执行 ABI

### 6.1 Function 入口

不再固定要求每个 SO 导出 handler。每个 Function 以 func_name 作为实际符号入口，统一遵循以下 ABI：

~~~c
typedef struct {
    const char *key;
    const void *data_addr;
    size_t data_size;
} pm_task_argument_t;

typedef struct {
    const char *session_id;
    pm_input_mode_t input_mode;
    size_t argc;
    const pm_task_argument_t *argv;
} pm_task_context_t;

typedef int (*pm_function_entry_t)(
    const pm_task_context_t *ctx
);
~~~

示例 SO：

~~~c
#ifdef __cplusplus
extern "C" {
#endif

int crop_image(const pm_task_context_t *ctx);
int resize_image(const pm_task_context_t *ctx);

#ifdef __cplusplus
}
#endif
~~~

Pool 执行步骤：

1. 根据 so_name 定位 /dev/shm/<so_name>。
2. dlopen 加载 SO。
3. dlsym(handle, func_name) 获取目标函数入口。
4. 将 TaskInvocation 的 session_id、input_mode、argc、argv 组织为 TaskContext。
5. 调用函数入口。
6. 函数返回后，TaskContext 和参数描述符视图不再有效；data_addr 指向的数据仍由上游按 Session 生命周期管理。

### 6.2 Object API 与来源函数注入

Function 通过 Object API 写入输出数据。Object SDK 在调用 event_trigger_notify 时，从当前 TaskContext 取得当前正在执行的 func_name，作为 source_func_name 传入。

外部 SMC Actor 不属于已注册 Function，可传 NULL。

## 7. 典型调用流程与示例

### 7.1 启动期

1. 模块内部读取 app.json。
2. JSON Parser 校验 Function、Bucket、DIRECT、Trigger 和资源配置。
3. 构建内部 Registry。
4. 将 FunctionRuntimeConfig[] 交付 Pool 静态注册机制。
5. Pool 完成 SO / 符号校验和静态配置准备。
6. Registry 发布为只读运行态，开放 event_trigger_notify。

### 7.2 运行期：上游通知一次 Commit

~~~c
pm_data_ready_event_t event = {
    .bucket = "b_input",
    .key = "image_001",
    .session_id = "session_1001"
};

const void *data_addr = committed_object_addr;
size_t data_size = committed_object_size;

pm_status_t rc = event_trigger_notify(
    &event,
    NULL,
    data_addr,
    data_size
);
~~~

Function 输出对象时，第二个参数传入当前 TaskContext 的 func_name；外部 Actor 可传 NULL。

### 7.3 运行期：Pool 接收任务

Task Builder 构造：

~~~text
TaskInvocation
    session_id = session_1001
    so_name = image_process.so
    func_name = crop_image
    input_mode = PM_INPUT_VALUE
    argc = 1
    argv[0]:
        key = image_001
        data_addr = committed_object_addr
        data_size = committed_object_size
~~~

Task Router 先检查资源，再调用 try_enqueue。Pool 接收后通过 dlopen / dlsym 调用 crop_image。

### 7.4 端到端时序

~~~mermaid
sequenceDiagram
    participant SDK as Data Bucket SDK
    participant ET as Event Trigger
    participant TB as Task Builder
    participant RT as Task Router
    participant Pool as Task Coroutine Pool
    participant Fn as Function

    SDK->>ET: event_trigger_notify(event, source_func_name, data_addr, data_size)
    ET->>ET: Bucket 定位 / DIRECT 判断 / Trigger 匹配
    ET->>TB: TaskAction + EventDataView
    TB->>TB: 构建 TaskInvocation.arguments[]
    TB->>RT: TaskInvocation
    RT->>RT: 查询 Function CPU / Memory 需求
    RT->>RT: 查询当前可用资源
    alt 资源不足
        RT->>RT: RESOURCE_INSUFFICIENT TODO；不调用 Pool
    else 资源满足
        RT->>Pool: try_enqueue(TaskInvocation)
        alt ACCEPTED
            Pool->>Pool: 入队并由内部协程消费
            Pool->>Fn: dlopen(so_name) / dlsym(func_name) / invoke(ctx)
        else NO_CAPACITY
            RT->>RT: Delay Queue 或终止
        else ERROR
            RT->>RT: 记录内部错误并终止
        end
    end
~~~

## 8. 内存所有权与生命周期契约

| 对象 | 创建方 | 使用方 | 释放方 / 有效期 |
|---|---|---|---|
| DataReadyEvent | 上游 SDK | event_trigger_notify | 上游保证至少在 notify 调用期间有效 |
| source_func_name | 上游 SDK / TaskContext | DIRECT 匹配 | 上游保证至少在 notify 调用期间有效 |
| key 字符串 | 上游 SDK | Task Builder / Pool / Function | Task Builder 复制；Pool 复制任务描述符；随任务结束释放元数据副本 |
| TaskInvocation / argv 描述符 | Task Builder | Router / Pool | Router 或 Pool 按入队结果管理描述符内存 |
| data_addr 指向的数据 | 上游 Data SDK | Task Builder / Pool / Function | 上游在 Session 结束且所有相关任务完成或终止后回收 |

不可违反的规则：

1. data_addr 是借用地址，不发生所有权转移。
2. Scheduler 和 Pool 不得释放 data_addr。
3. Task Builder 不复制数据内容，只构建参数描述符。
4. 一个事件命中多个 Task 时，所有 Task 都可能访问同一 data_addr。
5. 上游必须将 Delay Queue 中的待提交任务也视为未完成任务。
6. Session 数据回收必须发生在该 Session 所有相关任务完成或终止之后。
7. 同一 Session 中已提交的数据在相关任务结束前不得被原地覆盖或复用。

## 9. 并发、重入与调用顺序

- Registry 初始化后只读。
- event_trigger_notify 可被多个上游线程并发调用。
- Task Builder 不得把调用方的临时字符串指针直接放入异步队列。
- Task Router 和 Delay Queue 必须线程安全。
- try_enqueue 必须原子完成队列准入和入队。
- 同一数据地址被多个任务共享时，上游负责保证并发读期间地址稳定。
- 模块关闭前停止接收新通知，等待在途通知和 Router PendingTask 进入终态；Pool 已接收任务按 Pool 的关闭契约完成或终止。

## 10. 上下游责任边界与联调验收

### 10.1 本模块负责

- 内部 app.json 加载和 JSON 解析。
- Function / Bucket / DIRECT / Trigger 索引。
- event_trigger_notify。
- Task Builder.arguments[]。
- CPU / Memory 资源预检查。
- try_enqueue 调用与 Delay Queue。

### 10.2 上游 Data Bucket SDK 负责

- Commit 成功后调用通知 API。
- 传递 bucket、key、session_id、source_func_name、data_addr、data_size。
- 保证数据地址在 Session 相关任务完成或终止前有效。
- Session 结束后回收数据。
- Function 输出对象时注入当前 func_name。

### 10.3 下游 Task Coroutine Pool 负责

- 启动阶段接收 FunctionRuntimeConfig[]。
- 运行期提供唯一 try_enqueue 回调。
- 原子入队、队列消费和协程唤醒。
- dlopen(so_name)、dlsym(func_name) 和 Function ABI 调用。
- 复制任务描述符和字符串，不复制、不释放上游数据内容。

### 10.4 联调验收清单

- A 组对上游仅暴露 event_trigger_notify。
- DataReadyEvent 只有 bucket、key、session_id。
- source_func_name 是独立参数，外部 Actor 可为 NULL。
- data_addr / data_size 与事件一起传入。
- 不存在 DataRef Adapter 或 DataRef 相关 API。
- func_name 在当前 App 内唯一，DIRECT 仅按 func_name 匹配。
- SO 加载与函数定位分别使用 dlopen / dlsym。
- TaskInvocation 携带 arguments[]，当前 argc=1。
- Pool Adapter 只有 try_enqueue。
- Task Router 在 try_enqueue 前执行 CPU / Memory 资源预检查。
- 资源不足不调用 try_enqueue，走 TODO 分支。
- Pool NO_CAPACITY 与资源不足分开处理。
- Session 生命周期覆盖所有派生任务。
