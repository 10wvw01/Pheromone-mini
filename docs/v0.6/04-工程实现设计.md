### 12.2 模块依赖规则

- config 只负责 JSON 解析和配置对象，不依赖运行期 Trigger / Router。
- registry 依赖 config，负责索引构建和只读查询。
- direct_dependency 与 event_trigger 只读取 Registry 索引。
- task_builder 依赖 TaskAction、事件数据视图和 Function Index，不调用 Data SDK。
- task_router 依赖 Function resource 配置、Resource Probe、Pool Adapter 和 Delay Queue。
- Resource Probe 不依赖 Trigger 或 Task Builder。
- Pool 内部实现不进入本模块；本模块只依赖 try_enqueue 回调契约。

### 12.3 C 语言规范

- 对外结构体使用固定宽度整数或 size_t，明确指针借用与生命周期。
- 对异步任务需要持有的字符串进行深拷贝。
- data_addr 只作为借用指针传递，不执行 free、munmap 或 DataRef 操作。
- 函数指针通过统一 ABI 定义；SO 中导出函数使用 extern "C" 避免 C++ 符号改编。
- 所有数组显式携带 count；检查整数溢出和空指针。
- Registry 发布后只读；所有运行期索引查询不修改配置。

## 第 13 章 并发、生命周期与可靠性

### 13.1 内部 Registry 发布

1. 启动时读取 app.json。
2. 在临时对象中完成 JSON 解析和字段校验。
3. 建立 Function、Bucket、DIRECT、Trigger 索引。
4. 将 FunctionRuntimeConfig[] 交付 Pool 启动期注册机制。
5. Pool 静态配置准备成功后，原子发布 Registry。
6. 任一步骤失败则初始化失败，不允许开放 event_trigger_notify。

Registry 是单进程单实例，不提供外部 create / register / seal / destroy API。

### 13.2 Function 与索引唯一性

- func_name 在当前 App 内唯一。
- so_name 可以被同一 App 的多个 Function 共享。
- Function 记录以 so_name + func_name 作为执行入口组合标识。
- DIRECT 索引以当前 App + source_func_name 为键，目标为 func_name 列表。
- Bucket 在当前 Registry 所有 App 之间全局唯一。
- Trigger 目标引用 func_name，不引用 so_name。

### 13.3 event_trigger_notify 并发

DataReadyEvent 和 source_func_name 是只读借用视图，至少在 notify 调用期间有效。Task Builder 必须复制后续异步任务所需的 key、session_id 等字符串。

data_addr 不复制、不释放。上游必须保证数据地址在 Session 结束且该 Session 产生的所有任务（包括 Delay Queue 项）完成或终止之前有效。

多个 Task 可能同时读取同一 data_addr；上游保证数据在此期间不可变或至少满足并发读取安全要求。

### 13.4 TaskInvocation 元数据生命周期

TaskInvocation 的描述符、argv 数组和字符串元数据必须拥有明确所有者：

- Task Builder 构建阶段：创建任务描述符和字符串副本。
- Task Router 持有阶段：Router 拥有任务描述符；data_addr 仍为借用。
- try_enqueue = ACCEPTED：Pool 在返回前复制其后续执行所需的描述符和字符串；Router 可释放自己的元数据副本。
- try_enqueue = NO_CAPACITY / ERROR：Pool 不保留任何 TaskInvocation、argv 或字符串指针；Router 继续持有或终止任务。
- Delay Queue：Router 持有元数据副本，并继续借用 data_addr。
- 任务完成或终止：Pool / Router 释放各自拥有的元数据；数据内存由上游按 Session 规则回收。

### 13.5 Session 数据生命周期

Session 是上游数据地址的生命周期边界：
- Session 内数据在所有派生任务终态前保持有效。
- 任务终态包括 Pool 执行完成、执行失败、被取消，以及 Router Delay Queue 超时或明确终止。
- 多目标 DIRECT 或多 Trigger 可能产生多个并发 Task；上游必须覆盖全部任务。
- Scheduler 不实现 retain / release，不维护 DataRef 引用计数。
- 若上游无法获知所有派生任务是否终态，联调时必须由上下游现有 Session / Task 生命周期机制提供完成确认；不得通过复活 DataRef 引入第二套所有权体系。

## 第 14 章 Task Router 与 Delay Queue 实现

### 14.1 资源预检查原则

Task Router 在调用 try_enqueue 之前执行 CPU / Memory 资源预检查：

1. 根据 so_name + func_name 查询 Function 静态资源需求。
2. 获取当前进程可见的 CPU / Memory 限额与使用量。
3. 比较可用资源是否满足该 Function 的 cpu_cores、memory_mb。
4. 不满足时不调用 try_enqueue，记录 RESOURCE_INSUFFICIENT，预留上报 TODO。
5. 满足时调用 Pool try_enqueue。

资源预检查是快照判断，不是资源预留。Pool 的 try_enqueue 仍然负责队列容量和原子入队。

### 14.2 Linux 资源信息读取

建议优先按以下顺序读取：

- 通过 /proc/self/cgroup 获取当前进程所属 cgroup。
- cgroup v2：读取 cpu.max、cpu.stat、memory.max、memory.current。
- cgroup v1：读取 CPU quota / period、CPU accounting、memory limit / usage 对应文件。
- /proc/meminfo：读取宿主机 MemTotal / MemAvailable，作为宿主机参考或 cgroup 信息不可用时的兜底。
- CPU 可用配额与使用量应结合 cgroup CPU quota 和 accounting 计算；不能仅把宿主机逻辑 CPU 数当作容器可用 CPU。

资源探测结果建议抽象为：

~~~c
typedef struct {
    double cpu_limit_cores;
    double cpu_used_cores;
    double cpu_available_cores;
    uint64_t memory_limit_bytes;
    uint64_t memory_used_bytes;
    uint64_t memory_available_bytes;
    uint8_t source_is_cgroup;
} pm_resource_snapshot_t;
~~~

### 14.3 资源不足与队列无容量分离

| 状态 | 发生阶段 | 是否调用 try_enqueue | 处理 |
|---|---|---:|---|
| CPU / Memory 资源不足 | Pool 入队前 | 否 | RESOURCE_INSUFFICIENT 上报 TODO |
| Pool NO_CAPACITY | Pool 原子入队时 | 是 | 按 Delay Queue 策略暂存或终止 |
| Pool ERROR | Pool 原子入队时 | 是 | 记录错误并终止 |

资源不足不进入 Delay Queue；Delay Queue 只负责重试 Pool 队列容量不足。

### 14.4 Delay Queue 数据结构

~~~c
typedef struct {
    pm_task_invocation_t task;
    uint64_t first_enqueue_ms;
    uint64_t next_retry_ms;
    uint64_t deadline_ms;
} pm_router_pending_task_t;
~~~

Router PendingTask 拥有 TaskInvocation 的描述符和字符串副本，但不拥有 data_addr 指向的数据内存。Delay Queue 的最长等待时间不得超过上游保证的数据地址有效期。

### 14.5 延时调度状态机

~~~mermaid
stateDiagram-v2
    [*] --> ResourceCheck
    ResourceCheck --> ResourceInsufficient: CPU / Memory 不足
    ResourceCheck --> TryEnqueue: 资源满足
    ResourceInsufficient --> [*]: 上报 TODO / 终止
    TryEnqueue --> PoolOwned: ACCEPTED
    TryEnqueue --> DelayPending: NO_CAPACITY 且 Delay enabled
    TryEnqueue --> Rejected: NO_CAPACITY 且 Delay disabled
    TryEnqueue --> Failed: ERROR
    DelayPending --> TryEnqueue: 到达 retry_interval
    DelayPending --> Expired: 达到 max_wait
    PoolOwned --> [*]
    Rejected --> [*]
    Failed --> [*]
    Expired --> [*]
~~~

### 14.6 退出清理

模块关闭时停止接收新事件；Router 停止接受新 Task；Delay Queue 中未提交任务按关闭策略取消并释放 Router 自有元数据；Pool 已接收任务由 Pool 按其关闭契约清理。任何一方都不得释放上游 data_addr。

## 第 15 章 错误处理、日志与性能

### 15.1 错误分层

- API 参数错误：返回 PM_ERR_INVALID_ARGUMENT。
- JSON / Registry 初始化错误：阻止模块进入运行态，详细原因写初始化日志。
- 资源不足：不调用 try_enqueue，记录 RESOURCE_INSUFFICIENT，具体上报 TODO。
- Pool 队列无容量：根据 Delay Queue 策略处理。
- Pool 内部错误：记录并终止当前任务。
- 无 Trigger 命中：正常处理，不作为错误。

### 15.2 结构化日志字段

建议字段：trace_seq、app_name（仅内部日志）、bucket、key、session_id、source_func_name、so_name、func_name、route_path（DIRECT / BUCKET_TRIGGER）、trigger_name（仅内部日志）、input_mode、argc、resource_check、cpu_available、memory_available、pool_result、delay_state、elapsed_ms、dispatched。

上述内部诊断字段不因此进入 DataReadyEvent 或 TaskInvocation 公共 ABI。

### 15.3 性能原则

- JSON 只在启动期解析一次。
- Registry 索引运行期只读。
- Event Trigger 只按 Bucket 索引查找候选规则。
- DIRECT 只按 source_func_name 索引查找目标。
- Task Builder 只构建参数描述符，不复制数据内容。
- 资源查询尽量使用轻量快照；需要明确采样间隔和缓存策略，避免每个事件执行高开销完整扫描。
- try_enqueue 必须一次调用完成原子队列准入和入队。

## 第 16 章 编译、构建与交付

### 16.1 构建目标

- C11 静态库或共享库。
- JSON Parser / Registry 单元测试。
- Event Trigger / DIRECT 单元测试。
- Task Builder / Task Router 单元测试。

### 16.2 编译要求

- Linux 环境。
- C11 编译器。
- 线程库支持。
- JSON 解析库由工程统一选型。
- Resource Probe 仅依赖 Linux procfs / cgroup 文件接口。

### 16.3 实现顺序

1. JSON Parser、配置校验和内部 Registry。
2. Event Trigger：Immediate / ByName / DIRECT。
3. Task Builder：arguments[] 和元数据复制。
4. Task Router：CPU / Memory 预检查、try_enqueue、Delay Queue。
5. 与真实 Task Coroutine Pool 联调。

本期优先完成 JSON Parser、Event Trigger、Task Router 三个模块；Task Builder 作为轻量内部组件随链路实现。
