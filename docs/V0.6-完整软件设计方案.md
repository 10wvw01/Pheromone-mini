# Pheromone-mini V0.6 完整软件设计方案

**版本：** V0.6  
**修订日期：** 2026-11-26  
**状态：** 第二步设计文档修订基线  
**实现语言：** C11  
**前序版本：** V0.5

## 1. V0.6 核心结论

V0.6 以 Pheromone 的两级调度、Data Bucket 和 Trigger 设计为基础，在当前项目范围内实现单节点、单进程、单调度实例的数据驱动任务触发与本地任务分发。

本模块负责业务流程③④⑤：

1. 接收上游 Data SDK 的数据就绪通知。
2. 根据 DIRECT 独立依赖或 Bucket Trigger 规则判断目标函数。
3. 根据本次事件携带的数据地址构建函数参数列表。
4. Task Router 检查目标 Function 的 CPU / Memory 资源需求。
5. 资源满足时调用下游 Task Coroutine Pool 的原子 try_enqueue；资源不足时进入独立上报分支（本期 TODO）。

本次修订严格执行第一阶段已确认的设计基线：删除 DataRef 和数据载体类型区分；数据地址由上游随通知直接传入；Function 由 so_name 与 func_name 两个独立字段标识；DIRECT 只按 func_name 匹配。

## 2. 冻结设计基线

| 维度 | V0.6 冻结规则 |
|---|---|
| 调度实例 | 单进程、单个调度实例；Registry 是模块内部唯一运行实例 |
| 配置 | 模块内部加载 app.json，完成解析、校验、索引构建和静态 Function 配置准备 |
| 对上游 API | 只暴露 event_trigger_notify；不暴露 Registry 创建、注册、封存和销毁接口 |
| Bucket | 在当前调度实例管理的全部 App 范围内全局唯一；事件不携带 app_name |
| Function 标识 | so_name 表示动态库文件名；func_name 表示库内函数符号 |
| Function 唯一性 | func_name 在当前 App 内全局唯一；不同 App 可存在同名 func_name |
| SO 加载 | 下游根据 so_name 定位 .so 并执行 dlopen |
| 函数定位 | 下游在对应 SO Handle 上根据 func_name 执行 dlsym |
| Function 配置 | 每个 Function 配置分别包含 so_name、func_name、resource、execution；同一 SO 可导出多个函数 |
| DIRECT | 独立依赖路径；source_func_name → target func_name[]；不增加 source_so_name |
| Trigger | 仅 Immediate、ByName 两种 Bucket Trigger |
| 多 Trigger | 一个 Bucket 可关联多条 Trigger；逐条匹配，逐条生成任务 |
| DIRECT 优先级 | source_func_name 存在 DIRECT 目标时走 DIRECT 路径，本次事件不再执行 Bucket Trigger 匹配；否则执行 Bucket Trigger 匹配 |
| DataReadyEvent | 仅 bucket、key、session_id |
| 通知参数 | source_func_name、data_addr、data_size 作为 event_trigger_notify 的独立参数 |
| 数据传递 | 统一通过 data_addr + data_size 传递；不区分大小数据包 |
| Task 输入 | key 必须；采用 arguments[]；当前一次事件构建一个参数，argc=1 |
| 输入模式 | 保留 trigger_option：0=Value、1=Key+Value、2=Key Only；DIRECT 固定 Value |
| 数据生命周期 | 上游持有数据；Session 结束且所有相关任务完成或终止后，上游回收 |
| DataRef | 完全删除；不实现 validate / retain / release |
| Pool Adapter | 运行期 Adapter 只包含 try_enqueue |
| 静态 Function 注册 | 启动期单独完成，不放入运行期 Pool Adapter |
| 资源准入 | Task Router 在 try_enqueue 前检查目标 Function 的 CPU / Memory 资源 |
| 资源不足 | 不调用 try_enqueue；独立资源不足上报分支，本期 TODO |
| 队列无容量 | Pool 返回 NO_CAPACITY 后按进程级 Delay Queue 策略处理 |
| 协程调度 | Pool 内部负责队列消费和协程唤醒；本模块不调用 wake_one |
| 延时调度 | 保留进程级全局 Delay Queue；多 App 的配置必须一致 |
| 研发范围 | 单节点、单进程；不实现进程间、节点间分发 |

## 3. 核心模块

1. **App Registry / JSON Parser**：模块内部加载 app.json，解析并校验 App、Function、Bucket、DIRECT Dependency、Trigger 和资源配置，建立只读索引。
2. **DIRECT Dependency**：根据事件的 source_func_name 查询当前 App 的 DIRECT 目标函数，独立生成任务。
3. **Event Trigger**：根据 Bucket 索引匹配 Immediate / ByName Trigger。
4. **Task Builder**：将命中结果和事件数据视图组装为 TaskInvocation.arguments[]；复制异步任务需要持有的字符串元数据，不复制数据内容。
5. **Task Router**：查询 CPU / Memory 可用资源，资源满足后调用 try_enqueue；处理 Pool 容量不足和 Delay Queue。
6. **Task Coroutine Pool（下游）**：提供 try_enqueue，管理任务队列、协程消费、SO 加载、函数定位和函数执行。

## 4. 总体执行路径

~~~mermaid
flowchart TD
    A["上游 Data SDK：数据 Commit 成功"] --> B["event_trigger_notify"]
    B --> C["DataReadyEvent：bucket / key / session_id"]
    B --> D["source_func_name + data_addr + data_size"]
    C --> E["内部 Registry：Bucket -> App"]
    D --> F["DIRECT Dependency 判断"]
    E --> F
    F -->|存在 DIRECT 目标| G["DIRECT：source_func_name -> target func_name[]"]
    F -->|无 DIRECT 目标或来源为空| H["Event Trigger：Immediate / ByName"]
    G --> I["Task Builder：构建 arguments[]"]
    H --> I
    I --> J["Task Router：查询 Function 静态资源需求"]
    J --> K["查询 CPU / Memory 可用资源"]
    K --> L{"资源是否满足？"}
    L -->|否| M["资源不足上报分支（TODO）；不调用 try_enqueue"]
    L -->|是| N["task_pool_try_enqueue"]
    N -->|ACCEPTED| O["Task Coroutine Pool"]
    N -->|NO_CAPACITY| P{"Delay Queue 启用？"}
    P -->|是| Q["Delay Queue：到期重试"]
    Q --> J
    P -->|否或超时| R["记录拒绝 / 超时并终止任务"]
    O --> S["Pool 消费队列、唤醒协程"]
    S --> T["dlopen(so_name) -> dlsym(func_name) -> 执行"]
~~~

DIRECT 和 Bucket Trigger 是两条独立路径，不把 DIRECT 伪装成第三种 Trigger Primitive。资源不足与队列无容量是两个不同状态：前者在调用 Pool 前拦截，后者由 Pool 的原子 try_enqueue 返回。

## 5. 上下游接口

### 5.1 提供给上游 Data Bucket SDK

唯一对上游公开的运行期 API 是 event_trigger_notify。

DataReadyEvent 仅包含 bucket、key、session_id。source_func_name、data_addr、data_size 作为独立参数传入。上游不需要传 app_name、trigger_name、target_function、payload_type 或 DataRef。

外部 SMC Actor 写入时 source_func_name 可以为 NULL；Function 通过 Object API 写入数据时，由上游 SDK 从当前 TaskContext 注入当前 func_name。

### 5.2 对下游 Task Coroutine Pool 的要求

运行期 Pool Adapter 只包含 try_enqueue。try_enqueue 接收完整 TaskInvocation，其中包含 session_id、so_name、func_name、input_mode、argc 和 argv。

静态 Function 配置在启动阶段单独注册，不作为运行期 Adapter 回调。配置项按 Function 记录 so_name、func_name、resource 和 execution。

Pool 根据 so_name 加载动态库，根据 func_name 定位函数符号；不再固定要求导出 handler。

## 6. 关键数据与生命周期

- TaskArgument 包含 key、data_addr、data_size；key 必须存在。
- 当前一次 event_trigger_notify 对应一个数据对象，Task Builder 为每个命中目标构建独立 TaskInvocation，当前 argc=1。
- Task Builder 复制 key、session_id 等异步任务需要持有的字符串；不复制 data_addr 指向的数据内容。
- data_addr 是借用地址，不发生所有权转移；调度模块和 Pool 均不得释放该地址。
- 上游必须保证 data_addr 在 Session 生命周期内有效，且在该 Session 派生的所有任务（包括 Delay Queue 中的待提交任务）完成或终止前，不得释放或复用该数据区域。
- Session 结束且相关任务全部完成或终止后，由上游 Data SDK 回收数据。
- 如果一个事件命中多个 DIRECT 目标或多条 Trigger，所有任务都使用同一事件数据地址；上游必须等待全部相关任务结束后再回收。
- 不引入 DataRef、引用计数或 Scheduler 对 Data SDK 的主动查询。

## 7. 资源准入与 Delay Queue

Task Router 在每次调用 try_enqueue 前，先通过 Function Registry 获取该目标 Function 的 resource 配置，再查询当前节点 CPU / Memory 可用资源。

资源查询优先识别当前进程的 cgroup 限额与使用量：通过 /proc/self/cgroup 定位 cgroup，再读取 cgroup v2 或 v1 对应的 CPU / Memory 限额和使用统计；宿主机内存信息可从 /proc/meminfo 读取作为参考或兜底。资源判断是准入快照，不构成资源预留。

- 资源不足：不调用 try_enqueue，进入 RESOURCE_INSUFFICIENT 上报分支；本期仅预留 TODO，不进入 Delay Queue。
- 资源满足：调用 try_enqueue。
- Pool 返回 NO_CAPACITY：这是队列容量不足，不等同于 CPU / Memory 资源不足；按 Delay Queue 配置暂存并重试。
- Pool 返回 ACCEPTED：Pool 接管 TaskInvocation 元数据副本并负责后续执行。
- Pool 返回 ERROR：终止当前任务并记录内部错误。

## 8. 本期明确不实现

- DataRef、validate、retain、release 和 DataRef Adapter。
- INLINE / SHARED_MEMORY 两种载体及大小阈值选择。
- Scheduler 主动调用 Data SDK 查询数据。
- Rerun、自动重新执行、执行超时和 resource.timeout_ms。
- wake_one 或任何由本模块发起的协程唤醒操作。
- BySet、ByBatchSize、ByTime、DynamicGroup、Redundant 等其他 Trigger Primitive。
- Node Scheduler、Process Scheduler、Warm / Cold Executor、跨进程和跨节点分发。
- Data Bucket 创建/销毁、共享内存池、对象索引和底层数据搬运。
- Task Coroutine Pool、TaskQueue、工作协程、SO Loader 和函数执行实现。
- 动态 Trigger 更新、Exactly-once、事件持久化和事件去重。
