## 2. 阻塞最终冻结的问题

严重度：P1 为实现或协作契约缺口；P2 为一致性和可追踪性缺口。共 4 个 P1、2 个 P2。另有 1 项配置决策待核实。

### FDR-01 / P1：Session 回收条件缺少可执行的完成判定契约

位置：[04 §13.5](../04-工程实现设计.md#135-session-数据生命周期责任边界)、[03 §11.5–11.7](../03-接口与协作设计.md#115-内存所有权与生命周期契约)、附录 C §C.7。

文档要求上游等所有派生任务终态后回收共享内存，同时假定存在“既有 Session / Task 生命周期机制”。本基线未定义或引用该机制。EventTriggerNotify 只返回 error，TryEnqueue 只返回即时结果；上游无法从这些接口获知多目标展开数量、Router 资源拒绝、延时超时以及 Pool 执行终态。

例：一次事件派生两个目标，一个被 Pool 接收，另一个仍在 Delay Queue。若上游只观察 Pool 在途任务数，可能在延时任务提交前回收地址；若永不回收则可能永久占用内存。这是现有契约无法证明安全的风险，并非已观测到的实现故障。

修订要求：明确 Session 的关闭条件、任务派生登记与终态登记责任、Router 到 Pool 的责任交接，以及运行中任务继续产生事件时的判定顺序。可对接既有内部生命周期设施，但必须给出具体设施和契约；不要直接增加第三个上游业务 API，也不需要恢复 DataRef。

复审证据：多目标、Delay Pending、资源拒绝、Pool Error、延时超时、执行失败、关闭清理均能计入同一完成判定；最后一个派生任务终态前不得回收。

### FDR-02 / P1：Delay Queue 重试绕过资源复查

位置：[04 §14.5](../04-工程实现设计.md#145-延时调度状态机)，与主文档 §4、§7 及需求 RTE-02 对照。

状态机明确写为 DelayPending → TryEnqueue，而主流程返回资源查询。任务首次检查通过后可能等待较长时间；等待期间 CPU / Memory 可能变化，直接重试会绕过“每次 TryEnqueue 前检查资源”的约束。

修订要求：重试统一返回 ResourceCheck；先检查 deadline，未过期才执行资源检查及可能的 TryEnqueue。重试时资源不足也按既定规则终止并记录，不重新进入 Delay Queue。首次 NoCapacity 建立的 deadline 不得因重试重置；重试与超时同时满足时优先终止过期任务。

复审证据：首次资源充足且 NoCapacity，重试时资源不足，应不调用第二次 TryEnqueue；截止时间到达时不得再次提交。

### FDR-03 / P1：Resource Probe 尚未定义可复现的准入计算

位置：[02 §9.2](../02-核心模块详细设计.md#92-功能点-rte-02cpu--memory-可用资源预检查)、[04 §14.2](../04-工程实现设计.md#142-linux-资源信息读取)、TEST-RTE-04–06。

文档列出 CPU / Memory 文件和 ResourceSnapshot，但没有定义 CPU 使用量采样窗口、首次采样行为、CPUAvailableCores 计算、无配额或受 CPU 亲和性限制时的处理、内存单位，以及探测失败的决策。当前“正确读取”不足以形成唯一的验收预期。

修订要求：冻结单位、有效限额与可用量计算、采样周期及缓存有效期、无限额处理、读取失败与兜底策略；给出输入快照到准入结论的示例。继续明确这只是资源快照预检查，不承诺资源预留或并发任务资源总量硬保证。

复审证据：相同探测样本必得相同结论，覆盖首次采样、有限额、无限额、部分文件不可读、memory 边界和并发快照。无需扩大本期调度范围。

### FDR-04 / P1：Pool 依赖装配只写了结论，没有可接线的方案

位置：[03 §10.7.1](../03-接口与协作设计.md#1071-pool-api-001tryenqueue)、[04 §12.1–12.2](../04-工程实现设计.md#121-目录建议)、examples/task_scheduler.go。

文档说“内部依赖装配时绑定”，但当前两个上游函数均没有 Pool 参数，示例只有 TaskPool 类型，没有说明谁创建真实 Pool、何时绑定、调度模块如何得到该实例，以及未绑定时初始化是否失败。上游和下游团队仍需自行猜测集成入口。

修订要求：给出一个具体的内部组合根 / adapter 装配示例，说明单实例的创建顺序、依赖方向、错误行为和测试替身替换方式。保持两个上游业务 API 和一个下游 TryEnqueue，不恢复静态 Function 注册，不把内部装配变成第三个客户 API。

复审证据：启动伪代码能从真实 Pool 实例连接到 TriggerInit、EventTriggerNotify 和 Router；未装配依赖不能进入可接收业务事件的状态。

### FDR-05 / P2：API 编号未重排，功能需求 ID 与详细设计语义错位

位置：[03 §10.4.1](../03-接口与协作设计.md#1041-a-组本模块提供给上游的-api)、02 §5.1–5.5、06 §3。

两个 API 仍使用 PM-API-005 / PM-API-004，正文还明确保留旧编号，直接违背编号连续重排要求。此外，详细设计 APP-02 表示 Bucket 全局唯一，需求列表 APP-02 表示加载 function.json；详细设计 APP-03 表示 Function 双标识，需求列表 APP-03 表示 Bucket 全局唯一。同一 ID 无法唯一定位同一能力。

修订要求：上游 API 连续重排为 PM-API-001 / 002，并同步规格标题及引用。为功能需求指定唯一 ID 来源，将详细设计的小节标注与 06 需求列表、05 测试映射逐项对齐，不强行将多个不同能力合为一个 ID。

复审证据：章节连续、API 连续；每个需求 ID 在所有文档中语义一致；测试追踪覆盖一对多映射。

### FDR-06 / P2：初始化与运行切换没有确定的状态规则

位置：[02 §5.1](../02-核心模块详细设计.md#51-功能点-app-01triggerinit-加载-appjson)、[03 §11.6](../03-接口与协作设计.md#116-并发重入与调用顺序)、04 §13.1。

文档允许多次 TriggerInit，又规定“事件处理开始后不再接受新配置”，但没有定义谁触发状态切换、失败通知是否算开始、并发初始化与首个通知如何裁决，以及运行期再次 TriggerInit 的错误行为。现有描述可以作为调用顺序约束，但尚未形成确定的实现规则。

修订要求：定义内部初始化 / 运行状态和切换点、失败初始化的影响、运行期初始化拒绝规则；若并发初始化属于调用方禁止行为，应明确写出。保持现有两个上游 API，无需恢复 seal API。

复审证据：多 App 初始化成功、第二个 App 初始化失败不损坏已有配置、首个通知与初始化的合法顺序、运行期再初始化拒绝均有明确预期。

## 3. 配置组织决策需要核实

当前分支将 functions[].config_path 和单 Function 一份 function.json 写成冻结规则；此前讨论出现过“仅 app.json”以及“保留 app.json / function.json”两种阶段性方案。最近明确确认的是 TriggerInit 接收 app.json 文件路径，这本身不足以推导出必须采用 config_path 多文件组织。

因此，本次不擅自把其中一个阶段性方案当成最新确认，也不将多文件方案直接判定为代码错误。最终冻结前需明确配置组织的最新决定，并同步主文档、附录 B、示例和验收：若仅 app.json，则内嵌 Function 配置；若保留 function.json，则确认现有引用结构。该决定不影响 TriggerInit 的路径入参。
