# 第二部分：核心模块详细设计

[返回 V0.6 主文档](../V0.6-完整软件设计方案.md)

本部分描述 App Registry / JSON Parser、DIRECT Dependency、Event Trigger、Task Builder 和 Task Router 的职责、数据结构、处理流程和验收规则。所有运行期模块使用同一个内部 Registry；不向上游暴露 Registry 生命周期接口。

## 第 4 章 核心模块总结构

### 4.1 模块划分

| 核心模块 | 内部功能点 | 输入 | 输出 |
|---|---|---|---|
| App Registry / JSON Parser | JSON 解析、字段校验、全局索引、Function 静态配置 | app.json | 只读 App / Function / Bucket / Dependency / Trigger 索引 |
| DIRECT Dependency | 来源函数查询、目标函数展开、DIRECT 优先级 | source_func_name + 当前 App | 一个或多个 DIRECT TaskAction |
| Event Trigger | Bucket 查询、Immediate、ByName、多规则匹配 | DataReadyEvent | 一个或多个 Trigger TaskAction |
| Task Builder | input_mode 转换、arguments[] 构建、异步元数据复制 | TaskAction + 事件数据视图 | TaskInvocation |
| Task Router | CPU / Memory 预检查、原子准入、Delay Queue、失败日志 | TaskInvocation | Pool 接收或 Router 持有的延时任务 |

### 4.2 模块依赖

~~~mermaid
flowchart LR
    A["App Registry"] --> B["DIRECT Dependency"]
    A --> C["Event Trigger"]
    B --> D["Task Builder"]
    C --> D
    A --> D
    D --> E["Task Router"]
    A --> E
    E --> F["Task Coroutine Pool Adapter"]
    E --> G["Delay Queue"]
~~~

App Registry 在启动阶段构建只读索引。运行期 DIRECT Dependency 和 Event Trigger 只查询索引，不修改配置。Task Builder 不决定路由；Task Router 不重新解析 Trigger。

### 4.3 统一运行时对象

- **DataReadyEvent：** 上游通知视图，仅包含 bucket、key、session_id。
- **EventDataView：** event_trigger_notify 的独立数据参数，包含 source_func_name、data_addr、data_size。
- **TaskAction：** 本模块内部对象，包含目标 Function 记录和 input_mode；不传给下游。
- **TaskArgument：** 一项函数输入，包含 key、data_addr、data_size。
- **TaskInvocation：** 交给 Pool 的一次函数调用描述，包含 session_id、so_name、func_name、input_mode、argc、argv。
- **RouterPendingTask：** Task Router 私有对象，包含 TaskInvocation 的自有元数据、首次入队时间和下次重试时间；data_addr 仍为借用地址，不拥有数据内存。

## 第 5 章 App Registry / JSON Parser

### 5.1 功能点 APP-01：内部加载 app.json

职责：在模块启动阶段加载 app.json，解析配置并构建唯一 Registry。JSON Parser 是 App Registry 的内部组件，不单独对上游开放。

处理步骤：

1. 读取 app.json 完整内容。
2. 解析顶层 App、Function、Bucket、Dependency、Trigger 和 Scheduler 配置。
3. 校验字段类型、必填字段、唯一性及跨对象引用。
4. 构建候选索引，不直接修改当前运行态。
5. 将 Function 静态配置按 so_name + func_name 交付 Pool 启动期静态注册机制。
6. 全部成功后一次性发布只读 Registry；任一步骤失败，模块初始化失败，不开始接收事件。

单进程单实例下不需要公开 pm_registry_create、register_app、pm_registry_seal、pm_registry_destroy 等上游 API。模块内部可以保留初始化和关闭函数，但它们不是客户对接接口。

### 5.2 功能点 APP-02：Bucket 全局唯一索引

Bucket 在当前 Registry 管理的全部 App 之间全局唯一。

索引：

~~~text
bucket_index:
    bucket_name -> AppRecord + TriggerList
~~~

收到事件后先根据 bucket 找到所属 App。DataReadyEvent 不携带 app_name，避免上游重复提供可推导信息。

校验：
- Bucket 名称非空。
- 同一个 Registry 内不得重复。
- Trigger 引用的 Bucket 必须已经声明。

### 5.3 功能点 APP-03：Function 双标识与静态配置

每个动态库 Function 配置至少包含：

~~~json
{
  "so_name": "image_process.so",
  "func_name": "crop_image",
  "resource": {
    "cpu_cores": 2,
    "memory_mb": 512
  },
  "execution": {
    "type": "coroutine",
    "priority": 0,
    "max_concurrency": 0
  }
}
~~~

字段职责：

| 字段 | 含义 | 使用方 |
|---|---|---|
| so_name | .so 文件名 | Pool 使用 dlopen 定位动态库 |
| func_name | .so 内导出的函数符号名 | Pool 使用 dlsym 定位函数；DIRECT 使用逻辑函数标识 |
| resource | 该 Function 的静态资源需求 | Task Router 资源预检查 |
| execution | 该 Function 的执行配置 | Task Coroutine Pool |

规则：

1. so_name 和 func_name 是不同概念，不能合并成 handler。
2. 一个 SO 可以导出多个 func_name。
3. func_name 在当前 App 内全局唯一；不同 App 可以使用同名 func_name。
4. DIRECT 和 Trigger 的目标引用只使用 func_name。
5. resource / execution 绑定到当前 Function 记录，即绑定到 so_name + func_name 这一对标识。
6. 同一物理 SO 可以在 Pool 中复用一次 dlopen Handle，但每个 func_name 独立 dlsym 和配置。
7. 同一 so_name + func_name 被多个 App 复用时，其 resource / execution 必须一致。
8. so_name 必须是安全文件名，不允许路径分隔符、绝对路径和路径穿越。
9. func_name 必须非空，并满足目标平台导出符号命名约束。

索引：

~~~text
function_index[app_name][func_name] -> FunctionRecord {
    so_name,
    func_name,
    resource,
    execution
}
~~~

### 5.4 功能点 APP-04：Function、DIRECT 和 Trigger 引用校验

- 每个 Function 必须同时配置 so_name 和 func_name。
- 同一 App 内 func_name 不得重复。
- DIRECT 的 src_functions / tgt_functions 必须引用当前 App 已注册的 func_name。
- Trigger 的目标 function 必须引用当前 App 已注册的 func_name。
- Bucket 必须在当前 App 的 buckets 中声明。
- 资源配置必须可用于 CPU / Memory 预检查。
- 不再校验固定 handler 符号；Pool 必须验证 dlsym(so_name Handle, func_name) 能找到入口。

### 5.5 功能点 APP-05：Pool 静态 Function 配置准备

启动阶段为每个 Function 准备静态配置：

~~~text
FunctionRuntimeConfig:
    so_name
    func_name
    resource
    execution
~~~

静态注册与运行期入队分离：
- 启动阶段将配置批量交给 Pool 的静态 Function 注册机制。
- 运行期 Pool Adapter 不包含 register_function / unregister_function。
- 运行期 Adapter 只提供 try_enqueue。
- Pool 可按 so_name 缓存 dlopen Handle，按 func_name 缓存函数入口。
- 静态配置注册失败时，模块初始化失败，不发布 Registry。

## 第 6 章 DIRECT Dependency

### 6.1 功能点 DIR-01：独立依赖索引

DIRECT 不作为 Trigger Primitive，而是独立依赖路径。

配置语义：

~~~json
{
  "type": "DIRECT",
  "src_functions": ["image_reader"],
  "tgt_functions": ["image_processor", "image_analyzer"]
}
~~~

索引：

~~~text
direct_index[app_name][source_func_name] -> target_func_name[]
~~~

DIRECT 只使用 func_name，不使用 so_name，也不引入 source_so_name。Bucket 全局索引先确定所属 App，随后在该 App 范围内查找 source_func_name。

### 6.2 功能点 DIR-02：DIRECT 优先级和目标展开

DataReadyEvent 对应 App 确定后：

1. source_func_name 为空：跳过 DIRECT，进入 Bucket Trigger。
2. source_func_name 非空：在当前 App 校验该 Function 是否存在。
3. 存在 DIRECT target_func_name[]：为每个目标函数生成一个 DIRECT TaskAction，本次事件不再执行 Bucket Trigger。
4. 没有 DIRECT 目标：进入 Bucket Trigger 匹配。
5. 一个来源对应多个目标时，每个目标生成独立 TaskInvocation。

DIRECT 和 Bucket Trigger 不合并、不去重，优先级规则保持与当前设计一致。

### 6.3 功能点 DIR-03：DIRECT 输入规则

DIRECT 依赖触发的目标函数使用 Value 输入模式。

Task Builder 使用当前事件的：
- key
- data_addr
- data_size

构建一个 TaskArgument，当前 argc=1。Key 在 TaskArgument 中始终必填；Value 模式决定 Handler 的输入视图，不改变内部 Key 必填规则。

## 第 7 章 Event Trigger

### 7.1 功能点 EVT-01：全局 Bucket 定位

Event Trigger 根据 DataReadyEvent.bucket 查询 bucket_index，取得所属 App 和该 Bucket 的有序 Trigger[]。事件不传 app_name。

### 7.2 功能点 EVT-02：Immediate 匹配

Immediate 表示该 Bucket 收到有效数据就绪事件时命中。

处理：
1. 定位 Bucket。
2. 读取该 Bucket 关联的 Immediate Trigger。
3. 每条匹配规则独立生成 TaskAction。
4. TaskAction 目标为配置的 func_name。

### 7.3 功能点 EVT-03：ByName 精确匹配

ByName 表示 Bucket 和事件 Key 同时匹配时命中。

匹配条件：

~~~text
event.bucket == trigger.bucket
AND
event.key == trigger.key_name
~~~

Key 是 Task 输入的必填字段；ByName 的 key_name 是 Trigger 的匹配条件，两者不可混淆。

### 7.4 功能点 EVT-04：同 Bucket 多 Trigger 独立处理

一个 Bucket 可以关联多条 Trigger。事件到达后逐条匹配：
- 每条命中的 Trigger 单独生成 TaskAction。
- 不因其中一条 Trigger 命中而跳过其他 Trigger。
- 每个目标任务单独构建 TaskInvocation 和参数描述符。
- 多个任务可以共享同一 data_addr；上游必须保证所有任务结束前数据地址有效。

### 7.5 功能点 EVT-05：DIRECT 与 Bucket Trigger 路径隔离

DIRECT 优先级在 Event Dispatcher 统一处理：
- source_func_name 存在 DIRECT targets：只执行 DIRECT。
- source_func_name 为空或没有 DIRECT targets：执行 Bucket Trigger。
- 不把 DIRECT 配置写成 Immediate / ByName Trigger。
- 不在同一事件上同时执行 DIRECT 和 Bucket Trigger。

## 第 8 章 Task Builder

### 8.1 功能点 TSK-01：输入模式转换

保留现有 trigger_option 语义：

| trigger_option | input_mode | Handler 输入语义 |
|---:|---|---|
| 0 | PM_INPUT_VALUE | Value |
| 1 | PM_INPUT_KEY_VALUE | Key + Value |
| 2 | PM_INPUT_KEY_ONLY | Key Only |

DIRECT 固定使用 PM_INPUT_VALUE。

TaskArgument 内部始终包含必填 key、data_addr、data_size。input_mode 控制 Pool 构造给 Handler 的输入视图，不再选择 INLINE / SHARED_MEMORY，也不改变数据地址传递方式。

### 8.2 功能点 TSK-02：构建 arguments[]

参数结构语义：

~~~c
typedef struct {
    const char *key;
    const void *data_addr;
    size_t data_size;
} pm_task_argument_t;
~~~

当前一次 event_trigger_notify 对应一个已提交数据对象，Task Builder 构建：

~~~text
argc = 1
argv[0].key = event.key
argv[0].data_addr = data_addr
argv[0].data_size = data_size
~~~

一个事件命中多个目标函数时，每个目标分别获得自己的 TaskInvocation 和参数描述符，但 data_addr 指向同一份上游数据。

不复制 data_addr 指向的业务数据，不主动调用 Data SDK，不创建 DataRef。

### 8.3 功能点 TSK-03：TaskInvocation 组装

~~~c
typedef struct {
    const char *session_id;
    const char *so_name;
    const char *func_name;
    pm_input_mode_t input_mode;
    size_t argc;
    const pm_task_argument_t *argv;
} pm_task_invocation_t;
~~~

字段规则：

- session_id：必填，任务所属 Session。
- so_name：必填，目标动态库文件名。
- func_name：必填，目标函数符号名称。
- input_mode：DIRECT 固定 Value；Trigger 根据 trigger_option 映射。
- argc：当前固定为 1。
- argv：至少包含一个 TaskArgument，argv[0].key 必须存在。

Task Builder 必须复制异步任务需要持有的 session_id、key 等字符串，不能保留 notify 调用方的临时字符串指针。so_name、func_name 可引用 Registry 中生命周期覆盖整个运行期的不可变配置字符串，或复制到 Task 自有存储。

data_addr 是借用地址，不复制、不释放；其有效期由 Session 生命周期契约保证。

### 8.4 功能点 TSK-04：每个命中目标独立构建

- 一个 DIRECT source 对应多个 target：每个 target 一个 TaskInvocation。
- 一个 Bucket 多条 Trigger 命中：每条 Trigger 一个 TaskInvocation。
- 每个 TaskInvocation 拥有自己的描述符和字符串元数据。
- 多个 TaskInvocation 可以共享同一 data_addr。
- 不对数据地址做 retain / release；Session 结束条件必须覆盖所有派生任务。

## 第 9 章 Task Router

### 9.1 功能点 RTE-01：Function 资源需求查询

Task Router 根据 TaskInvocation 的 so_name + func_name，查询内部 Function Registry，取得该 Function 的静态 resource 配置。

至少读取：
- cpu_cores：该 Function 的 CPU 需求。
- memory_mb：该 Function 的内存需求。

找不到 Function 配置属于内部不变量错误，不得继续入队。

### 9.2 功能点 RTE-02：CPU / Memory 可用资源预检查

在调用 task_pool_try_enqueue 前执行资源预检查：

1. 获取当前节点 / 当前进程的 CPU 与 Memory 限额和使用量快照。
2. 优先通过 /proc/self/cgroup 定位当前进程所属 cgroup。
3. cgroup v2 读取 cpu.max、cpu.stat、memory.max、memory.current。
4. cgroup v1 读取对应 CPU quota / period、CPU accounting 和 memory limit / usage 文件。
5. /proc/meminfo 用于宿主机内存参考或 cgroup 信息不可用时的兜底。
6. 根据可用 CPU / Memory 与 Function 的静态需求判断是否满足准入条件。

资源查询是快照，不是资源预留；Pool 的 try_enqueue 仍然负责队列容量和原子入队。

### 9.3 功能点 RTE-03：资源不足分支

如果 CPU 或 Memory 不足：
- 不调用 task_pool_try_enqueue。
- 不把资源不足误判为 Pool 队列无容量。
- 进入 RESOURCE_INSUFFICIENT 上报分支。
- 本期只保留日志 / 监控字段和 TODO，不实现具体外部上报。
- 资源不足分支不进入 Delay Queue；Delay Queue 只处理 Pool 返回 NO_CAPACITY。

### 9.4 功能点 RTE-04：原子 try_enqueue

资源预检查通过后，调用下游 Pool Adapter 的唯一运行期回调：

~~~c
pm_pool_submit_result_t (*try_enqueue)(
    void *ctx,
    const pm_task_invocation_t *task);
~~~

try_enqueue 必须原子完成队列容量判断和入队，禁止拆分为先查询队列容量再单独 enqueue 的两阶段操作。

结果：
- ACCEPTED：Pool 接收任务，负责复制任务描述符和必要字符串；不复制、不释放 data_addr 指向的数据。
- NO_CAPACITY：Pool 不接管任务；Router 按 Delay Queue 配置决定暂存或终止。
- ERROR：Pool 内部错误；Router 终止任务并记录错误。

### 9.5 功能点 RTE-05：全局 Delay Queue

Delay Queue 是进程级全局配置，沿用当前 app.json 的 enabled、retry_interval_ms、max_wait_ms 规则。多个 App 声明的全局配置必须一致。

只有 Pool 返回 NO_CAPACITY 才进入 Delay Queue：
- enabled=true：Router 保留 TaskInvocation 元数据和 data_addr 借用视图，到期重试 try_enqueue。
- 重试成功：Pool 接收任务，Router 释放自己的任务描述符副本。
- 达到 max_wait_ms：记录 TASK_DELAY_EXPIRED，终止任务。
- enabled=false：记录 PROCESS_DISPATCH_REQUIRED，终止任务。
- 所有终止路径释放 Router 自己分配的字符串和描述符；不得释放 data_addr。

### 9.6 功能点 RTE-06：Pool 消费与协程唤醒边界

Task Router 只提交 Task，不调用单独的协程唤醒接口。Task Coroutine Pool 必须保证成功入队的 Task 最终可被内部消费者发现；队列通知、协程等待和唤醒均由 Pool 自己实现。
