# 第四部分：工程实现设计（第 15～18 章）

[返回主文档](V0.4-完整软件设计方案.md)

## 第 15 章 并发与可靠性设计

### 15.1 并发模型

本模块是进程内 C 库，不创建专用调度线程。SDK 可在多个线程/协程并发 notify；每次调用只使用栈上 Action、TaskDescriptor 和调用者独立结果缓冲区。Registry 在启动后不可变，Task ID 使用 C11 原子计数器。SDK 和 Pool callbacks 必须线程安全；不得在 Scheduler 加全局锁调用 Pool，以免串行化或阻断重入链路。

### 15.2 多生产者与准入

不同 event_id 独立处理，同 Session 不意味着串行。Pool try_submit 必须将最终容量检查和入队作为同一原子接受过程；查询到空位并非预留资源。无可用等待协程但队列有空间时仍接收。下游负责队列同步与无丢唤醒，本模块只进行契约测试。

### 15.3 生命周期与异常

SDK 基础引用贯穿 notify；每个成功构建的 Task 一份 retain。所有拒绝释放且不入队；接受后由 Pool 释放。构建时最后一步 retain；返回失败之前无需释放未取得引用。跨调用不缓存 event、Registry 指针或 Payload。配置初始化事务式完成；失败清理临时对象。退出需停止新调用、等待在途 notify，SDK 与 Pool 的依赖生命周期长于所有已接收任务。

### 15.4 部分失败、重试和去重

P0 不做自动重试、任务重放、持久事件表或 exactly-once。返回逐项结果；已接收项不回滚；调用者不得把所有失败解释为可安全重放。结果缓冲区不足发生在投递前，可安全扩容重试。同一 event_id 重复通知在 P0 可重复产生任务（必须测试并记录这一边界）。

P1 可按需求增加有界去重：DIRECT 键=(app,session,event_id,src,target)；Bucket 键=(app,session,event_id,bucket,trigger_name)。单键状态 RESERVED→ACCEPTED；拒绝则删除 RESERVED，ACCEPTED 在 TTL 内跳过；并发 RESERVED 返回 in-flight 而非已接受。不得持锁调用 SDK/Pool，不能淘汰仍 RESERVED 的项；容量耗尽明确拒绝，不静默退化。P1 若实施须补充结果字段、原子状态测试和重试契约，不影响 P0 代码范围。

### 15.5 错误与安全边界

非法配置、未声明 Bucket/函数、错误显式目标、DataRef 无效、池拒绝、内存不足分开处理。数据写成功不代表投递成功；投递成功不代表执行成功。任务无状态要求不等于幂等。进程崩溃可能丢失内存中的事件/任务，本期不提供恢复保证。SO 为可信部署，不能把 handler 或 SO 路径开放给未经验证的任意数据。

## 第 16 章 性能设计

### 16.1 调度关键路径

T0=SDK Commit 完成；T1=notify 进入；T2=匹配计数完成；T3_i=第 i 项 TaskBuilder 完成（含 retain）；T4_i=Pool 接收/拒绝的线性化点（若下游提供）；T5_i=try_submit 返回；T6=notify 返回；T7_i=工作协程开始执行（下游打点）。

- 本模块总耗时 T6−T1；每项构建/投递耗时按自身起止测量。
- Commit 到队列接收 T4_i−T0 需 Pool 线性化点支持；否则用 T5_i−T0 表示提交返回延迟，不混称入队时刻。
- Commit 到执行开始 T7_i−T0；仅成功入队样本。执行开始可能早于 try_submit 返回，不能用 T7_i−T5_i 代替排队时间。
- 排队时间仅在同一时钟和精确入队打点可用时计算 T7_i−T4_i。

### 16.2 查询与内存开销

配置预解析、稳定索引、只读数组；平均复杂度可为源/Bucket 哈希查询 O(1)（依实现），加 O(K) 匹配规则或 fan-out。两遍匹配用于预检结果容量，P0 无逐 Action 堆分配，固定大小描述符按值传递；测量描述符大小和栈预算，特别是协程栈，不假定固定大小天然最优。

### 16.3 锁、零拷贝与负载

Registry 无运行期写锁；原子 ID 仅共享计数；SDK/Pool 内部同步由对方负责。Scheduler 不复制 Payload，传元数据不是零成本；retain、描述符复制、日志均计入延迟。队列满快速返回，不自旋、不睡眠重试。P1 优化需由 profile 证明，不先引入对象池、批量路由或自定义队列。

### 16.4 性能评测

固定硬件、编译选项、并发度、队列容量、规则数、fan-out 数、数据大小与消费者速度；预热后分别测单事件命中、未命中、DIRECT、ByName、多规则及饱和。报告成功与失败吞吐、p50/p95/p99、样本数、CPU/RSS、队列满比例、每事件 retain/release 和 Payload 复制次数；性能打点与详细日志开关分别测试。区分 Mock 性能与真实集成性能，不给无实测依据的微秒指标。

## 第 17 章 日志与可观测性设计

### 17.1 日志规范

使用宿主日志接口或轻量 C adapter。结构字段：level、module、monotonic_ns、app_name、session_id、event_id、task_id、src_function、task_name、bucket、trigger_name、source_type、status、route、duration_ns。Key 按业务敏感性选择脱敏；禁止写 Payload。进程运行实例标识用于区分重启后的 ID。

### 17.2 关键日志

| 场景 | 级别 | 事件名 |
|---|---|---|
| 配置完成/失败 | INFO/ERROR | CONFIG_READY / CONFIG_INVALID |
| 事件校验失败 | WARN | EVENT_INVALID |
| DIRECT / Trigger 命中 | DEBUG | RULE_MATCHED |
| 构建失败 | WARN | TASK_BUILD_FAILED |
| 本地接收 | DEBUG | LOCAL_SUBMIT_OK |
| 队列满 | WARN | PROCESS_DISPATCH_REQUIRED |
| 其他池拒绝 | WARN | LOCAL_SUBMIT_REJECTED |

PROCESS_DISPATCH_REQUIRED 示例：event_id=42 task_id=7 function=processor.so reason=QUEUE_FULL dispatched=false。必须能区分“需要进程间分发”与“实际分发成功”；该日志只在 POOL_QUEUE_FULL 分支触发。性能测试可关闭逐事件 DEBUG，满队列日志若限频须保留计数和可观测证据。

### 17.3 指标

events_total（valid/invalid/no_match）、matched_total（DIRECT/IMMEDIATE/BY_NAME）、tasks_enqueued_total、tasks_overflow_total、tasks_failed_total、notify_latency、build_latency、submit_latency、可选 Pool 公开的 queue_depth；引用余额通过 Mock/SDK 测试计数核对。计数器并发安全、不开启高基数事件 ID 标签。P0 可由测试 Harness 采集，无须另建监控服务。

### 18.2 依赖与编译

Linux、C11、CMake、cJSON（启动解析）、必要时 C11 atomics/pthread（仅同步需求）。优先静态库 task_scheduler_core；公开头文件无第三方 JSON 依赖，真实 SDK/Pool 经 adapter 连接。Mock 不进入正式库。编译启用 -Wall -Wextra -Werror，测试用 ASan/UBSan，独立 TSan 运行；固定依赖版本待编码时确认。SO 示例可使用 gcc -std=c11 -fPIC -shared。

### 18.3 构建与集成建议

```cmake
# 计划示例：待源文件实现后使用
cmake_minimum_required(VERSION 3.16)
project(pheromone_mini LANGUAGES C)
set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)
find_package(cJSON CONFIG REQUIRED)
add_library(task_scheduler_core STATIC
    src/config/config_loader.c src/config/config_validator.c
    src/registry/function_registry.c src/registry/dependency_registry.c
    src/registry/trigger_registry.c src/trigger/event_trigger.c
    src/trigger/direct_dependency.c src/trigger/immediate_trigger.c
    src/trigger/byname_trigger.c src/trigger/task_builder.c
    src/router/task_router.c src/router/task_pool_adapter.c)
target_include_directories(task_scheduler_core PUBLIC include PRIVATE src/private)
# cJSON package exported target name 以实际发行包为准
target_link_libraries(task_scheduler_core PRIVATE cjson)
target_compile_options(task_scheduler_core PRIVATE -Wall -Wextra -Werror)
```

### 18.4 Mock 与 Demo

Mock Data SDK 维护对象 token、版本、长度、引用计数；模拟 Commit、validate/retain 错误和释放，业务数据用内存块模拟。Mock Pool 仅作为测试桩：固定容量、接收时复制描述符、记录 wake 尝试、模拟完成后释放引用；不开发生产协程池。先用 Mock 验证全部本模块 P0，再替换真实 adapters。JSON 与 C 业务示例放在 docs/examples 供评审；正式编码时移入工程 examples。运行命令待实际构建目标完成，不能宣称当前仓库已有可运行 Demo。
